Beginner

1. What is Apache Iceberg?

Apache Iceberg is an open table format for large analytic datasets. It defines how data files (Parquet, ORC or Avro) and metadata files together make up a table, so that different engines can read and write that table safely. It was created at Netflix and is now a top-level Apache project.

It is a written specification plus libraries that engines embed, with no Iceberg server in the data path. The metadata it writes next to the data records which files belong to the table right now, what the columns are, how the files are partitioned and which rows have been deleted. On that basis it gives plain files atomic commits, snapshot isolation, schema and partition evolution, row-level DELETE, UPDATE and MERGE, and a history you can query or roll back to.

The value shows when several jobs touch the same data. A reader sees all of a write or none of it, even while another job is still writing. Iceberg does not compact files or delete old ones on a schedule, though; those remain jobs you run. The example below creates a first table and reads it.

DROP TABLE IF EXISTS demo.shop.hello PURGE;
CREATE TABLE demo.shop.hello (id BIGINT, name STRING) USING iceberg;
INSERT INTO demo.shop.hello VALUES (1, 'first'), (2, 'second');
SELECT * FROM demo.shop.hello ORDER BY id;
2. What problems with Hive tables does Iceberg solve?

A Hive table is a directory, and its partitions are subdirectories. The metastore knows the partitions while the file system knows the files, and nothing ties the two together atomically. Most of the pain follows from that split.

Readers can see a job that has written only some of its partitions, and coordinating concurrent writers is left to the user or to Hive locks. Planning lists every partition directory, so it slows down as partitions multiply. Queries have to filter on the partition column to avoid a full scan, changing the partitioning means rewriting the table, and renaming a column can make old files read wrongly. Hive’s transactional tables address part of this, but they are tied to ORC and Hive’s transaction manager.

Iceberg removes the root cause by tracking individual files in a snapshot instead of directories. A commit swaps one pointer, so a write appears all at once. Planning reads manifests and skips most of them, filters on the real column still prune, new partitioning applies to new data only, and columns are matched by ID.

3. Is Iceberg a file format, a storage system or a query engine?

Iceberg is none of the three. It is the table layer between the query engine and the files, recording which files make up a table, with which schema, at a given point in time.

The other layers stay separate. Parquet, ORC or Avro files hold the rows, object storage or HDFS holds the files, and Spark, Flink, Trino and other engines run the queries. A catalog is also required to commit safely. The catalog interface is part of the Iceberg project, while the service behind it, such as a Hive Metastore or a REST server, is something you operate.

Because the layers are independent, you can change one without the others, for example moving queries from Spark to Trino without converting data. It also means a slow query can come from several places: small row groups in the file format, too many small files in the table, a poor join plan in the engine, or throttling in storage. Finding the layer first points to the right fix.

4. Which file formats can an Iceberg table use?

Iceberg stores data and delete files as Parquet, ORC or Avro. Parquet is the default, set by write.format.default, and new tables compress it with zstd. Metadata uses JSON for the table metadata file and Avro for manifest lists and manifests.

The format is recorded for each file in the manifest, so one table can hold more than one, for example after migrating a mixed Hive table or after changing the default. Compaction rewrites files in whatever format is configured at that time. Parquet and ORC are columnar and suit analytics, with Parquet having the widest engine support. Avro is row based and fits landing data that is read whole. Manifests use Avro because planning reads them row by row, one file description at a time.

In files written by Iceberg, column IDs let readers map old files to the current schema, and imported files without IDs need a name mapping. Support for particular features can differ by format and engine reader, so test the exact combination, such as deletes on ORC, instead of assuming parity.

5. Which engines work with Iceberg?

Spark, Flink, Trino, Presto, Hive, Impala, Dremio, StarRocks and a number of cloud warehouses can work with Iceberg tables. Support differs from engine to engine, so it is a matrix rather than a yes or no.

For each engine, check four things: whether it can read your format version including every delete type in use, which write operations it supports (append, overwrite, MERGE), which catalogs it can talk to, and whether it can run maintenance. A common arrangement has Flink ingesting streams, Spark running merges and maintenance, and Trino or a warehouse serving interactive reads, all resolving the same catalog.

The least capable reader sets the limit. Once a table uses a newer feature, every consumer has to understand it, so one old engine can hold back an upgrade for the whole table. Before upgrading an engine or the format, write a test table with each writer, read it with each reader and compare counts and aggregates.

6. What is a snapshot?

A snapshot is the complete state of a table at one commit: the set of data and delete files that were live at that moment. Every write produces a new snapshot and never edits an old one.

Each snapshot has a random ID, a parent, a sequence number, a timestamp, a path to the manifest list that names its manifests, and a summary of what changed. The operation is recorded as append for added files, overwrite for a change that adds and removes data, delete for removed data, or replace for a rewrite such as compaction that leaves results unchanged.

A snapshot is a list of references, not a copy, so many snapshots of a mostly unchanged table share almost all their files. That is what makes time travel and rollback cheap. Order snapshots by committed_at, never by ID. The snapshots table lists those that exist, while history shows which one was current at each time, including rollbacks.

SELECT snapshot_id, operation, committed_at
FROM demo.shop.orders.snapshots
ORDER BY committed_at;
7. How does Iceberg provide ACID guarantees on object storage?

Every file a write produces is new and stays invisible until the commit. The commit itself is one atomic step in which the catalog moves the table’s pointer from the old metadata file to the new one.

That single step provides atomicity, since the pointer either moves or it does not. A commit is accepted only against the version it was built on and is validated against concurrent changes, which keeps the table consistent. A reader loads one metadata file and sees that snapshot for the whole query, giving isolation, and files reach durable storage before anything references them.

Object storage therefore needs no transactions of its own, because Iceberg never modifies a file and never relies on listing a directory. The guarantee covers one table per commit, so two statements are two commits and a reader can see the state between them. Files from a failed write remain in storage unseen until remove_orphan_files deletes them.

before   catalog -> v7.metadata.json -> snapshot 7 -> files A, B
         writer creates files C, new manifests, v8.metadata.json
commit   catalog -> v8.metadata.json -> snapshot 8 -> files A, B, C
8. What is a catalog and why does Iceberg need one?

A catalog maps a table name to the location of its current metadata file and performs the atomic swap of that location during a commit. It may also manage namespaces, create and rename tables, and in some products control access, vend credentials or store views.

Storage alone cannot do this, because a table directory holds many metadata files and nothing in them says which is current. A commit asks the catalog to replace metadata file X with Y only if X is still current. If another writer got there first, the request is rejected and the writer reloads and retries.

This check and swap is what makes concurrent writes safe, so the catalog affects correctness and not just discovery: two tables that look identical in storage can have different guarantees. If the catalog is unavailable, queries and commits cannot resolve the table even though the files are intact, apart from a session still using a cached copy. Plan its availability and backups.

The catalog answers one question and performs one atomic swap.

9. Describe the layers of Iceberg metadata.

Iceberg metadata is a tree with the catalog at the top. The catalog points to a metadata JSON file, which lists snapshots; each snapshot has a manifest list, which names manifests; and the manifests name the data and delete files.

The metadata file keeps the table UUID, every schema and partition spec used so far, sort orders, properties, the snapshot and metadata logs and the named references. A manifest list has one row per manifest, and a manifest has one row per file with its partition values and statistics. Everything below the catalog is immutable. A commit that creates a snapshot writes a new metadata file and manifest list, while a change without a snapshot writes only the metadata file.

Each level summarises the one below, so planning can skip whole branches and a commit can reuse unchanged ones. The cost is that metadata files, manifest lists and manifests accumulate and are cleaned by different settings and procedures. The query below shows the chain of metadata files.

The three tiers of a table.

SELECT timestamp, file, latest_snapshot_id
FROM demo.shop.orders.metadata_log_entries
ORDER BY timestamp DESC LIMIT 3;
10. What is the difference between a manifest and a manifest list?

A manifest lists data files or delete files, one entry per file. A manifest list belongs to a single snapshot and lists the manifests that make it up.

The manifest list records each manifest’s partition value ranges, file and row counts and sequence numbers. A manifest entry records one file’s partition values, record count, size and per-column counts and bounds, and marks the file as added, existing or deleted, which is how incremental reads find what a commit added. A manifest covers one partition spec and holds either data files or delete files. A new manifest list is written for every snapshot, whereas manifests are shared between snapshots.

The split saves work twice. A query for one day can drop a manifest that covers other days without opening it, and a commit that adds one file writes one small manifest and reuses the rest. Pruning weakens when each manifest spans many partitions, which rewrite_manifests corrects.

SELECT path, partition_spec_id, added_data_files_count, existing_data_files_count
FROM demo.shop.orders.manifests;
11. What is hidden partitioning?

Hidden partitioning means a table declares its partition as a transform of an ordinary column, such as days(order_ts), and Iceberg derives the value itself. Writers supply no separate partition column, and readers filter on the real one.

During planning, a row filter is projected onto each transform, so order_ts >= X becomes a condition on the day of order_ts. The projection is inclusive: it may keep a partition with no matching row but never drops one that holds matching rows. A bucket transform can be projected from equality and IN filters but not from ranges, because hashing destroys order.

Hive instead needs an extra column such as dt that writers must compute correctly and readers must remember to filter on. Hidden partitioning removes both mistakes and lets the granularity change later without rewriting queries. Wrapping the column in an arbitrary function can still block pruning, so compare it with literal bounds, as in the plan below.

EXPLAIN SELECT order_id, amount FROM demo.shop.orders
WHERE order_ts >= TIMESTAMP '2026-11-02 00:00:00'
  AND order_ts <  TIMESTAMP '2026-11-03 00:00:00';
12. Which partition transforms does Iceberg support?

A partition transform turns a column value into a partition value. The specification offers identity, year, month, day, hour, bucket, truncate and void, summarised in the table below.

Time transforms suit time-series data. bucket applies a 32-bit Murmur3 hash and takes the result modulo N, so every engine computes the same bucket and bucketed tables can be joined consistently. For strings, truncate keeps the first W characters; for numbers it rounds down to a multiple of W, so truncate(100, id) groups 0 to 99, then 100 to 199. void always produces null and is used for removed fields in version 1 tables.

Several fields can be combined, such as days(order_ts), bucket(4, customer_id), but the partition count multiplies, so check that each combination still fills files near the target size. Partitioning on a raw timestamp creates one tiny file per distinct value, and changing N in a bucket applies only to new data.

identity The value itself region Low-cardinality columns
year, month, day, hour Time unit since 1970 days(order_ts) Time-series data
bucket[N] Hash of the value modulo N bucket(16, customer_id) High-cardinality keys, joins
truncate[W] Value cut to width W truncate(4, sku) String prefixes, numeric ranges
void Always null   Removed fields in version 1 tables
13. What schema changes can you make without rewriting data?

You can add, drop, rename and reorder columns, including fields inside structs, widen some types and make a required column optional. All of these change metadata only.

Old files stay readable because every column has an ID. Reading a file written under an earlier schema, Iceberg matches by ID: a renamed column is found, a dropped one is ignored, and a newly added one reads as null, or as its declared default on format version 3. Making an optional column required is refused by default because old files may contain nulls, narrowing a type is refused because values may not fit, and a partition source column cannot be dropped while a spec uses it.

A cheap change is not a harmless one. Renaming or dropping a column still breaks queries, views and downstream jobs that use the old name. Spark can also add columns during a write when write.spark.accept-any-schema and mergeSchema are set, so enable that deliberately, or a typo becomes a column.

ALTER TABLE demo.shop.orders ADD COLUMN channel STRING;
ALTER TABLE demo.shop.orders RENAME COLUMN channel TO sales_channel;
ALTER TABLE demo.shop.orders ALTER COLUMN amount TYPE DECIMAL(12,2);
ALTER TABLE demo.shop.orders DROP COLUMN sales_channel;
14. What is time travel?

Time travel means querying a table as it was at an earlier snapshot, chosen by snapshot ID, timestamp, branch or tag.

For a timestamp, Iceberg looks in the snapshot log for the snapshot that was current at that moment and plans the scan from its manifest list. Nothing is reconstructed, because the old files are still there. A read by snapshot ID, timestamp or tag uses the schema that belonged to that snapshot, while reading a branch uses the table’s current schema.

It is useful for comparing results before and after a job, for reproducing training data from a tagged snapshot and for recovering rows removed by mistake. It works only while the snapshot exists: once expiry removes it, that point in history is gone, which a tag can prevent. It is also not a backup, since losing the files or the bucket destroys the history with them.

ALTER TABLE demo.shop.orders CREATE TAG initial_load;

SELECT count(*) FROM demo.shop.orders VERSION AS OF 'initial_load';
SELECT count(*) FROM demo.shop.orders TIMESTAMP AS OF current_timestamp();
15. What is a table format version?

The format version states which features a table’s metadata may use, so that an older reader does not misread newer ones. Current libraries create version 2 tables by default.

Version 1 covers analytic tables on immutable files. Version 2 added row-level deletes through delete files and sequence numbers. Version 3 adds deletion vectors, row lineage, default values and new types, and version 4, which introduces relative paths in metadata, is still under development. A new version is introduced only when an older reader would otherwise get wrong results; one that ignored delete files would return deleted rows.

Choose the lowest version that provides what you need and that every engine supports. Upgrading is a single property change that rewrites nothing, with new features applying to later writes, but there is no downgrade. A newer library reads older tables, while an older one may fail on newer tables. You can check a table’s version as shown below.

SHOW TBLPROPERTIES demo.shop.orders ('format-version');
16. What are copy-on-write and merge-on-read?

Copy-on-write and merge-on-read are two ways to change rows held in files that cannot be edited. Copy-on-write rewrites the affected files, while merge-on-read leaves them in place and records which rows are gone.

Copy-on-write makes writes expensive, since every touched file is rewritten, and adds nothing to reads. Merge-on-read writes small delete files or deletion vectors quickly, and every scan then has to apply them. The mode is chosen separately with write.delete.mode, write.update.mode and write.merge.mode, all defaulting to copy-on-write. Appends only add files in either mode.

Choose by how often data changes. Rare changes with heavy reading favour copy-on-write, and frequent small changes such as change data capture favour merge-on-read. The latter does not remove the cost of rewriting but moves it to compaction, so a merge-on-read table without a compaction job gets slower with every write.

The same delete under both modes.

17. Does Iceberg support UPDATE, DELETE and MERGE?

Yes. Iceberg supports UPDATE, DELETE and MERGE in engines that implement them, and Spark needs the Iceberg SQL extensions.

Spark scans the target to find affected files, joins it with the source for a MERGE, then writes either replacement files or delete markers plus new rows, depending on the table’s mode, and commits everything as one snapshot. A DELETE that matches whole files, such as an entire partition, can be done in metadata alone. If two source rows match one target row, the MERGE fails, although two source rows with a new key are both inserted.

Iceberg has no primary key index, so a MERGE is a real join. Put partition predicates in the ON clause so that only the relevant part of the table is scanned and fewer concurrent writers conflict. For upserts, a MERGE states the intent by key, whereas an overwrite depends on how the table happens to be partitioned.

UPDATE demo.shop.orders SET status = 'PAID' WHERE order_id < 100;
DELETE FROM demo.shop.orders WHERE order_id BETWEEN 100 AND 109;

MERGE INTO demo.shop.orders t
USING (SELECT 1L AS order_id, 'SHIPPED' AS status) s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.status = s.status;
18. What are metadata tables?

Metadata tables are read-only tables that expose Iceberg’s own metadata through ordinary SQL, addressed as a suffix on the table name.

files, data_files and delete_files show live files with sizes and statistics, partitions shows rows and files per partition, and manifests shows how planning metadata is organised. snapshots and history describe what changed and when, refs lists branches and tags, and metadata_log_entries lists earlier metadata files. File and manifest tables describe the current snapshot; their all_ variants cover every snapshot and can list a file more than once, so count distinct paths.

They are the first place to look when diagnosing small files, delete build-up or unexpected growth. Because they are queryable, you can alert on average file size, delete file count or snapshot age without parsing metadata files, and several support time travel to show an earlier layout.

SELECT file_path, record_count, file_size_in_bytes FROM demo.shop.orders.files;
SELECT * FROM demo.shop.orders.history;
SELECT partition, file_count, record_count FROM demo.shop.orders.partitions;
SELECT name, type FROM demo.shop.orders.refs;
19. How is an Iceberg table different from a folder of Parquet files?

A folder of Parquet files does not say which files count, what the current schema is or when a write finished. An Iceberg table records all three in its metadata.

With a plain folder, the table is whatever a listing returns, completeness is guessed from marker files and the schema is inferred or kept elsewhere. In Iceberg only the files referenced by the current snapshot belong to the table, a write becomes visible only on commit, and the schema is versioned and tracked by column ID. A file copied into the data directory is ignored, while deleting a referenced file breaks queries. Existing files are brought in with add_files, snapshot or migrate, without rewriting them.

Keeping that metadata is what makes atomic row removal and access to earlier states possible. The price is metadata, a catalog and maintenance jobs, so for a small append-only dataset with one reader, plain Parquet can be the simpler choice.

20. How does Iceberg compare with Delta Lake and Apache Hudi?

Iceberg, Delta Lake and Apache Hudi all provide ACID tables on object storage, with different designs: Iceberg uses a tree of snapshots and manifests, Delta Lake a transaction log with checkpoints, and Hudi a timeline with record keys and file groups.

Iceberg commits by swapping a catalog pointer and offers hidden, evolvable partitioning, with engine neutrality as its main strength. Delta Lake commits by writing the next log entry and integrates closely with Spark and Databricks. Hudi records instants on its timeline and indexes record keys, which targets frequent upserts and incremental pipelines.

Choose from your engines and workload. Iceberg is a weaker fit when the main job is high-rate keyed upserts that a record index handles more cheaply, or when your platform’s tooling is built around another format. Speed depends on layout and versions, so benchmark on your own data. The comparison of the open table formats goes further.

21. What happens when you run an INSERT?

An insert writes data files first, then the metadata describing them, and finally asks the catalog to make that metadata current. Nothing is visible until the last step.

Executors write the data files, grouped by partition after applying the transforms, and report paths and column statistics to the driver. The driver writes the manifest, manifest list and metadata file and then commits. If the job fails before the commit, readers see nothing and the files become orphans. If another writer commits first, the driver reapplies the append on the new base and retries without rewriting data, since adding files cannot conflict logically.

Every insert is therefore a commit and a new snapshot. A loop of single-row inserts creates a data file, a manifest, a manifest list and a metadata file each time, which is why rows should be batched.

1. write data files            (executors)
2. write a manifest            lists the new files and their statistics
3. write a manifest list       new manifest + reused manifests
4. write a metadata file       adds the snapshot, makes it current
5. catalog swap                only if the base version is still current
22. How do you roll a table back?

You roll a table back by calling a procedure that makes an earlier snapshot current. No data is rewritten.

rollback_to_snapshot takes a snapshot ID and rollback_to_timestamp a time, and both are limited to ancestors of the current snapshot. set_current_snapshot accepts any snapshot or reference. cherrypick_snapshot is different: it applies one snapshot’s changes as a new commit. After a rollback the newer snapshots remain in metadata until expiry, and history records that the current pointer moved back. Schema and property changes are not undone.

A rollback discards every later good commit on that branch, and a consumer that already processed the removed data is not told. To undo one bad commit while keeping later ones, repair forward instead: read the correct rows from the snapshot before it with time travel and merge them into the current table.

DELETE FROM demo.shop.orders WHERE status = 'PAID';

CALL demo.system.set_current_snapshot(table => 'shop.orders', ref => 'initial_load');

SELECT count(*) FROM demo.shop.orders;
23. What is the difference between DROP TABLE and DROP TABLE PURGE?

DROP TABLE ... PURGE in Spark asks for the table’s data and metadata files to be deleted. What a plain DROP TABLE keeps depends on the catalog.

Hive, REST and similar service catalogs typically remove only the entry and leave the files, so the table can be brought back by registering its latest metadata file with register_table. The Hadoop catalog used in these examples has no separate entry, because the directory is the table, so it deletes the directory even without PURGE. Tables created with the snapshot procedure have gc.enabled set to false so that Iceberg does not delete files they do not own.

After a purge, recovery depends entirely on storage protection such as object versioning or backups. A catalog may add soft delete or refuse a purge, so test yours before relying on a drop either for cleanup or for recovery, restrict who can drop tables, and record metadata locations.

24. Where does Iceberg store a table's files?

An Iceberg table normally keeps its files under the table location, with data and delete files in a data directory and metadata files, manifest lists and manifests in a metadata directory.

That layout is a convention, because metadata records the full path of every file. Files can live elsewhere: imported files stay where they were, the object storage layout spreads them under hashed prefixes, and write.data.path or write.metadata.path can redirect new ones. Directory names that look like partitions are only for people, since partition values come from manifests. To find the current metadata file, ask the catalog or query metadata_log_entries.

Paths are absolute through format version 3, so copying a directory to another bucket does not move the table; rewrite_table_path prepares metadata for the new prefix. Never point two tables at one location, or orphan removal on one can delete the other’s files.

<table location>/
  data/
    order_ts_day=2026-11-01/00000-...parquet
  metadata/
    00001-<uuid>.metadata.json      or v1.metadata.json (Hadoop catalog)
    snap-<snapshot>-...avro         manifest lists
    <uuid>-m0.avro                  manifests
25. Does Iceberg require Hive Metastore?

No. The Hive Metastore is one catalog option among several, which include REST, JDBC, AWS Glue, Nessie and the Hadoop catalog.

In a Hive catalog, the metastore entry holds a property pointing to the current metadata file. The schema is mirrored there for other tools, but Iceberg’s metadata file remains the source of truth. A REST catalog gives every engine one API and can enforce access control, with whatever storage the server chooses behind it. The JDBC catalog uses a relational database. The Hadoop catalog needs no service at all but is unsafe on object stores.

Many platforms keep using Hive because they already run it. For a new platform a REST catalog is the usual choice, provided your engines support it and someone will operate it. To move between catalogs, stop writers, register the latest metadata file in the new one and repoint every client, never writing through both.

Intermediate

26. How does Iceberg plan a query?

Query planning narrows the files to read in stages, using metadata only.

Iceberg loads the current metadata file and picks a snapshot, reads its manifest list and skips manifests whose partition ranges cannot match, then reads the remaining manifests and drops files by partition value and column bounds. It attaches the relevant delete files and splits what is left into tasks, after which Parquet row group and page statistics prune within files. Filters are projected onto the partition spec each manifest was written with, so partition evolution does not break pruning. Manifests can be planned on the driver or across the cluster, controlled by read.data-planning-mode and read.delete-planning-mode.

Pruning is only as good as the metadata. Overlapping bounds, scattered manifests and filters on columns without statistics leave more files in the scan. Confirm the result by checking pushed filters in the plan and files read in the Spark UI.

Two rounds of pruning happen before any data file is opened.

27. What column statistics does Iceberg keep, and what limits them?

Iceberg keeps, for each file and column, value counts, null counts, NaN counts, column sizes and lower and upper bounds. Planning uses them to skip files, so a filter amount > 900 ignores a file whose upper bound is 800.

The metrics mode can be none, counts, truncate(N) or full. The default truncate(16) keeps a 16-character prefix of string bounds, rounding a truncated upper bound up so that it still covers every value. Bounds are stored as bytes in a standard single-value form, because one manifest schema must hold any column type. For wide tables, metrics are inferred only for the first 100 columns.

More statistics prune better but enlarge manifests and slow planning. Set full or another mode per column where it matters, for example an identifier whose first 16 characters are identical everywhere; the change affects only new files. Even good bounds skip nothing if every file spans the whole range, which sorting fixes.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'write.metadata.metrics.column.status' = 'full');
28. Why are column renames safe?

Column renames are safe because every field has a permanent ID and data files record those IDs. A rename changes only the name attached to an ID.

Readers match columns by ID, including struct fields, list elements and map keys and values. An ID is never reused, so a column dropped and added again under the same name is a new column: current queries read null for older rows, while time travel to an earlier snapshot still shows the old values under that snapshot’s schema.

Formats that match by name can expose old data when a name is reused, and formats that match by position shift columns when one is dropped. Files written outside Iceberg carry no IDs, so a name mapping in schema.name-mapping.default tells readers which names correspond to which IDs. Migration procedures set it up, and if you later rename such a column, keep the old name in the mapping.

A rename edits the schema, not the files.

29. Which type promotions are allowed?

Iceberg allows only widening type changes, ones that can still read every old value exactly. The table below lists them with the format versions that support each.

Old files are not rewritten. Their statistics remain usable because readers can tell the original type from the encoded length. Narrowing is rejected since values could overflow, and changing a decimal’s scale would change what stored numbers mean. Changing string to int is not allowed, because every old file would need rewriting and some values might not parse. For any such change, add a new column, backfill it, switch readers over and drop the old one. The example performs permitted promotions on a scratch table.

30. What is partition evolution?

Partition evolution means changing the partition spec of an existing table. Each manifest records the spec its files were written with, so old data keeps its layout and new data uses the new one.

ADD PARTITION FIELD, DROP PARTITION FIELD and REPLACE PARTITION FIELD change how future writes are partitioned, for instance from months to days. A query is projected onto each spec separately, so original fields prune old files and all fields prune new ones. You can evolve the spec again, and existing files keep whatever they had.

This avoids rewriting a large table just to change its layout. Rewrite old files with rewrite_data_files only if queries on them need the new layout. Dynamic partition overwrite uses the current spec, so the same INSERT OVERWRITE can replace a different amount of data afterwards; check those jobs before making the change.

Old and new layouts live side by side.

ALTER TABLE demo.shop.orders ADD PARTITION FIELD bucket(4, customer_id);

INSERT INTO demo.shop.orders (order_id, customer_id, amount, status, order_ts)
VALUES (2001, 3, 15.00, 'NEW', TIMESTAMP '2026-11-02 08:00:00');

SELECT spec_id, count(*) AS files FROM demo.shop.orders.files GROUP BY spec_id;
31. Why does Iceberg not need to list directories?

Iceberg does not need to list directories because its manifests already name every file in a snapshot. Planning reads metadata instead of asking storage what exists.

A directory-based planner issues at least one listing for each partition, and object stores return listings in pages, so cost grows with partitions and files. Iceberg reads the manifest list and then only the manifests that might match. File statistics are already in those manifests, so footers need not be opened just to prune.

It also helps correctness, since a listing cannot distinguish a finished file from one still being written or a leftover from a failed job, whereas a manifest lists only committed files. Listing does still happen in remove_orphan_files, which looks for files absent from metadata and is expensive for that reason. The thing to watch instead is too much metadata, visible in the manifests and files tables.

32. How do you choose a partitioning scheme?

Choose a partitioning scheme from the filters your queries use and the amount of data per partition, and start coarse, because the spec can evolve later.

Time-series tables usually use days(ts), or months(ts) when a day holds little data, and hours(ts) only at very high volume. A key used for point lookups or joins suits bucket(N, key), a column with few values that is always filtered can use identity, and a small table may need no partitioning. Estimate bytes per partition per day, and multiply cardinalities before combining fields.

The common mistake is over-partitioning, which creates tiny files, heavy metadata and many open files per write, especially in streaming. For a second filter column, sorting often gives file skipping without multiplying partitions. Validate by running real queries, comparing files scanned with files in the table and checking the spread in the partitions table.

33. What is a table sort order, and how does it help?

A table sort order is a declared ordering that writers apply, so each file covers a narrow range of the sort columns and its column bounds become selective.

WRITE ORDERED BY range-shuffles data and orders it across tasks and within files. WRITE LOCALLY ORDERED BY sorts only within each file, and WRITE DISTRIBUTED BY PARTITION controls how rows are grouped without ordering them. These apply to new writes; existing files need a compaction with the sort strategy, and a Z-order rewrite can spread the benefit over several independent filter columns at some cost to the first.

Without clustering, every file may span all values and a filter reads them all. Sorting adds work to each write, so it pays off when a table is read far more than it is written. It is also the better tool for high-cardinality columns, which would create huge numbers of tiny partitions. See sorting and clustering.

Narrow ranges are what let a filter skip files.

ALTER TABLE demo.shop.orders WRITE ORDERED BY customer_id, order_ts;

unsorted   file1 [cust 1..99]   file2 [cust 0..98]   -> filter reads both
sorted     file1 [cust 0..49]   file2 [cust 50..99]  -> filter reads one
34. What are the write distribution modes?

The write distribution mode decides how rows are shuffled before files are written. The property write.distribution-mode accepts none, hash or range.

With none there is no shuffle and each task writes whatever it holds, which is cheapest but can produce tasks times partitions files. hash shuffles by partition value, giving few files per partition. range samples the data and range-shuffles on partition and sort keys, producing globally ordered output at the highest cost. When the property is unset, Spark picks range for sorted tables, hash for partitioned ones and none otherwise.

With 200 tasks each holding 30 days of data, none could write 6,000 files in one commit where hash writes about one per day. A very large partition under hash can be split by adaptive execution. Under none, rows must be clustered within tasks or the fanout writer enabled. Row-level operations have separate settings such as write.merge.distribution-mode.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'write.distribution-mode' = 'hash');
35. What controls output file size?

Output file size is controlled by write.target-file-size-bytes, 512 MB by default. It is a target rather than a guarantee.

A task cannot write a file larger than the data it holds, files never cross partition boundaries, and compressed output is far smaller than the shuffle data it came from, while very large tasks roll over into several files. With a shuffling distribution mode, adaptive execution sizes write tasks from spark.sql.adaptive.advisoryPartitionSizeInBytes, which measures shuffle data and so usually has to exceed the file target.

Large files suit full scans, while smaller ones can help selective queries and reduce copy-on-write rewrite cost. If files are far below target, for example 20 MB against 512 MB, each task or partition usually holds little data or commits are too frequent. Write reasonably sized files and let compaction reach the target. The statement below lowers it for one table.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'write.target-file-size-bytes' = '134217728');
36. Why are small files a problem?

Small files are a problem because each one adds a manifest entry, a request to open it and a footer to parse, whatever its size.

Planning has more entries to read, scans spend their time opening files, compression works worse on little data, object stores charge and throttle by request, and merges have more files to join. The usual causes are frequent commits, fine partitioning, high write parallelism with little data and the none distribution mode.

Measure by comparing average file size in the files table with the target and counting files per partition; no fixed size is too small, but files far below target in large numbers are the signal. Compaction repairs existing files, while longer triggers, coarser partitioning or hash distribution stop new ones. Storage is not freed until old snapshots expire, because they still reference the original files.

37. How does compaction work?

Compaction in Iceberg is done by rewrite_data_files, which reads selected files and commits larger replacements in a replace snapshot.

A file is a candidate when it is below 75% or above 180% of the target size, or when its deletes cross a threshold. Candidates are grouped per partition, and a group is rewritten if it has at least five files, holds more than one file totalling over the target size, exceeds the maximum file size or contains a file over a delete threshold. where limits the scope, strategy => 'sort' re-clusters data, rewrite-all ignores the selection rules, partial-progress.enabled commits group by group and max-concurrent-file-group-rewrites (default 5) sets parallelism. Delete rewriting is steered by delete-file-threshold, effectively off by default, and delete-ratio-threshold, 0.3.

It is safe to run because results do not change. The commit fails if a rewritten file was removed or deleted from meanwhile, and the new files keep the starting sequence number so that later equality deletes still apply. If nothing is rewritten, no group met a trigger.

CALL demo.system.rewrite_data_files(
  table => 'shop.orders',
  options => map('min-input-files', '2'));
38. What does expire_snapshots do?

expire_snapshots removes old snapshots from metadata and deletes the files that no remaining snapshot references. It is what actually reclaims storage.

Every branch and tag head is kept. On each branch, ancestors survive while they are younger than the age limit or within the minimum count, set by history.expire.max-snapshot-age-ms (five days) and history.expire.min-snapshots-to-keep (one). A run can override these with older_than and retain_last or name snapshot_ids. stream_results avoids collecting a huge delete list on the driver, max_concurrent_deletes deletes in parallel and clean_expired_metadata drops unused specs and schemas.

Afterwards, time travel, rollback and incremental reads before the retained point no longer work. If nothing is deleted, the files are still held by a retained snapshot, often through a branch or tag, or the snapshots are too young. The date in the example is far in the future only so that everything on a test table qualifies.

CALL demo.system.expire_snapshots(
  table => 'shop.orders',
  older_than => TIMESTAMP '2030-01-01 00:00:00',
  retain_last => 5);
39. What are orphan files, and how do you remove them?

Orphan files are files under the table location that no metadata references, usually left behind by failed or killed jobs. remove_orphan_files finds and deletes them.

The procedure lists the location, collects every file referenced by any snapshot’s metadata and treats the rest, beyond an age limit, as orphans. The limit defaults to three days and may not be under 24 hours, because a file from a write still in progress looks exactly like an orphan. Use dry_run to list without deleting and location to narrow the search. Expiry cannot do this job, since it never learns of files that no snapshot ever knew.

Path forms are the main danger. If metadata stores one URI form and the listing returns another, live files appear unreferenced. equal_schemes and equal_authorities declare variants equivalent, and prefix_mismatch_mode defaults to ERROR; do not switch it to DELETE without understanding the mismatch.

CALL demo.system.remove_orphan_files(table => 'shop.orders', dry_run => true);
40. When do you rewrite manifests?

Rewrite manifests when planning is slow because the table has many small manifests, or manifests whose entries are spread across partitions so that none can be skipped.

The procedure reads manifest entries, sorts and groups them by partition fields, writes reasonably sized manifests and commits a new snapshot. Data files are untouched. Iceberg already merges manifests during many commits when commit.manifest-merge.enabled is true, but streaming writes use fast appends by default, which skip merging, so streaming tables benefit most.

The payoff is that a filter on one partition can then open only the manifests covering it. Check the count, size and partition summaries in the manifests table first, and compact small data files before this, since compaction changes the entries anyway. A rewrite invalidates cached plans for the table and can conflict with concurrent commits.

CALL demo.system.rewrite_manifests('shop.orders');

after   m1 [day1, day2]        m2 [day5]   m3 [day8, day9]
41. Why do metadata files pile up, and how do you stop it?

Metadata files pile up because every commit writes a new metadata.json and, by default, old ones are kept.

Two table properties delete earlier files after each commit, with a default of 100 retained versions. That cleanup covers only files tracked in the metadata log, so any that left the log before it was enabled remain until orphan removal. The files also grow, since each lists every retained snapshot along with schemas and properties; expire_snapshots shrinks that list and removes the related manifest lists, while manifests are handled by rewrite_manifests, commit-time merging and expiry.

This matters for tables that commit often. A table committing every minute without expiry rewrites an ever larger JSON file each time, which slows commits and raises the chance of conflicts. On an old table, check the file size and snapshot count, expire snapshots first, then enable the cleanup shown below.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'write.metadata.delete-after-commit.enabled' = 'true',
  'write.metadata.previous-versions-max' = '50');
42. What is the difference between a branch and a tag?

Branches and tags are both named references to a snapshot. A branch moves as you commit to it, while a tag stays on one snapshot.

A branch accepts writes and suits audits, experiments and backfills; a tag marks releases or month-end states. Either one protects its snapshot from expiry. RETAIN sets a maximum reference age, measured from the snapshot’s age, after which expiry may drop the reference; main is never dropped. Branches can also keep a number of snapshots. Write to a branch with table.branch_<name>, or set spark.wap.branch, which works only when the table has write.wap.enabled=true and otherwise silently writes to main.

References share data files with main, so creating one is cheap, but a long-lived one keeps old files alive and costs storage. The schema belongs to the whole table. To publish a branch, use fast_forward if main has not moved, or cherry-pick; there is no three-way merge.

A branch is a second line of history.

ALTER TABLE demo.shop.orders CREATE BRANCH etl_test RETAIN 7 DAYS;
ALTER TABLE demo.shop.orders CREATE TAG month_end RETAIN 365 DAYS;
43. What is write-audit-publish?

Write-audit-publish means writing data where consumers cannot see it, validating it, and then publishing it with one metadata operation.

With branches, a job commits to a named branch, checks run against it, and fast_forward moves main, which succeeds only if main has not diverged. The other method sets write.wap.enabled and a session spark.wap.id, which stages an unreferenced snapshot that publish_changes later applies as a new one; it fails if the ID was used for several snapshots. Good audits check counts against the source, nulls and ranges, duplicate keys and business totals.

Consumers therefore never see a batch that failed its checks. If main moves during an audit, recreate the branch from the new head or cherry-pick the audited commit. Give audit branches a retention period so failed runs do not hold files forever, and remember that a branch is not access control.

ALTER TABLE demo.shop.orders CREATE BRANCH audit;

INSERT INTO demo.shop.orders.branch_audit (order_id, customer_id, amount, status, order_ts)
VALUES (5001, 1, 10.00, 'NEW', TIMESTAMP '2026-11-03 09:00:00');

SELECT count(*) FROM demo.shop.orders.branch_audit WHERE amount < 0;

CALL demo.system.fast_forward('shop.orders', 'main', 'audit');
44. How do you read only the data added between two snapshots?

To read only new data, use an incremental read with start-snapshot-id, which is exclusive, and end-snapshot-id, which is inclusive. It returns the rows added by append commits in that range.

Iceberg walks the snapshots between the two IDs and reads the files those appends added, without comparing table states, so it is cheap. Both snapshots must still exist on the same line of history. Updates, deletes and overwrites in the range are not represented, so tables changed in place need the changelog view instead.

A pipeline stores the last processed snapshot ID with its output, reads from there to the current snapshot and saves both together or in a way that is safe to repeat. If expiry removes the stored ID, the job cannot resume and needs a full reload, so keep snapshots longer than the longest outage you expect.

ids = [r.snapshot_id for r in spark.sql(
    "SELECT snapshot_id FROM demo.shop.orders.snapshots "
    "WHERE operation = 'append' ORDER BY committed_at").collect()]
start_id, end_id = ids[-2], ids[-1]

(spark.read.format("iceberg")
    .option("start-snapshot-id", start_id)
    .option("end-snapshot-id", end_id)
    .load("demo.shop.orders"))
45. How do you capture row-level changes from an Iceberg table?

Row-level changes come from a changelog view over a snapshot range. It reports inserted and deleted rows with the columns _change_type, _change_ordinal and _commit_snapshot_id.

Iceberg records files and deleted positions, not logical updates, so an update looks like a delete plus an insert. Passing identifier_columns pairs them, compute_updates produces before and after images, and net_changes collapses intermediate changes to their net effect; the last two cannot be combined. The options argument sets the snapshot or timestamp range. Removing rows that were merely carried over by a copy-on-write rewrite costs extra work on large rewrites.

This gives downstream jobs the changes to a table that is updated in place. It is limited to retained snapshots, some delete types are not supported, and it shows differences between commits rather than every source event, so it does not replace change capture at the database.

CALL demo.system.create_changelog_view(table => 'shop.orders', changelog_view => 'orders_changes');

SELECT _change_type, count(*) FROM orders_changes GROUP BY _change_type;
46. Why does a MERGE fail with MERGE_CARDINALITY_VIOLATION?

MERGE_CARDINALITY_VIOLATION means more than one source row matched the same target row, so the result would be ambiguous.

The fix is to deduplicate the source, keeping one row per key ordered by a sequence that comes from the source system. Arrival time is a poor choice, because retries and out-of-order delivery would let an older version win. Two source rows with a key that does not yet exist raise no error and are both inserted.

Two related traps pass silently. If the match condition is not unique in the target, every matching target row is updated, and without a guard such as `s.seq

t.seq` a replayed batch can overwrite newer data. Identifier fields declare which columns identify a row, but writes are not checked against them, so the pipeline must enforce and monitor uniqueness itself.

target: key=1            source: key=1 'b', key=1 'c'   -> error
target: no key=2         source: key=2 'b', key=2 'c'   -> both inserted

SELECT order_id, status FROM (
  SELECT *, row_number() OVER (PARTITION BY order_id ORDER BY order_ts DESC) AS rn
  FROM demo.shop.orders
) latest WHERE rn = 1 LIMIT 5;
47. What are position deletes and equality deletes?

A position delete names a data file and a row position. An equality delete names column values, such as an ID, without knowing where the row is.

To write a position delete, the writer must read the target to find the row, and readers then simply skip known positions in one file. An equality delete needs no lookup, which is why streaming upsert writers such as Flink use it: they write “delete key 42” and the new row, leaving the matching to readers. Those deletes apply to older files in the partition, or to all files if global. In format version 3, new position deletes are written as deletion vectors.

The cost lands on queries, which must load equality delete values and check them against every applicable file, often as an in-memory join. Compact data files so that deletes are applied and removed, frequently for equality deletes. The query below counts files by content: 0 data, 1 position deletes, 2 equality deletes.

SELECT content, count(*) FROM demo.shop.orders.files GROUP BY content;
48. What is the difference between static and dynamic partition overwrite?

The two modes decide what INSERT OVERWRITE replaces. In static mode, Spark’s default, it replaces the whole table unless a partition is given; in dynamic mode it replaces only the partitions that receive rows.

Iceberg recommends dynamic mode, or MERGE INTO. The DataFrame v2 writer makes the choice explicit: writeTo(t).overwritePartitions() is dynamic, while writeTo(t).overwrite(condition) replaces rows matching a filter. With hidden partitioning, which partitions count as touched depends on the current spec, so after evolution a job that replaced a day might replace a bucket of a day or a whole month.

The difference is dangerous with an empty source, where static mode can empty the table. For a safe backfill, overwrite with an explicit condition, run it on a branch, validate the result and publish it.

SET spark.sql.sources.partitionOverwriteMode=dynamic;

INSERT OVERWRITE demo.shop.orders (order_id, customer_id, amount, status, order_ts)
VALUES (6001, 2, 20.00, 'NEW', TIMESTAMP '2026-11-04 10:00:00');

SET spark.sql.sources.partitionOverwriteMode=static;
49. How do you choose a catalog?

Choose a catalog from the engines that must connect, how access is controlled, the commit rate and what you already operate.

A REST catalog suits many engines and central security, at the price of running or buying the server. Hive Metastore suits existing Hadoop platforms and commits by checking and swapping the table entry; AWS Glue suits AWS platforms through conditional updates. JDBC uses a database row and works for small deployments, though every client needs database access. Nessie adds branching across tables, and the Hadoop catalog belongs only in local tests.

Before deciding, confirm that every engine supports it, find out who authorises access and issues storage credentials, check the sustained commit rate and plan for outages and restores. Tables can move by registering their metadata elsewhere, but permissions, views and automation move with more effort, so the choice tends to stick. See Iceberg catalogs.

50. Why is the Hadoop catalog unsafe on object storage?

The Hadoop catalog commits by renaming a file to the next version number, and it depends on that rename being atomic and failing if the target already exists.

Many object stores give no such guarantee, because a rename is often a copy followed by a delete. Two writers can then both appear to succeed while one commit is lost. Nothing fails at write time; later you find missing rows, snapshots gone from history or a stale version-hint.text. The specification marks this file-system table scheme as deprecated and calls it unsafe in object stores and local file systems.

It is acceptable for local development, tests and single-writer experiments such as the examples here. Anywhere else, use a catalog with a real compare-and-swap and register the existing metadata file in it. A lock manager helps only if every client cooperates.

writer A: write tmp-a.json -> rename to v8.metadata.json
writer B: write tmp-b.json -> rename to v8.metadata.json
HDFS:          second rename fails, B retries
some stores:   second rename may overwrite, A's commit is lost
51. What are Iceberg views?

An Iceberg view is a view definition stored under its own specification, so that engines can share it.

It keeps the SQL text with its dialect, the output columns and types, a history of versions with one marked current, and the default catalog and namespace used to resolve names. A view created by one engine is visible to others through the catalog, and replacing it is an atomic, versioned change. It stores no data and materialises nothing.

Sharing is not translation, though. An engine needs a representation in a dialect it understands, so SQL with engine-specific functions or casts may not run elsewhere. Prefer standard SQL and test each view in every engine that uses it. Support depends on the catalog; the Hadoop catalog has none, which is why there is no runnable example here. See Iceberg views.

52. How do you migrate a Hive table to Iceberg?

A Hive table can be migrated with the snapshot, migrate or add_files procedures, or by rewriting its data into a new Iceberg table.

snapshot creates an Iceberg table over the source files and leaves the source unchanged, which makes it ideal for rehearsal, although that table does not own the files, has expiry disabled and can break if the source changes. migrate replaces the table in place, renaming the original to a backup by default; it needs Parquet, ORC or Avro and refuses bucketed tables. add_files imports files into an existing table without checking their schema, and expiry may later delete them; it refuses already referenced files by default, but with check_duplicate_files => false adding one twice duplicates its rows. In-place methods read footers, record statistics and add a name mapping without copying data.

Rewrite when partitioning or file sizes are poor, and migrate in place when the layout is already good. To roll back, stop writers, drop the new table without purging and restore the backup, which lacks later writes. See Hive to Iceberg migration.

Rehearse with snapshot, cut over with migrate.

53. What does register_table do?

register_table adds an existing Iceberg table to a catalog by pointing at one of its metadata files. No data is copied.

It is used to move a table between catalogs, to recreate an entry after a drop that kept the files, and to bring up a replicated copy during disaster recovery. For a move, stop writers, note the final metadata location, register it, repoint clients, verify and then remove the old entry without purging. If storage has moved, prepare the absolute paths with rewrite_table_path and copy the files first.

Two mistakes lose data. Registering an older metadata file silently drops every later commit, and later maintenance may delete files the newer history needs. Leaving the table writable in two catalogs makes their pointers diverge, and cleanup in one can remove files the other still references.

CALL <catalog>.system.register_table(
  table => 'db.orders',
  metadata_file => 's3://bucket/warehouse/db/orders/metadata/00042-<uuid>.metadata.json');
54. How does Spark Structured Streaming write to Iceberg?

Spark Structured Streaming commits each micro-batch to an Iceberg table as one snapshot, in append or complete output mode.

For exactly-once delivery, the sink records the query ID and epoch ID in the snapshot summary. Before committing, it walks back through the current history for this query’s last epoch and skips a batch already present. Appends are fast appends unless use-merge-append-for-streaming is set, and fanout-enabled keeps a writer open per partition to avoid sorting.

The trigger interval decides commit frequency; Iceberg recommends at least a minute, and longer triggers give fewer, larger files. Compaction and expiry are still needed. The guarantee covers this sink and its checkpoint only: a new checkpoint means a new query ID, foreachBatch writes must be made idempotent yourself, and aggressive expiry can remove the snapshots the check relies on. Remove the checkpoint before resetting the table and rerunning the example.

One micro-batch, one commit.

events = (spark.readStream.format("rate").option("rowsPerSecond", 5).load()
    .selectExpr("value AS order_id", "value AS customer_id",
                "CAST(1 AS DECIMAL(12,2)) AS amount", "'NEW' AS status",
                "timestamp AS order_ts"))

query = (events.writeStream.format("iceberg")
    .outputMode("append")
    .trigger(processingTime="1 minute")
    .option("checkpointLocation", "/tmp/ckpt/orders")
    .toTable("demo.shop.orders"))

# after a few triggers:
query.stop()
55. Can you stream from an Iceberg table?

Yes. Spark can read an Iceberg table as a stream, picking up newly appended files incrementally and keeping its position in the checkpoint.

Each micro-batch plans the files added since the recorded snapshot and file. stream-from-timestamp chooses where to start, and streaming-max-files-per-micro-batch or streaming-max-rows-per-micro-batch limit batch size, which stops catch-up after downtime from becoming one enormous batch.

The source is designed for appends. An overwrite or delete snapshot stops the query unless you set streaming-skip-overwrite-snapshots or streaming-skip-delete-snapshots, and skipping means the change never reaches downstream. Compaction commits add no new rows and are not replayed. For tables with updates, run the changelog view in a batch loop or stream from an append-only raw table, and keep snapshot expiry behind the slowest consumer.

56. How do you upgrade the format version?

You upgrade a table by setting its format-version property. The change touches metadata only.

Going from version 1 to 2 introduces sequence numbers and allows row-level deletes. Going from 2 to 3 makes new deletes use deletion vectors and starts row lineage for new snapshots. Existing files are not rewritten, and old position delete files remain valid until that file’s deletes are written again.

There is no downgrade, only copying into a new table at the lower version, which loses history. So list every reader, writer and maintenance job first, confirm each supports both the version and the features you will start using, rehearse on a test table with the same properties, upgrade readers before writers and have a recovery plan.

DROP TABLE IF EXISTS demo.shop.upgrade_demo PURGE;
CREATE TABLE demo.shop.upgrade_demo (id BIGINT) USING iceberg;
ALTER TABLE demo.shop.upgrade_demo SET TBLPROPERTIES ('format-version' = '3');
57. What does write.object-storage.enabled do?

write.object-storage.enabled adds a hash-based prefix to data file paths so that requests spread across many object-store key prefixes. It is off by default.

Object stores scale request rates by key range, so a table whose newest files all share one date prefix concentrates traffic and can be throttled. The hash comes from the file name, combined with the partition path on partitioned tables when write.object-storage.partitioned-paths includes it. Iceberg reads are unaffected, because paths come from metadata.

The trade-off is that directories become hard to browse and anything assuming a partition layout, such as lifecycle rules or scripts, stops working. Existing files keep their paths until rewritten. Small tables, low concurrency and file systems such as HDFS do not need it.

Advanced

61. Walk through the commit protocol.

In the commit protocol, a writer builds new files and metadata from the current table version, then asks the catalog to switch the pointer only if that version is still current.

It reads the current metadata as its base, writes data and delete files, then manifests, a manifest list and a new metadata file, and requests the swap. If another writer got there first, it reloads, checks that its change is still valid and retries. An append requires nothing. A compaction requires its replaced files to be present with no new position deletes, a file delete requires its files, row-level changes require no conflicting data or deletes at their isolation level, and schema or spec changes require the old definition to be unchanged.

No locks are held during the work, which favours workloads with rare conflicts. Retries reuse data files and often manifests, and the whole design rests on the catalog’s compare-and-swap.

A commit is new files plus one conditional pointer swap.

62. Compare CommitFailedException, ValidationException and CommitStateUnknownException.

The three exceptions mean that a commit lost a race, that it is no longer valid against newer changes, or that nobody knows whether it happened.

CommitFailedException comes from the catalog rejecting the swap; it is safe to retry, and Iceberg retries automatically first. ValidationException comes from checking the new base during a retry, for example “Found conflicting files that can contain records matching” the operation’s filter, so the whole operation must be recomputed or the overlap removed. CommitStateUnknownException arises when the request was sent and no definite answer returned, such as after a network timeout.

The third is the dangerous one. If the commit succeeded, its files are live, so deleting them would corrupt the table and rerunning could apply the change twice. Check the table before acting. Jobs become safe to repeat by merging on a business key, overwriting a deterministic partition or recording a batch ID in the snapshot summary.

CommitFailedException         let retries run; if exhausted, reduce contention
ValidationException           recompute from the new table state
CommitStateUnknownException   query snapshots; decide; then rerun if absent
63. What isolation levels do row-level operations offer?

Row-level operations offer serializable, the default, and snapshot isolation, set per command with write.delete.isolation-level, write.update.isolation-level and write.merge.isolation-level.

Under both, a commit fails if another removed or rewrote a file it depends on, or added deletes for rows being updated, and changes outside the operation’s filter are allowed. They differ on new data: serializable rejects a concurrent append that matches the filter, while snapshot isolation permits it. So an UPDATE ... WHERE status = 'NEW' can commit under snapshot isolation while newly appended NEW rows stay unchanged, a result no serial order would produce. Readers always see one committed snapshot either way.

Keep serializable unless the pipeline can tolerate rows appearing concurrently, such as heavy ingestion beside corrections to older data. A filter on the partition column avoids most false conflicts.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'write.delete.isolation-level' = 'serializable',
  'write.merge.isolation-level'  = 'serializable');
64. How are commit retries configured?

Four table properties control how a writer retries a lost commit: commit.retry.num-retries (default 4), commit.retry.min-wait-ms (100), commit.retry.max-wait-ms (60,000) and commit.retry.total-timeout-ms (1,800,000).

After a rejected swap, the writer waits with exponential back-off between the minimum and maximum, refreshes the table, revalidates and tries again until attempts or time run out. This resolves contention among compatible operations, mainly appends. It cannot resolve validation failures, which are logical conflicts, or a commit rate higher than the catalog and metadata size allow.

Tune by first reducing commit frequency and competing writers, then keeping metadata small so each attempt is short, and only then raising retries, as the example does. Very high counts hide a design problem and lengthen job tails. Rising attempts per commit in reports and driver logs are an early warning.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'commit.retry.num-retries' = '10');
65. What are sequence numbers for?

Sequence numbers give commits a reliable order. Each successful commit receives an increasing number, and files carry the number of the commit that added them, which tells Iceberg which delete files apply to which data files.

Each file has a data sequence number, stating how old its data is logically and used to match deletes, and a file sequence number, recording when it was added. They differ after compaction, which writes new files that keep the older data number; otherwise an equality delete committed during the rewrite would stop applying and deleted rows would return. The manifest list also records each manifest’s min_sequence_number, which helps planning discard deletes that can no longer apply.

Clocks on different writers could not provide this order. New manifest entries store null and inherit the number at commit, so a retried commit gets a new one without rewriting manifests, and files in tables upgraded from version 1 count as 0.

seq 1   data file A
seq 2   equality delete "id = 7"   applies to A (1 < 2)
        data file B added in seq 2  not affected (2 is not < 2)
seq 3   data file C with id = 7     not affected
66. When does a delete file apply to a data file?

A delete file applies to a data file when the data is old enough and in scope.

A deletion vector or position delete applies when the data file’s sequence number is at most the delete’s, the partition spec and values match and the file is referenced; position deletes are ignored for a file that has a deletion vector, since the vector must already include them. An equality delete requires a strictly older data file in the same partition, unless it was written unpartitioned, in which case it applies everywhere, which is powerful and expensive.

The two rules differ for a reason. “At most” lets one commit add a file and delete positions in it, as streaming writers must, while “strictly less” lets one commit delete a key and insert its new version safely. After partition evolution, an old partition-scoped delete does not reach new files. A file with many applicable deletes costs more to scan.

67. What are deletion vectors, and why replace position delete files?

A deletion vector is a bitmap of deleted row positions for one data file, stored as a blob in a Puffin file. It was introduced in format version 3 to replace position delete files.

Positions are kept in Roaring bitmaps, compact for both sparse and dense deletions, and one Puffin file can hold vectors for many data files. The manifest records the file, offset and length, and there is at most one vector per data file in a snapshot. A new delete merges with the existing vector and replaces it, so concurrent deletes to the same file conflict. Old position delete files stay valid after an upgrade until that file’s deletes are next written.

Readers benefit by loading one bitmap and testing positions instead of finding and merging many delete files. Deleted rows are still stored and read before being skipped, so rewrite heavily deleted files. The example uses the version 3 table from question 56.

68. What is row lineage?

Row lineage, added in format version 3, gives every row a stable ID and records which commit last changed it, exposed as _row_id and _last_updated_sequence_number.

IDs are inherited: a data file receives a first row ID, and each row’s ID is that value plus its position, while the table tracks the next unused number. New rows need nothing written, which keeps commit retries cheap. When compaction or copy-on-write moves a row, its ID is copied; a modified row leaves the last-updated value empty so it takes the new commit’s number.

This lets incremental processing distinguish a changed row from a new one and supports auditing. Rows changed through equality deletes lose their identity, because the writer never read the old row, and snapshots from before an upgrade have no IDs. A row ID also says nothing about business uniqueness.

69. What else does format version 3 add, and what is the status of version 4?

Format version 3 adds, besides deletion vectors and row lineage, new types, default values, multi-argument transforms and table encryption keys. Version 4 is still being designed.

The new types are variant for semi-structured data, geometry and geography for spatial data, nanosecond timestamps and unknown for a column whose type is not yet decided. An initial-default fills a new column for older rows, and a write-default applies to later writes that omit it. Version 4 is not formally adopted, its documented change so far is relative paths in metadata, and it should not be used in production.

A feature in the specification is usable only when every engine on the table implements it for reading and writing; variant, for instance, needs an engine with that type. Verify each engine, trial on a new table and then upgrade.

70. How does a REST catalog change commits and security?

With a REST catalog, the client sends requirements and updates, and the server applies the updates only if every requirement still holds.

Requirements include assert-table-uuid against a replaced table, assert-ref-snapshot-id against a moved branch, schema and partition spec checks against concurrent changes and assert-create for new tables. The server writes the metadata file and swaps the pointer. It can authorise each operation and issue short-lived storage credentials or sign requests, so engines need no long-lived keys. The specification also defines multi-table commits and server-side planning, which servers may or may not implement.

Compared with clients swapping a pointer, conflict checks are finer, commit logic lives in one place for every language and policy can be enforced centrally. The cost is that the service’s availability, latency, backups and authentication become critical. Apache Polaris is one implementation.

71. What is the difference between a fast append and a merge append?

A fast append writes a new manifest for the new files and reuses the others. A merge append may also combine small manifests during the commit.

Fast append does minimal work and keeps the conflict window short, but manifests accumulate and planning degrades without maintenance. Merge append reads and rewrites some manifests, which keeps their number in check at the cost of a longer commit. Merging begins at commit.manifest.min-count-to-merge (100), targets commit.manifest.target-size-bytes (8 MB) and can be disabled with commit.manifest-merge.enabled. Spark batch appends merge, while Structured Streaming uses fast appends unless use-merge-append-for-streaming is set.

So a streaming table can collect thousands of manifests. Count them with the query below, then rewrite them on a schedule or accept slightly slower commits by merging.

72. How are files turned into Spark tasks?

Spark tasks are built by splitting large Iceberg files and packing small ones together.

Large files are divided at row group boundaries, and pieces are combined until a task reaches read.split.target-size, 128 MB by default. Every file counts at least read.split.open-file-cost, 4 MB, so a task does not receive thousands of tiny files, and read.split.planning-lookback, 10, sets how many bins stay open while packing. Spark may adjust split size to the scan and available parallelism, and the split-size read option overrides it for one query.

Task counts therefore reflect file layout. Many very short tasks suggest a small split size or tiny files, while a few long tasks on a large cluster suggest the opposite or unsplittable input. Tasks must also apply deletes, which byte sizes do not show.

73. What is a storage-partitioned join?

A storage-partitioned join lets Spark join two tables partition by partition, with no shuffle, when both are partitioned compatibly on the join keys.

It needs spark.sql.sources.v2.bucketing.enabled and the Iceberg setting spark.sql.iceberg.planning.preserve-data-grouping, matching transforms on the join columns, and a join condition that covers them. Further Spark settings handle partition values present on only one side and ease skew by partially clustering one side. Parallelism is limited by the number of partitions, so a skewed partition becomes a skewed task.

It pays off when both tables are large and joined repeatedly on the same key; if one side is small, a broadcast join is simpler. Confirm that it happened by looking for the absence of Exchange under both sides in the physical plan. The two settings are shown below.

74. How do you run compaction alongside active writers?

Run compaction alongside writers by limiting it to data that is not changing and letting it commit in pieces, so that a conflict loses little.

Appends never conflict with compaction. A copy-on-write update of a file being compacted, or new position deletes against it, does conflict, while new equality deletes still apply afterwards thanks to the preserved sequence number. Filter with where to partitions no longer receiving changes, enable partial-progress.enabled so that groups commit separately, keep file groups small and schedule around heavy merge jobs.

Partial progress means more snapshots and a result that may be only partly applied, with failed groups logged. A finished job does not prove the table was compacted, so compare files before and after and read the output. When one side has to lose, let it be compaction, which can be repeated without hurting freshness.

75. Why can delete files survive a compaction?

Delete files can survive a data compaction because it replaces data files and may leave delete files pointing at files that are no longer live. These dangling deletes change no result but still cost planning and storage.

rewrite_data_files applies deletes into new files when delete-file-threshold or delete-ratio-threshold selects them, and with remove-dangling-deletes it also drops the ones that no longer apply. rewrite_position_delete_files compacts position delete files and removes dangling positions. By default a file is not rewritten for deletes until they reach 30% of its rows, and the position delete procedure may select nothing.

So check counts after running them. Removal based on sequence numbers misses some cases, such as global equality deletes that match nothing, behaviour has changed between releases, and storage stays used until old snapshots expire. See copy-on-write or merge-on-read.

76. What are Puffin files and table statistics?

Puffin is a file format for blobs that do not fit in manifests, a container whose footer describes each blob’s type, fields, snapshot and offset. Iceberg uses it for deletion vectors and for table statistics.

The statistics are distinct-value estimates per column, stored as Apache DataSketches theta sketches and computed by compute_table_stats, which covers all top-level primitive columns unless the columns argument narrows it. Partition statistics are a separate file with per-partition counts, produced by compute_partition_stats.

Cost-based optimisers need distinct counts to estimate join sizes and choose join order and build side, which column bounds cannot provide. The sketches belong to one snapshot and do not refresh themselves, so recompute them after large changes. They help only if the engine reads them, so compare plans before and after.

77. Why might one session not see another session's commit?

A session may not see another session’s commit because its catalog is serving a cached copy of the table.

Caching is on by default (spark.sql.catalog.<name>.cache-enabled) with an expiry of 30,000 milliseconds. The timer restarts on every access, so a session that queries more often than every 30 seconds can keep reading an earlier snapshot indefinitely. The cache avoids repeated catalog calls and metadata reads and keeps references within a query consistent.

To see the new data, run REFRESH TABLE, disable the cache or shorten the expiry, accepting more catalog traffic; a value of -1 turns expiry off entirely. The same symptom can come from a branch or time-travel setting in the session, two catalogs pointing at different metadata or a commit that failed, so compare the session’s snapshot ID with the writer’s.

REFRESH TABLE demo.shop.orders;
78. Does Iceberg support multi-table transactions?

Not through the table format itself, which commits one table at a time.

Some support exists around it. The REST specification has a multi-table commit endpoint, though server and engine support vary, and a catalog such as Nessie can publish many tables by merging a branch, provided everyone uses that catalog. Without these, you can write every table to a branch, validate and fast-forward them one after another, tag all tables with the same batch name after loading, or make jobs idempotent so a rerun repairs a partial failure.

This matters when readers must see related tables agree. They then need to read a published set, by tag or recorded snapshot ID, instead of each table’s latest state. If a two-table job fails halfway, finish it by rerunning, or roll back the first table if nobody has committed to it since.

79. How do you honour a right-to-erasure request?

To honour a right-to-erasure request, delete the rows, rewrite the files that held them, remove the references and snapshots that keep old versions, and clean up storage.

A DELETE only changes the current snapshot, and with merge-on-read the original data file still contains the row until compaction. Forgotten tags and branches keep everything they reference, old metadata can hold identifiers in column statistics and partition values until it expires, and raw tables, derived tables, exports, object versions and backups need the same treatment. Verify the removal across all snapshots, not just the current one.

It is far easier when designed in: keep personal data in few tables, cluster by the subject key so deletes rewrite little, set retention shorter than the legal deadline and record evidence. Per-subject encryption keys that can be destroyed are an alternative.

DELETE          current snapshot no longer shows the rows
compaction      data files rewritten without them (needed for merge-on-read)
drop refs       branches and tags stop protecting old snapshots
expire          old snapshots removed, their files deleted
orphan cleanup  leftovers from failed jobs removed
storage         object versions, backups and replicas handled
80. What do you check before several engines write to one table?

Before several engines write to one table, confirm that they share a catalog, support the same format features and agree on who maintains it.

Two catalogs would lose commits. One engine lagging on format version or delete types can break reads or return wrong rows. Time zone and timestamp handling differ, some writers ignore partition or sort hints, and each has its own retry defaults. Table properties are shared but not always honoured, so verify behaviour rather than settings. Assign one owner for maintenance and keep retention longer than the slowest consumer needs.

Prefer one writer per table or partition range, since a streaming upsert and a batch merge on the same partitions will keep failing validation. Test each engine’s writes, updates, deletes and reads, run the engines concurrently, compare results on a pinned snapshot and repeat on upgrades. Block old writers in the catalog before enabling new features.

83. Twenty jobs append to one table and some fail with CommitFailedException. How do you fix it?

Twenty appending jobs fail with CommitFailedException because they lose the pointer swap more times than their retry budget allows. Appends never conflict logically, so this is pure contention.

Confirm the exception is not ValidationException, then measure commits per minute and commit duration. The chance of collision rises with both, since the window between reading the base and swapping the pointer is where others get in, and a bloated metadata file widens it. Make fewer commits through longer triggers or fewer writers, then shorten each commit by expiring snapshots, rewriting manifests and checking catalog capacity, and only then raise the retry settings, which lengthens job tails.

If the design allows, have producers write to a queue that a single job commits, or give independent sources their own tables, combined later by a view or merge.

84. Two MERGE jobs fail intermittently with ValidationException. What is happening?

Two merge jobs fail with ValidationException when each finds that the other changed files or added rows covered by its own condition. Retrying the commit cannot fix a logical conflict.

The message names the conflicting files. Typically both jobs match on the key only, so each conflict filter covers the whole table even though their data does not overlap. Adding a literal partition predicate to the ON clause, such as t.region = 'EU', lets Iceberg see that they are disjoint. Otherwise give each job its own partitions, run overlapping jobs one after another or combine them, and keep them short.

Snapshot isolation helps only where ignoring concurrent appends is safe, and never lets two writers rewrite the same files. A rerun must execute the whole merge against the new state, and merge-on-read does not remove conflicts on the same rows.

Each run gets its own branch. The audit checks counts, nulls, duplicates and totals against the source, with a few meaningful thresholds agreed with consumers. 89. Plan the migration of a very large Hive table to Iceberg with little downtime.

Plan the migration of a large Hive table by taking an inventory, rehearsing on a copy, choosing in-place migration or rewrite, cutting over with a rollback plan and starting maintenance at once.

Record formats, partitioning, file sizes, writers, readers, engine support and permissions. Rehearse with snapshot and compare counts, aggregates and query plans. In-place migrate needs only a short metadata step but keeps the old layout; a rewrite costs a full copy, so choose it when files are small or partitioning is poor. For little downtime, backfill history partition by partition while the old table serves, apply recent changes, validate and switch.

At cutover, pause writers, migrate, validate, repoint jobs and views, and keep the backup table until confidence is established. While a snapshot table exists, deleting source files breaks it, and old Hive-style writers and partition filters need review. Prove correctness with per-partition checksums and important queries.

90. A streaming job creates thousands of small files a day. What do you change?

A streaming job’s file count is roughly files per commit times commits per day, so reduce both and compact what remains.

For example, 200 write tasks on one partition with 1,440 commits a day produce 288,000 files. Lengthen the trigger to the longest acceptable latency, use hash distribution with fewer shuffle partitions or adaptive coalescing, partition more coarsely and keep late data from spreading across many partitions. The fanout writer avoids a sort at a memory cost but does not itself reduce file counts.

Compact partitions older than the active window with partial progress and expire snapshots so storage follows. The query below shows files added per hour, which confirms the effect. If the trigger cannot change, compact continuously or keep a hot append table apart from the optimised table that consumers query.

200 write tasks x 1 partition x 1,440 commits per day = 288,000 files per day

SELECT date_trunc('hour', committed_at) AS hour, count(*) AS commits,
       sum(CAST(summary['added-data-files'] AS INT)) AS files_added
FROM demo.shop.orders.snapshots
GROUP BY 1 ORDER BY 1 DESC;
91. A busy table gets 503 Slow Down errors from object storage. What do you do?

For 503 Slow Down errors, reduce the number of requests first, mainly by compacting, then spread new files across key prefixes and back off on retries.

Find which operations and prefixes are throttled and what changed, such as a new job, many small files or a large expiry deleting everything at once. Compaction and better pruning cut requests, write.object-storage.enabled spreads new files, lower maintenance concurrency softens delete bursts and the file IO’s retry and back-off settings absorb transient throttling. Existing files keep their paths, so layout changes help gradually.

More parallelism or immediate retries make throttling worse. One enormous file per partition would reduce requests but hurt selective reads and rewrites, so aim for target-sized files.

92. Queries fail with a missing data file after a cleanup job. How can that happen, and how do you respond?

A cleanup job can delete files that are still referenced when retention is too short, table locations are shared, paths do not match or something outside Iceberg removes objects.

Typical causes are orphan removal catching files of a write still in progress, one table’s cleanup treating another’s files as orphans, URI scheme mismatches with prefix_mismatch_mode => 'DELETE', a table registered in two catalogs, storage lifecycle rules and manual deletion. Stop cleanup and writers, compare all_data_files with storage to list what is missing, and restore from object versions or backups, the only way to get the exact files back. Otherwise remove the broken references and reload that data from a source, checking every affected snapshot.

Prevent it with one location per table, generous retention, reviewed dry runs, bucket versioning, no lifecycle rules on table paths and a job that verifies referenced files exist.

93. Spark and Trino report different counts for the same table. How do you investigate?

When Spark and Trino count differently, first make sure both read the same catalog and snapshot, then compare how they handle deletes, types and caching.

Check the metadata location and pin both queries to one snapshot ID, watching for caches, branch settings and time travel. If pinned counts then agree, the difference was freshness. If they differ without filters, suspect engine support, often for delete files. If they differ only with filters, look at time zones, timestamp types, case sensitivity, null handling or a pruning defect.

Narrow it per partition and then per file until the differing rows appear, reproduce on a small table and check release notes; compacting can remove the problem feature meanwhile. Do not treat total-records in a snapshot summary as truth, because it ignores merge-on-read deletes.

SELECT snapshot_id, committed_at, summary['total-records'] AS total_records
FROM demo.shop.orders.snapshots
ORDER BY committed_at DESC LIMIT 3;
94. One customer produces half of all events. How do you partition?

When one customer produces half the events, partition by time plus a bucket on an evenly spread key, and sort by customer within files.

Time partitions serve retention and most queries. Bucketing on a high-cardinality key such as the event ID spreads writes, including the large tenant’s, and sorting by customer lets filters on other customers skip files. Bucketing by customer would be a mistake, since all of one customer’s rows hash to one bucket and recreate the skew. Size the bucket count by dividing daily bytes by the target file size.

Queries for the large tenant will read many files regardless, while small tenants skip almost everything. Watch write task sizes, as a range shuffle can still skew and adaptive execution may need to split partitions. A separate table behind a view suits a tenant with a completely different volume and access pattern.

partition:  days(event_ts), bucket(N, event_id)
sort:       customer_id, event_ts
95. You must change partitioning on a live table. How?

Change partitioning on a live table with partition evolution, which affects new writes only and lets old data be rewritten later if needed.

Review writers, especially dynamic overwrites, and readers, rehearse on a copy, then apply the change in one statement, such as REPLACE PARTITION FIELD months(ts) WITH days(ts). Verify with the query below that new files carry the new spec ID. There is no downtime, queries plan across both specs and old data keeps its layout.

Overwrite jobs may now replace more or less than before. To reverse, evolve back; files written meanwhile stay readable.

96. An auditor needs a report exactly as it ran six months ago. Is that possible?

An auditor’s six-month-old report can be reproduced only if the snapshot still exists, and normal retention will not keep it that long, so it has to be designed in advance.

At each reporting close, tag the snapshot with a long retention or none, record the snapshot ID of every table the report read, keep the query and application version, and note engine settings such as the time zone. Reading by tag also uses that snapshot’s schema. If any one input has expired, reproduction fails.

Every tag keeps its files alive, so for many years of history an archive table holding the reported data may be cheaper and clearer. Time travel is neither a backup nor tamper proof, since someone with rights can drop a tag; control those permissions and consider immutable storage if the audit requires it.

97. Compaction keeps failing because streaming upserts run continuously. What are the options?

When continuous upserts keep breaking compaction, keep compaction away from the files being updated and let it commit in small groups.

You can compact only settled partitions, accepting that recent data stays fragmented; use partial progress with small groups so a conflict loses little; run in quiet windows between batches; pause the stream briefly for guaranteed progress; or append raw changes and merge periodically, trading freshness for fewer conflicts. Running compaction between micro-batches in the same application removes the race at some latency cost.

If updates hit every partition there are no settled ones, so a layout that concentrates changes in recent data makes everything easier. Check which side fails, make sure a failing stream restarts from its checkpoint, and track delete counts and file sizes rather than job success.

98. A job ends with CommitStateUnknownException. What now?

After a CommitStateUnknownException, do not rerun the job yet and do not delete its files.

Query the snapshots for a matching application ID, operation, time and record counts, or look for the written keys; streaming writes also record query and epoch IDs. If the commit exists, the write succeeded and downstream steps can continue. If it does not and the catalog is healthy, rerun. If the catalog is still unhealthy, wait and check again. Files from a commit that never happened are collected later by orphan removal.

There is no automatic retry because it could write the data twice. Make the next occurrence easy by stamping a batch ID into the snapshot summary with a snapshot-property. write option, merging on a key so reruns are harmless and alerting on this exception separately.

100. Design the Iceberg settings for a raw, cleaned and reporting pipeline.

For a raw, cleaned and reporting pipeline, state volume, latency, update rate, consumers and retention first, then choose a write pattern, layout, row-level mode and maintenance plan for each layer.

Raw takes frequent appends, partitioned by ingest day, with settled days compacted and source fields kept so later layers can be rebuilt. Cleaned takes upserts by key, laid out by event time and key, using merge-on-read when updates are frequent, with deletes compacted often. Reporting is rebuilt in batches, sorted by common filters, copy-on-write, and tagged at each publish. Raw feeds cleaned incrementally because it is append only; reporting needs the changelog view or a partition rebuild.

All layers need one catalog, a maintenance owner, alerts on file size, deletes, failures and freshness, and a recovery path. To cut cost, start with retention and over-frequent commits.

Concepts and comparisons

101. What is a data lakehouse, and where does Iceberg fit?

A data lakehouse runs warehouse-style workloads, with transactions, schemas and fast SQL, directly on files in cheap open storage instead of copying data into a separate warehouse.

A warehouse manages its own storage and gives strong guarantees, mostly to one engine. A plain data lake keeps open files shared loosely by many engines with few guarantees. A lakehouse keeps the open files and lets a table format and catalog provide the guarantees. Iceberg is that table layer: it records which files make up a table and how to change that safely, but it is not the storage, the engine or the permission system.

The architecture still needs modeling, data quality, access control and maintenance, otherwise it only gives you transactional messy data. Nor must it replace the warehouse, which many platforms keep for low-latency serving.

+------------------------------------------------------------+
| Consumers      BI, notebooks, ML, applications             |
| Engines        Spark, Flink, Trino, warehouses             |
| Catalog        names, commits, permissions                 |
| Table format   Iceberg: snapshots, schema, partitioning    |
| Files          Parquet, ORC, Avro                          |
| Storage        object storage or HDFS                      |
+------------------------------------------------------------+
102. Could you build a lake without a table format? What would you have to solve yourself?

You can build a lake without a table format, but you then have to build the guarantees yourself: complete writes, safe concurrency, row deletes, schema changes and history.

Hiding partial writes takes staging directories, markers and renames. Two writers need external locks. Deleting one customer’s rows means custom partition rewrites, changing a column means coordinating every reader, reprocessing means keeping copies and planning means listing directories. Iceberg covers these with atomic commits, optimistic concurrency, DELETE, field IDs, time travel and manifests.

Plain files are enough for immutable, append-only data with one writer, one reader and partitions written once. The hardest part to build is safe concurrent commits, which on object storage need a compare-and-swap that files cannot provide, so weigh that work against running a catalog and maintenance.

103. How does Iceberg metadata differ from the Delta Lake transaction log?

Iceberg keeps a tree of immutable metadata for each snapshot, with a pointer to the current version in the catalog. Delta Lake keeps an ordered log of changes with periodic checkpoints.

In Delta, the highest committed log entry is current and a writer commits by creating the next log file, which must not already exist; readers load the checkpoint and later entries before skipping files. In Iceberg, the catalog compare-and-swap is the commit point and planning skips manifests and then files. Iceberg partitions through evolvable transforms and tracks columns by field ID, while Delta uses partition columns, generated columns or clustering, and names unless column mapping is on.

Both provide atomic commits and time travel, so the choice usually turns on engines, catalog and platform. Tools can generate one format’s metadata over the other’s files, best treated as read only.

Iceberg   catalog -> metadata.json -> manifest list -> manifests -> files
Delta     _delta_log/  000...000.json, 000...001.json, ..., checkpoint.parquet
          table state = latest checkpoint + the JSON entries after it
104. How do Iceberg's transactions differ from Hive's transactional tables?

Hive transactional tables depend on the metastore’s transaction manager and ORC delta files. Iceberg commits by atomically swapping metadata, which any engine that follows the specification can do.

Hive records state in metastore transaction tables and delta directories, uses locks, plans from metastore partitions and file listings and compacts delta files itself. Iceberg keeps state in metadata files and a catalog pointer, validates commits optimistically, plans from manifests, works with Parquet, ORC or Avro and is maintained by procedures run from the engine you choose.

Because Hive’s guarantees require every writer to use its transaction manager, support elsewhere is uneven. Iceberg can still use the Hive Metastore, but only to hold the table pointer. A transactional Hive table cannot simply be registered, because its delta files are not plain data files, so compact and rewrite it first.

105. One platform on object storage must serve BI and machine learning. Iceberg, Delta Lake or Hudi?

To choose between Iceberg, Delta Lake and Hudi for a platform serving BI and machine learning, decide from the workload: engines, update rate, existing governance and required freshness.

Engine support differs most, so list who must read and write. Many independent engines and a vendor-neutral catalog API favour Iceberg, a Spark and Databricks platform favours Delta Lake, and high-rate upserts with incremental pipelines favour Hudi. An existing catalog or governance setup often settles it, and freshness drives the write mode and compaction effort. For reproducible model training, all three offer time travel, and what matters is pinning and retaining the version, for example with an Iceberg tag.

Prove the choice with your two hardest workloads on the real engines, measuring performance and operational effort. Metadata translation can postpone the choice, at the price of another moving part.

106. What are the Iceberg equivalents of Delta Lake's OPTIMIZE and VACUUM?

Delta Lake’s OPTIMIZE corresponds to Iceberg’s rewrite_data_files, and VACUUM is split between expire_snapshots and remove_orphan_files.

Compaction is the rewrite procedure, ZORDER BY becomes a Z-order sort strategy within it, and where Delta writes log checkpoints, Iceberg has rewrite_manifests to reorganise metadata. Expiry deletes files that expired snapshots stop referencing; it never searches for files no snapshot knew about, which is orphan removal’s job.

Treating the two cleanup steps as one is the usual mistake. Defaults differ too: Delta retains seven days, while Iceberg keeps five days of snapshots and removes orphans older than three days, a limit that should exceed your longest write. To free space after a large delete, rewrite affected files if deletes are merge-on-read, then expire old snapshots.

CALL demo.system.expire_snapshots(table => 'shop.orders', retain_last => 3);
CALL demo.system.remove_orphan_files(table => 'shop.orders', dry_run => true);
107. When would you not use Iceberg?

Avoid Iceberg when you need row-level transactions, millisecond lookups, only very small simple datasets, or when nobody can run maintenance.

An application database belongs in PostgreSQL or similar, with indexes, constraints and row-level latency. High-rate point lookups suit a key-value store, because Iceberg has no row index. A small dataset with one reader needs nothing more than Parquet or a database, event streaming between services belongs in a log such as Kafka, and sub-second, highly concurrent dashboards need a serving store or warehouse. Without anyone to compact and expire, a managed warehouse is safer.

Iceberg costs a catalog, maintenance jobs, small-file care for streaming and engine testing, which large analytic history repays. Repeated partial-write incidents, painful schema or partition changes, slow planning from partition counts or a second engine needing the same tables are the signals to adopt it.

108. What is in a snapshot summary, and how do you use it?

A snapshot summary is a map of properties recorded with each commit: the operation, counts of files and records added or removed, totals and engine identifiers.

Added file and record counts reveal small files per commit; keys such as spark.app.id or flink.job-id identify the writing job; and streaming query and epoch IDs trace a micro-batch. You can add your own values through write options with the snapshot-property. prefix. Which keys exist depends on the operation and engine, and totals count records in data files without subtracting merge-on-read deletes.

Within those limits, summaries are the quickest record of what each job did to a table. A batch ID of your own pays off after an unknown commit outcome or a retry, because one query answers whether the batch landed. The query below reads several keys.

SELECT committed_at, operation,
       summary['added-data-files']  AS added_files,
       summary['added-records']     AS added_records,
       summary['total-data-files']  AS total_files,
       summary['spark.app.id']      AS app_id
FROM demo.shop.orders.snapshots
ORDER BY committed_at DESC
LIMIT 5;
109. You moved from daily to hourly partitions. Why do some queries still scan daily files?

Queries can still scan daily files after a move to hourly partitions because partition evolution does not rewrite history. Files written under the old spec still cover whole days.

The new spec applies to new writes, so the table holds both layouts and planning handles each separately; the query below shows which spec each partition uses. Old files that were clustered by time may still be skipped within a day through their column bounds.

If old data is rarely queried by hour, leave it. If a recent window needs hourly pruning, run rewrite_data_files with a where clause and options => map('rewrite-all', 'true'), since well-sized files do not otherwise qualify; check the rewritten count and expire snapshots so storage does not hold both layouts. Rewriting everything is rarely worth the compute, and sorting by timestamp can achieve hour-level skipping instead.

before the change   spec 0: days(ts)    one file may hold 24 hours
after the change    spec 1: hours(ts)   files hold one hour

query for one old hour  -> must open that day's files
query for one new hour  -> opens only that hour

FROM demo.shop.orders.partitions
ORDER BY spec_id, partition
LIMIT 10;
110. What are Iceberg's Spark procedures, and how do you call them?

Iceberg’s Spark procedures are table operations exposed in the catalog’s system namespace and run with CALL <catalog>.system.<procedure>(name => value), which requires the Iceberg SQL extensions.

For snapshots and branches there are rollback, set_current_snapshot, cherrypick_snapshot, fast_forward and publish_changes. Maintenance covers rewriting data files, manifests and position delete files, expiring snapshots and removing orphans. Migration uses migrate, snapshot, add_files, register_table and rewrite_table_path, and analysis includes changelog views, table and partition statistics and ancestors_of.

Prefer named arguments and literal values, since a call such as current_timestamp() is rejected, and read the result row, which reports what changed. A procedure that changes nothing matched no files. The same operations exist in the Java actions API, and other engines use their own syntax.

CALL <catalog>.system.<procedure>(name => value, ...);

Engines, APIs and access

111. How does Flink write to Iceberg?

Flink writers create files continuously, and the Iceberg sink commits them to the table when a Flink checkpoint completes.

Append mode adds data files, overwrite replaces partitions in batch jobs, and upsert mode, keyed on a primary key and requiring format version 2 or later, writes delete files alongside new rows. Upsert and overwrite cannot be combined, and in upsert mode partition source columns must belong to the equality fields. Rows can be hash distributed by partition or equality key, which struggles with skew, or range distributed through an experimental option.

Because the checkpoint interval is the commit interval, it sets both freshness and the rate of small files, and upserts produce equality deletes that need regular compaction. If checkpoints succeed but no snapshots appear, inspect committer failures and alert on the time since the last commit.

records -> writer tasks -> data (and delete) files
checkpoint completes -> committer -> one Iceberg snapshot

CREATE TABLE sample (
  id BIGINT, data STRING,
  PRIMARY KEY (id) NOT ENFORCED
) WITH ('format-version' = '2', 'write.upsert.enabled' = 'true');
112. What can table maintenance break in a running Flink job?

Table maintenance can break a running Flink job’s commit tracking and delete data it has not yet committed.

Expiring the job’s latest snapshot, identified by flink.job-id in the summary, loses the record of what it committed. Orphan removal with a short age limit can delete files waiting for a checkpoint to commit, and compaction on active partitions conflicts with upserts. So keep each job’s latest snapshot, set the orphan age well beyond the longest checkpoint outage you expect, retain snapshots longer than the longest planned downtime and compact only partitions no longer being updated.

The risk shows during recovery: a job stopped for a week may be unable to restart safely if maintenance assumed an hour of lag. Give each table one maintenance owner, whether a scheduled Spark job or post-commit maintenance, so retention is set in one place.

113. How do you use Iceberg from Python without a Spark cluster?

PyIceberg lets Python use Iceberg without a Spark cluster. It loads a table from a catalog, plans the scan from metadata and returns Arrow data for pandas or DuckDB.

It suits reading filtered slices for analysis or machine learning and inspecting metadata, can handle small appends and overwrites from a service, and is the wrong tool for large joins or compaction. Pass a row filter and the selected columns to the scan so that pruning happens before data reaches memory.

One process is limited by memory and by the delete files it must apply, so read only the partitions you need. Supported write operations, delete types, transforms and format versions differ from the Java library and change quickly, so check your release. DuckDB and some warehouses can also read Iceberg directly, with their own limits.

catalog (REST, Hive, Glue, SQL) -> table -> scan(filter, columns)
                                          -> Arrow, pandas, DuckDB
114. How do you share Iceberg tables with consumers outside your platform or cloud?

Share Iceberg tables externally by letting capable consumers read them through a catalog, serving others from a query engine or API, or replicating a published copy.

Direct access through a REST catalog with short-lived credentials suits large reads by capable engines, at the cost of egress and version compatibility. A query service helps tools without Iceberg support, while you pay for compute and concurrency. A data API suits applications with small payloads, and a copy gives strict isolation at the price of freshness and duplication. Bucket access alone is a poor option, since storage permissions cannot express table rules and raw files give no consistent view.

Decide how consumers authenticate, what they may see, how access is audited and how schema or format changes reach them. Publish a stable view or tagged snapshot so your maintenance does not surprise them.

115. How do JDBC clients and BI tools query Iceberg tables?

JDBC clients and BI tools reach Iceberg through a query engine over JDBC or ODBC, because Iceberg has no query server of its own.

Trino or Presto serves interactive SQL to many users, a Spark Thrift server reuses Spark SQL logic, a warehouse with Iceberg support fits an existing BI estate and Hive serves existing Hive clients. The engine resolves the table through the catalog and reads the files. The JDBC catalog is a different thing: it stores table pointers in a relational database and runs no queries.

Dashboard speed depends mostly on the table: cluster it for the dashboard filters, keep file counts reasonable, expose views as the stable interface and size the engine for concurrency. If queries are slow only from the BI tool, inspect its SQL, since wrapped columns or implicit casts can stop pruning.

BI tool --JDBC/ODBC--> query engine --catalog--> Iceberg metadata --> files
116. What is the difference between the REST catalog API and a REST API that serves data?

The REST catalog API serves table metadata and commits to query engines. A data API serves rows to applications and is something you design yourself.

The catalog follows Iceberg’s REST specification and returns table metadata, file locations and credentials; it never returns query results, and the engine still reads the files. A data API is called by your consumers’ applications and should answer from a query engine or serving store instead of reading files on each request.

Expecting rows from the catalog is the common mistake. For a data API, precompute the shapes it needs, paginate, pin each response to a snapshot so pages stay consistent and cache by snapshot ID, comparing it with the table’s current one to invalidate. For millisecond responses, publish results to a key-value or relational store and keep Iceberg as the source of truth.

117. How do you query Iceberg together with data in other systems?

To query Iceberg together with data in other systems, either federate the query or move the data into Iceberg.

Federation connects several catalogs in an engine such as Trino or Spark, pushes filters to each source where possible and joins the results. It is current and quick to start, but loads the source on every query, performs only as well as pushdown and the slowest side allow and reads each source at a different moment. Ingestion costs pipelines and lags behind the source, in return for controlled extraction, optimised layout and a consistent set of snapshots.

Weigh how often the query runs, how much data crosses the network, whether the source can take the load and whether results must be reproducible. A hybrid usually works: federate small reference lookups and ingest large or frequently joined data, since an unpushed filter pulls a whole table.

118. How are access control and encryption handled for Iceberg tables?

Access control for Iceberg tables is enforced by the catalog, storage permissions and engines, not by the table format.

The catalog decides who may list, read, change or drop tables, storage decides who may touch objects, credential vending issues short-lived table-scoped storage access and engines apply row filters, masks or views. If any identity has broad storage access it can bypass the catalog by reading files, so grant storage access through the catalog.

Table encryption needs format version 3 and a supporting release: set a key management service on the catalog and encryption.key-id on the table. Data, delete, manifest and manifest list files are encrypted, the metadata JSON is not, and support depends on the catalog and file format. Storage-side encryption is a simpler, separate layer. Column statistics contain real values, so protect metadata too.

119. How do you replicate Iceberg tables to another region for disaster recovery?

To replicate an Iceberg table to another region, rewrite its paths for the new location, copy data before the metadata that references it and register the metadata in the second catalog. A plain directory copy fails because metadata holds absolute paths.

Run rewrite_table_path on the primary. It writes rewritten metadata and position delete files to a staging area and lists source and target paths, but copies nothing; skip it only if storage preserves the original paths. Copy data files first, then the rewritten files, register the metadata and validate, and rehearse failover and failback.

Bucket replication alone is not enough, since objects arrive out of order and the catalog pointer is not replicated. Define recovery point and time objectives, keep a single writer, and make sure expiry on the primary cannot delete files the secondary needs.

primary                          secondary
data + metadata  --replicate-->  data + metadata (paths rewritten)
catalog          --register -->  catalog entry at a chosen metadata file
120. How do you tune read performance on an Iceberg table?

Tune read performance by removing the largest source of wasted reading first, usually in the order partitioning, sort order, file sizes, delete cleanup, manifests and statistics.

Partitions that match filters skip whole sets of files, sorting or Z-order makes column bounds selective, larger files and fewer deletes reduce per-file work, rewritten manifests speed planning and column metrics and table statistics help the optimiser. Bloom filters (write.parquet.bloom-filter-enabled.column.<name>) help point lookups, and split size and vectorised reads come last.

Work from one slow query: record files scanned, bytes read, planning time and the plan, change one thing and measure again. If every file is still read, the filtered column is neither partitioned nor clustered. Dynamic filtering, storage-partitioned joins and aggregate pushdown vary by engine and version.

Design and recovery scenarios

121. Someone deleted a manifest file from storage. Is the data lost?

Usually not. A manifest only lists files, so the data files are normally still there.

Queries on any snapshot that needs the manifest fail with NotFoundException naming the missing .avro file, while other snapshots read normally. Stop writers and pause maintenance first, because orphan removal could delete data that only the broken snapshot referenced. Best is to restore the exact file from object versioning or backup. Otherwise roll back to the latest snapshot that does not use it, as below, and reload newer data from the source.

If neither works, rebuild, preferably by reloading from the source. Salvaging files is delicate, because the data directory also holds replaced and orphan files and add_files imports whole directories without applying delete files, so deleted and duplicate rows come back. Copy only the files known to be live to a staging location and reapply the deletes. Versioned buckets, no lifecycle rules on metadata paths and delete rights limited to maintenance protect against this; a missing data file, unlike a manifest, means missing rows.

CALL demo.system.rollback_to_snapshot('shop.orders', <last good snapshot id>);
122. The catalog entry is gone or points to a missing metadata file. How do you recover?

If the catalog entry is lost or points to a missing file but the table’s files survive, you can register the table again from a metadata file.

Stop all writers, list the metadata/ directory, find the newest valid metadata JSON and confirm that its manifest lists and manifests exist. Register it under a temporary name, validate counts and then swap the name, using the call shown below.

Choosing the file is the delicate part. An older one silently loses later commits, and a newer one may come from a commit that failed and was never current. Catalog backups, audit logs and the metadata log inside candidate files are better evidence than the highest version number. Never write through two entries for the same table, and back up catalog state with enough storage history to restore what it references.

CALL demo.system.register_table(
  table => 'shop.orders_recovered',
  metadata_file => '<full path to the metadata.json>');
123. A job overwrote a large table with wrong data. How do you restore it?

Restore a wrongly overwritten table by rolling back to the snapshot before the bad commit, provided nothing valid followed it. The earlier files remain until snapshot expiry removes them.

Pause writers and expiry, find the bad commit in snapshots by operation, time and application ID, check its parent with a time-travel query, roll back and replay the corrected job. If good commits followed, rebuild only the affected partitions from the earlier snapshot and reapply later changes. If the snapshot has expired, restore from backup or reload from the source.

The usual cause is static overwrite mode replacing the whole table when one partition was intended. Use dynamic or filtered overwrites, validate on a branch before publishing and fail jobs on a row-count guard. The statements below show the inspection and a timestamp rollback.

124. Design a table that serves a near-real-time view and a daily batch report from the same data.

To serve both a near-real-time view and a daily report, write the stream into one table, serve the live view from the latest snapshot and run the report from a tag taken at the day’s close.

First clarify freshness, whether rows are updated or only appended and whether the report must be reproducible. Commit every minute or few minutes, compact closed partitions to control small files, define a cut-off for late events and keep raw data append only, building a merged table if updates are needed.

128. How do you test pipeline changes against production-sized Iceberg data safely?

A branch on the production table hides test writes from readers of main. Time travel gives fixed input for comparing old and new logic. The snapshot procedure rehearses a migration of a Hive or Spark table, not of an Iceberg one, and a copy of representative partitions is safest for DDL or layout changes.

131. How does schema evolution work inside structs, lists and maps?

Schema evolution works inside structs, lists and maps because every nested field has its own field ID. You can add, rename, widen and drop nested fields without rewriting data, except that you cannot add a field to a map’s key struct.

Nested fields are addressed by a dotted path, with element naming the struct inside a list and value the struct inside a map. Reading by ID keeps old files compatible: a field missing from a file is filled with null or its default, and one no longer in the schema is skipped.

In the example below, addr.city is dropped and added again, so the final query returns NULL although the old file holds Pune; the new field has a new ID. A query on an earlier snapshot still shows the old structure.

132. What is the VARIANT type, and what does shredding do?

variant is a format version 3 type that stores semi-structured values such as JSON in a binary encoding. Shredding writes frequently occurring paths into their own typed Parquet columns, so a reader can fetch a path without decoding the whole value.

The engine needs a variant type of its own: a Spark 4 build with the matching Iceberg runtime can use it, while Spark 3.5 cannot create such a column. Shredding is off by default and can be enabled by table property, session setting or write option. Rare paths, or ones whose type changes, stay in the binary value.

This sits between a JSON string, which must be parsed on every read, and a struct, which is fast but needs a schema change for each new field. Pruning on shredded paths depends on engine and release, so measure bytes read.

CREATE TABLE demo.shop.events (id BIGINT, payload VARIANT) USING iceberg
TBLPROPERTIES ('format-version' = '3', 'write.parquet.shred-variants' = 'true');

INSERT INTO demo.shop.events
SELECT id, parse_json(concat('{"user":', id, ',"city":"Pune"}')) FROM range(100);

SELECT variant_get(payload, '$.city', 'string')
FROM demo.shop.events
WHERE variant_get(payload, '$.user', 'int') = 7;
133. Can two concurrent jobs insert the same key? How do you enforce uniqueness?

Yes, two concurrent jobs can insert the same key, because Iceberg enforces no primary key. Two appends succeed, and so do two MERGE statements that only insert; only a MERGE that also has WHEN MATCHED rejects the second writer under serializable isolation.

The reason is how each commits. In Spark, a MERGE with only WHEN NOT MATCHED runs as a plain append, which validates nothing against other writers at any isolation level. With WHEN MATCHED it is a row-level operation: serializable isolation checks for newly added files that could match, and the loser gets ValidationException, while snapshot isolation skips the check and both insert.

To keep keys unique, use that second form with serializable isolation, rerun the whole statement after a failure and deduplicate the source. A single writer per key range avoids the race altogether. Alert on duplicate keys either way.

ALTER TABLE demo.shop.orders SET TBLPROPERTIES (
  'write.merge.isolation-level' = 'serializable');
134. What happens if the schema changes while a job is writing?

If the schema changes while a job is writing, a running append normally still commits. Its files carry field IDs, so readers map them to the new schema.

The writer fixed its schema when it planned the job, and at commit it reapplies its files on the latest metadata. A column added meanwhile reads as null or its default for those rows, a rename has no effect, a widened type promotes older values and a dropped column’s values stay in the file unread.

Two racing schema changes behave differently: each is committed once against the metadata it started from, so the loser gets CommitFailedException and must be rerun. Row-level operations validate more than appends, and streaming jobs usually keep their starting schema until restarted, so coordinate breaking changes with writers even though the table stays readable.

135. How does the Flink sink achieve exactly-once delivery into Iceberg?

The Flink sink achieves exactly-once delivery with a two-phase commit tied to checkpoints: writers close files when a checkpoint starts, the file list is saved in checkpoint state and the committer publishes it after the checkpoint completes.

Each snapshot records the job ID, operator ID and highest committed checkpoint ID. If the job fails after committing but before learning of success, recovery reads that ID and does not commit those files again.

End to end, the Kafka source replays from offsets saved in the same checkpoint, so source position and table move together. This requires checkpointing, a restart from checkpoint or savepoint and a latest commit that expiry has not removed. Duplicates written into Kafka by producers remain and need a key-based merge or upsert. The Kafka Connect sink has its own exactly-once path through Kafka transactions.

barrier arrives     writers close data and delete files
checkpoint state    the file list is persisted; Kafka offsets are saved too
checkpoint done     committer creates an Iceberg snapshot
snapshot summary    flink.job-id, flink.operator-id, flink.max-committed-checkpoint-id
restore             commit only checkpoints newer than the recorded ID
136. Design a CDC pipeline from a database into Iceberg for high event rates with low latency.

Start with arithmetic: at 100,000 events per second and a 30 second checkpoint, each commit carries 3 million events and there are 2,880 commits a day, which sets parallelism, file sizes and maintenance. Keying by primary key keeps each row’s changes ordered, the commit interval should be the longest the latency target allows, the current table is bucketed by key and the source log position is kept for deduplication.

137. Why does Flink write equality deletes instead of finding the old row's position?

Flink writes equality deletes because finding an old row’s position would need an index from every key to its file and row. Its writer keeps that map only for rows inserted during the current checkpoint.

So a key inserted and then changed within one checkpoint gets a position delete, while a key from an earlier commit gets an equality delete holding just the key. This keeps writer state small and writes fast, and shifts the read cost described in question 47 onto queries until compaction removes the deletes.

The alternative builds the index in maintenance. An experimental Flink task reads equality deletes from a staging branch, resolves them through a primary key index in Flink state and commits deletion vectors to the target branch, requiring format version 3. State grows with live rows, so size it generously, prefer RocksDB and avoid other writers on the target.

key inserted in this checkpoint, then updated  -> position delete (writer knows file and row)
key written by an earlier commit               -> equality delete (writer knows only the key)
138. Change events arrive out of order or hours late. How do you apply them correctly?

Apply late or out-of-order change events by ordering on a sequence from the source rather than arrival time: keep the newest event per key in each batch, apply it only if newer than the stored row and keep deletes soft while old events can still arrive.

In the example below, an event for key 1 with sequence 15 arrives after a delete at 30 and changes nothing. Had the row been physically removed, that old event would have found no match and brought the customer back. Readers filter on deleted = false, usually through a view, and soft-deleted rows are purged once older than the longest possible delay.

A direct streaming upsert applies events in arrival order, so it is safe only when each key’s events arrive in order, such as through one Kafka partition. Check how far back late events reach, since merging them touches old partitions.

DROP TABLE IF EXISTS demo.shop.customers PURGE;
CREATE TABLE demo.shop.customers (id BIGINT, name STRING, seq BIGINT, deleted BOOLEAN)
USING iceberg;
INSERT INTO demo.shop.customers VALUES (1, 'new name', 30, true);

MERGE INTO demo.shop.customers t
USING (
  SELECT id, name, seq, deleted FROM (
    SELECT *, row_number() OVER (PARTITION BY id ORDER BY seq DESC) AS rn
    FROM VALUES (1, 'late name', 15L, false), (2, 'second', 40L, false)
      AS v(id, name, seq, deleted)
  ) latest WHERE rn = 1
) s
ON t.id = s.id
WHEN MATCHED AND s.seq > t.seq THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

SELECT * FROM demo.shop.customers ORDER BY id;
139. How do you handle bad or mismatched records without stopping a streaming sink?

Handle bad or mismatched records by separating them before the Iceberg sink: validate each one, write good rows to the table and send failures to a dead-letter topic or errors table with enough context to replay them.

In Flink this is a side output from the validating operator; in Spark Structured Streaming, a split inside foreachBatch whose two writes must be safe to repeat. Kafka Connect’s error handling covers converter and transform failures, so check what your sink does when a record fails at write time.

Once a bad record reaches the writer, a type or schema mismatch usually fails the task, and a restart meets it again, so validate types, required fields and ranges. Alert on the dead-letter rate, stop the pipeline if most records fail and keep a replay job that merges corrected records by key.

                             -> invalid  -> dead-letter: raw payload, reason, topic, partition, offset
140. How does Spark's AvailableNow trigger work with an Iceberg source?

Spark’s AvailableNow trigger processes everything available in the Iceberg source when the query starts, in one or more micro-batches, and then stops. The checkpoint lets the next run continue.

Each micro-batch commits its own snapshot to the target, and rate limit options such as maximum files per batch decide how a backlog is divided. A run with no new data commits nothing, and commits arriving after the end point is fixed wait for the next run.

This gives scheduled jobs streaming’s bookkeeping without a permanently running cluster. The usual streaming limits remain: overwrite and delete snapshots stop the query unless skipped, and the source must retain snapshots until the next run has read them. The code below shows the pattern.

(spark.readStream.format("iceberg")
    .option("streaming-max-files-per-micro-batch", "100")
    .load("demo.shop.source")
    .writeStream.format("iceberg")
    .trigger(availableNow=True)
    .option("checkpointLocation", "s3://bucket/checkpoints/target")
    .toTable("demo.shop.target")
    .awaitTermination())
141. How do you handle schema changes automatically in a Kafka to Iceberg pipeline?

Automate only additive schema changes in a Kafka to Iceberg pipeline: let the sink add nullable columns, send incompatible records to a dead-letter path and review renames, type narrowing and drops.

Kafka Connect can add missing record fields with iceberg.tables.evolve-schema-enabled, Flink’s experimental dynamic sink can update table schemas and Spark can use mergeSchema on tables with write.spark.accept-any-schema. A schema registry with compatibility rules stops most breaking changes at the producer, which is cheaper.

Without those rules, a misspelt field becomes a permanent column and a rename appears as a new column beside one that stops filling. Many streaming jobs also fix their parser schema at startup and ignore new fields until restarted, so alert on unknown fields and let someone decide.

142. When would you append to a staging table and merge periodically instead of upserting directly?

Append to a staging table and merge periodically when minutes or hours of latency are acceptable and you want cheap reads, replay and control over conflicts. Upsert directly when the table must be fresh within one checkpoint.

Direct upserts accumulate equality deletes, order events by arrival, replay from Kafka only while it retains them and conflict with compaction continuously. Staging lets the merge choose its write mode, order and deduplicate by a source sequence, replay from the table and schedule compaction between runs, at the price of storing data twice. The merge reads new staging rows incrementally, which works because that table only receives appends.

A mix is common: consumers needing seconds read the append table through a latest-row view, while everyone else reads the merged table.

Layout, maintenance and performance

143. What goes wrong when you change identity(region) to bucket(16, region)?

Changing identity(region) to bucket(16, region) usually backfires, because bucketing suits columns with many distinct values and a region has few. With eu, us and ap, two of the three fall into the same bucket of 16, leaving only two partitions in use.

Old files keep the identity layout and new ones use buckets, so queries are planned against both specs. A filter on region = 'eu' reads exactly that region in old files, but a whole shared bucket in new ones. Range filters stop pruning, deleting a region now rewrites mixed files instead of changing metadata, and dynamic overwrite replaces a bucket that may cover several regions.

If the aim was to split one large region into smaller pieces, keep the region partition and add a bucket on a high-cardinality key, or sort by that key within each partition.

ALTER TABLE t REPLACE PARTITION FIELD region WITH bucket(16, region);
SELECT spec_id, partition, record_count FROM t.files;
144. Linear sort, Z-order or Hilbert curve: which clustering should you use?

Use a linear sort when one column dominates the filters, and a space-filling curve (Z-order or Hilbert) when queries filter on two to four columns independently.

A linear sort prunes superbly on its leading column and poorly on later ones. A curve spreads locality across columns, giving up some precision on each; Z-order’s jumps widen some file ranges, while Hilbert keeps better locality but has narrower support. Spark’s rewrite_data_files accepts Z-order, and newer releases accept hilbert() on Spark 4.1 and later; on Spark 3.5 it fails with “Cannot convert transform with more than one column reference”.

Choose curve columns carefully. A mostly null or single-valued column adds little, a steadily increasing timestamp is usually clustered already by ingestion and partitioning, and only the first 8 bytes of a long string count by default (var-length-contribution). Each extra column weakens the others.

CALL demo.system.rewrite_data_files(
  table => 'shop.orders', strategy => 'sort',
  sort_order => 'zorder(customer_id, order_id)',
  options => map('rewrite-all', 'true'));
145. When does bin-pack compaction make queries slower?

Bin-pack compaction makes queries slower when it merges files that held different, narrow ranges of a filter column, so that each output covers a wide range and column bounds stop skipping files.

Bin-pack combines files by size without clustering data across them. It is the cheapest strategy, with little shuffle. A sort rewrite shuffles and sorts to restore narrow ranges, and Z-order costs the most while narrowing several columns together.

The damage appears on tables that were deliberately sorted or whose arrival order clustered a column: planning gets faster with fewer files, yet each query reads more bytes. Use bin-pack where tables are read in full or by partition, and the sort strategy, restricted with where to closed partitions, where speed depends on bounds. Judge the result by bytes scanned, not file counts.

before    file A: customer 1..10     file B: customer 900..910    filter 905 reads B
bin-pack  file AB: customer 1..910                                filter 905 reads AB
146. How does the Parquet row group size affect pruning and object store reads?

The Parquet row group size controls pruning inside a file and how a scan splits it into byte-range requests. Manifest pruning works on whole files and is unaffected.

Each row group has its own column statistics. Readers fetch the needed column chunks with ranged reads, and Iceberg records split offsets so that a large file can be divided between tasks at row group boundaries. Smaller groups skip more precisely but add footer metadata and requests. Larger ones compress and encode better and need fewer requests, while using more writer memory for each open file.

The property is write.parquet.row-group-size-bytes, 128 MB by default. Wide tables fit few rows into a group, and many open partitions multiply writer memory by that size. Sort the data first, since statistics help little on unclustered data, and change the size only after measuring.

147. How do you optimise a table with hundreds of columns when queries read only a few?

Optimise a very wide table by relying on Parquet to read only the projected columns, then controlling the costs that grow with width: statistics, footers, write memory and rows per row group.

Bounds are collected for the first 100 columns by default, so a filter column beyond that cannot skip files until you set write.metadata.metrics.column.<name>. If manifests are large, set the default mode to none or counts and enable only filter columns. Publish views to discourage SELECT *, limit partitions per write task, and group sparse, changing attributes in a struct, map or variant.

Sort on common filter columns so their bounds are selective. Rarely used columns that bloat rewrites can move to a second table with the same key, but that adds a join, so split only when the column groups are really used apart.

148. How would you automate maintenance for thousands of tables?

Automate maintenance across thousands of tables with a control plane that reads each table’s metadata, scores the work worth doing and runs it within a compute budget, skipping tables that have not changed and have no problem.

A registry holds owner, tier and retention. Signals come cheaply from metadata tables, as in the query below: small files, delete files and average size. Rank higher the frequently queried partitions with many small files, growing delete counts and tight targets; rank lower unread tables, tables with no new snapshot and rewrites that move much data to save few files.

Compact only qualifying partitions with where, run expiry and orphan removal from each retention policy, allow one maintenance job per table and record before and after values. That record shows whether the spend helped and exposes jobs that keep selecting nothing or losing conflicts.

registry (owner, tier, retention) -> collect signals -> score -> queue
      -> workers with a concurrency limit, one maintenance job per table -> record results

       sum(CASE WHEN file_size_in_bytes < 134217728 THEN 1 ELSE 0 END) AS small_files,
       sum(CASE WHEN content <> 0 THEN 1 ELSE 0 END) AS delete_files,
       round(avg(file_size_in_bytes) / 1048576, 2) AS avg_mb
FROM demo.shop.orders.files;
149. How do you stop rewrite_data_files from running out of memory on very large tables?

Stop rewrite_data_files running out of memory by bounding how much is in flight: smaller file groups, fewer groups at once, a where clause and partial progress.

max-file-group-size-bytes (100 GB) sets each unit of work and max-concurrent-file-group-rewrites (5) how many run together. With partial-progress.enabled, finished groups commit early, in at most partial-progress.max-commits (10) commits, and partial-progress.max-failed-commits, equal to that by default, sets the failures tolerated. A partial-progress job can finish with only part of its selection rewritten, so check failed_data_files_count and rerun. min-input-files changes which groups qualify, not their memory use.

Planning can stay slow after rewrite_manifests because the rewrite helps only when the number or arrangement of manifests was the problem. It cannot fix filters that do not prune, large metadata files, many delete files or a slow catalog.

151. How do you fix driver out-of-memory errors during scan planning?

Fix driver out-of-memory errors in planning by shrinking the metadata the driver holds or spreading planning across the cluster. The usual cause is a scan over very many files, each with statistics for many columns, some with deletes.

Filters on partition and sort columns load fewer manifests, compaction removes file entries, limiting metrics to filter columns makes entries smaller, delete compaction shrinks the delete index and rewritten manifests skip better. Setting read.data-planning-mode to distributed has executors read manifests; the default is auto. Finally, give the driver more memory.

152. A Trino query filtered on the partition column still scans tens of thousands of files. How do you diagnose it?

153. Does a filter such as CAST(event_ts AS DATE) still prune partitions?

154. A MERGE updating ten thousand rows in a huge table takes hours. How do you fix it?

A MERGE that updates ten thousand rows but takes hours is probably scanning and rewriting far more than it changes. Without a predicate limiting the target, every file is a candidate.

Copy-on-write rewrites each file holding even one match, so ten thousand rows spread over as many 512 MB files means rewriting about 5 TB. Put a literal partition range, computed from the source, in the ON clause, as below. Cluster the table on the merge key so matches fall in few files, use merge-on-read, deduplicate and filter the source so it may broadcast, or partition both sides compatibly to avoid a shuffle.

Spark’s runtime row-level group filter, on by default, reduces rewritten files, but the matching join still reads whatever static predicates allow. Compare files scanned and written in the Spark UI and look for spill.

SELECT order_id, 'PAID' AS status, max(order_ts) AS order_ts
FROM demo.shop.orders WHERE order_id < 10 GROUP BY order_id;

MERGE INTO demo.shop.orders t
USING order_updates s
ON t.order_id = s.order_id
   AND t.order_ts >= TIMESTAMP '2026-11-01 00:00:00'
   AND t.order_ts <  TIMESTAMP '2026-11-06 00:00:00'
WHEN MATCHED THEN UPDATE SET status = s.status;
155. Do delete files turn off vectorized reads?

Delete files do not turn off vectorized reads for Parquet in Iceberg’s Spark reader, although they do rule them out for ORC.

Spark batch reads use the vectorized Parquet reader when it is enabled, the projected columns are primitive and all files are Parquet, with or without deletes. Projecting a struct, list or map, or mixing file formats, falls back to row reads, as does ORC with delete files. read.parquet.vectorization.enabled is true by default, while ORC vectorization is off.

So a slow table with deletes is usually paying to load and apply them, particularly equality deletes, rather than suffering a change of reader; check delete counts and compact. These rules describe one release of the Spark connector. Trino and other engines have their own readers, so confirm their behaviour from plans and statistics.

156. Object storage request costs are high although queries return little data. Why?

Object storage request costs can be high on small results because each query and job requests metadata and file ranges before returning anything. The count follows files, delete files and planning passes, not result size.

Many small data files, each with a footer and column ranges, are cured by compaction, and delete files by delete compaction. Heavy planning calls for manifest rewrites and table caching, constant polling for longer intervals or cached results and useless filters for better partitioning and sorting. Run orphan removal, which lists whole prefixes, less often and more narrowly, and commit less often.

Measure first with access logs or request metrics grouped by prefix, operation and identity, to see whether data, metadata or listings dominate. A very short or disabled catalog cache trades request cost for freshness.

157. ZSTD or Snappy for Iceberg data files?

ZSTD is the default for new Iceberg tables and usually produces much smaller files, while Snappy uses less CPU. On object storage, where network reads are often the bottleneck, smaller files tend to win.

The ratio depends heavily on content: for one synthetic table of a million rows with repetitive strings, ZSTD wrote about 1.9 MB and Snappy about 6.0 MB. ZSTD therefore saves storage and bytes read, costs more write CPU and offers tunable levels.

Measure with your own data by writing the same sample with both codecs and recording file size, write time and real query time on your engines. The property affects only files written afterwards, and old files keep their codec until a rewrite touches them, so a mixed table is normal and readable.

ALTER TABLE t SET TBLPROPERTIES ('write.parquet.compression-codec' = 'snappy');

Catalogs, governance and migration

158. How do Hive Metastore, AWS Glue, Nessie, Polaris and Unity Catalog compare as Iceberg catalogs?

Hive Metastore, AWS Glue, Nessie, Apache Polaris and Unity Catalog can all hold the pointer to an Iceberg table’s metadata; they differ in protocol, access control, features and operator.

Hive Metastore speaks Thrift and is already present on Hadoop platforms, with scaling and coarse security as concerns. Glue is managed and tied to AWS permissions. Nessie adds branches and tags across tables but is another service to run. Polaris speaks Iceberg REST, grants privileges to roles and vends short-lived credentials. Unity Catalog exposes a REST endpoint where Databricks documents external read and write for managed Iceberg tables, and read only for foreign Iceberg and Delta tables exposed as Iceberg.

Decide on engine write support, permissions, commit rate, backup and exit effort, checking current documentation because these products change quickly. Question 49 covers general selection.

159. How does credential vending work in a REST catalog, and what can it not secure?

With credential vending, the engine asks a REST catalog to load a table, and the catalog returns short-lived storage credentials limited to that table’s location.

The client requests this with the X-Iceberg-Access-Delegation header; the catalog authorises the principal and returns metadata with temporary credentials. Compared with giving engines direct bucket access, which lets them bypass catalog permissions, only the catalog holds broad rights. Remote signing is the alternative in which the catalog signs each request, at the cost of more calls. Scoping per table avoids writing storage policies for every user and table, and long jobs depend on the client refreshing expiring credentials.

It cannot restrict rows or columns, since anyone who can read a file reads all of it. Remove engines’ standing bucket permissions and give each table its own prefix.

engine -> catalog: load table   (header X-Iceberg-Access-Delegation: vended-credentials)
catalog: authorises the principal for this table
catalog -> engine: metadata + temporary credentials scoped to the table's paths
engine -> storage: reads and writes with those credentials
160. What happens if two catalogs point at the same table, and how do you avoid it?

If two catalogs point at the same table, each swaps its own pointer and never sees the other’s commits, so the table forks. Changes are lost, and maintenance on one side can delete files the other references.

One catalog must own commits, with every engine writing through it and other platforms reading through it or receiving a refreshed read-only copy. Snowflake shows both arrangements: for Snowflake-managed tables it is the catalog, handles maintenance and documents external read and write through the Horizon Iceberg REST API; for externally managed ones another catalog owns the table. Snowflake’s support is then more limited, it must refresh to see changes, and writes are supported for tables in a remote Iceberg REST catalog. Check current limits.

Detect a fork by comparing metadata locations. Repair it by stopping writers, choosing the true history, replaying the other’s changes and removing the duplicate without purge.

catalog A -> v10 -> writer A commits v11a
catalog B -> v10 -> writer B commits v11b     both succeed; the histories diverge
161. How do query engines cache Iceberg metadata, and when can results be stale?

Engines cache Iceberg metadata safely because metadata files are immutable. Results go stale when an engine caches which snapshot or metadata file is current.

Spark’s catalog cache is on by default with a 30 second expiry. Trino’s iceberg.metadata-cache.enabled, also on, keeps metadata files in coordinator memory, or on local disk when the file system cache is used. StarRocks caches in memory and optionally on disk and refreshes in the background by polling the metastore, every ten minutes by default, which can appear directly as lag after another engine commits.

When engines disagree, find the snapshot ID each one is using, refresh or restart the lagging cache and compare again. Check the cache settings for your versions, and for results that must match, pin both queries to one snapshot or tag.

162. How do you apply column masking and row-level security consistently across engines?

The Iceberg table format defines no row or column policies, so masking and row-level security are enforced by the catalog and engines. Consistency comes from letting only engines that enforce your rules read the files.

Per-engine policies drift unless carefully duplicated, and a central policy service covers only engines with its plugin. Views with filters and masks need compatible dialects and denied access to base tables. Masked copies and a query service in front of restricted data work everywhere, at the cost of extra pipelines or a single access path.

Credential vending and storage permissions stop at the file: anyone who can read it sees every column and row. Classify data, limit direct file access to trusted jobs, publish masked copies for others, test one user in every engine and remember that statistics reveal values.

163. What can Iceberg's metrics reporting tell you?

Iceberg’s metrics reporting produces a report after planning a scan or committing a change.

A scan report shows planning time, manifests and data files scanned or skipped and delete files involved. A commit report shows attempts, duration and the files and records added or removed. Reports are only logged by default. Setting the catalog property metrics-reporter-impl to a class implementing MetricsReporter, as below, sends them to your monitoring system, and REST catalogs can receive them from clients.

This is a cheap way to see trends across many tables, where rising commit attempts signal contention and a falling share of skipped files signals layout decay. Only clients that report are covered, so combine it with metadata tables, which describe a table whoever wrote it.

spark.sql.catalog.prod.metrics-reporter-impl=com.example.PlatformMetricsReporter
164. How do you enforce table standards at creation time?

Enforce table standards at creation through catalog configuration: table-default. properties apply when a statement gives no value, and table-override. properties replace whatever it asks for.

With the override shown below, a CREATE TABLE that sets the property to false still produces true. Defaults suit sensible starting values that owners may change, while overrides apply to tables created through that configuration. A catalog service policy, where supported, binds every client, and a scheduled audit finds drift.

The prefixes are client settings, so an engine configured without them ignores them, and they do not stop a later ALTER TABLE. Pair them with permissions on altering tables and an audit job that reads properties and reports exceptions.

spark.sql.catalog.prod.table-default.write.parquet.compression-codec=zstd
spark.sql.catalog.prod.table-override.write.metadata.delete-after-commit.enabled=true
spark.sql.catalog.prod.table-default.history.expire.max-snapshot-age-ms=604800000
165. What do Apache XTable and Delta UniForm translate, and what is lost?

Apache XTable and Delta UniForm both write another format’s metadata over existing data files without copying data. XTable converts between Hudi, Delta Lake and Iceberg, while UniForm goes only from Delta to Iceberg or Hudi.

XTable runs as a separate sync step and does not carry over merge-on-read tables or deletion vectors. UniForm generates metadata asynchronously after Delta commits, is read only for the other clients, and its documented Iceberg compatibility version 2 mode excludes deletion vectors. Format-specific features, such as generated columns, may be missing on the target.

Treat translated metadata as a read-only view: let only the source format’s writers change and maintain the table, monitor sync lag and check the current limitation list before depending on it.

166. Why can add_files return wrong query results, and how do you guard against it?

add_files can return wrong results because it registers existing files from their footer metadata without checking that their schema matches the table, and planning then trusts that metadata.

A wrong bound from a faulty writer makes planning skip a file that holds matching rows, silently. Mismatched types or names give errors, nulls or wrong values, adding a file twice with the duplicate check disabled duplicates rows, and expiry may later physically delete the files even if another system uses them.

After importing, compare minimum and maximum values read from the data with the bounds in the files table, and filtered counts with the source. A filter returning fewer rows than the same condition applied after a full scan indicates bad bounds. If the files’ history is doubtful, rewrite them so Iceberg computes the statistics.

167. Which legacy Hive data types cause trouble in a migration?

The legacy Hive types that cause trouble are CHAR and VARCHAR, which become plain strings, and old INT96 timestamps, which are imported without usable statistics. Both can change query behaviour silently.

A CHAR(5) value such as ab depends on its writer: Spark pads it, so WHERE c = 'ab' finds nothing after migration, while Hive’s Parquet writer stores it unpadded, so the padded comparison fails; a table may hold both. VARCHAR loses its length limit. INT96 columns are readable but have no bounds in manifests, and timestamps written under different time zone settings may shift.

Check stored lengths, then trim CHAR values while rewriting or fix every comparison. Enforce limits in the pipeline and compare edge values, including old dates, on every engine. Rewriting with rewrite_data_files and rewrite-all restores statistics but not inconsistent strings, which need an explicit transformation.

168. How do you keep Hive and Iceberg consistent if both are written during a cutover?

Keep Hive and Iceberg consistent during a cutover by avoiding independent dual writes: have one authoritative write path, derive the other table from it and reconcile every batch.

Two separate writes cannot be atomic, so one can fail while the other succeeds and retries then differ. If both must come straight from the source, make each write idempotent per batch, record the batch ID in both and publish it only when both have it. First Iceberg shadows Hive and is validated, then readers move in groups, writes switch to Iceberg with Hive fed from it, and finally Hive is retired.

Set an exit criterion, such as a number of reconciled batches, and an end date, because an open-ended dual-write period doubles cost and leaves nobody sure which table is right.

source -> authoritative table -> derived copy
                 |                     |
                 +---- reconcile per batch (counts, key checks, checksums)
169. How do you migrate a Hive table whose partitions live in different buckets or paths?

A Hive table with partitions in different buckets or paths can be migrated as it is, because migrate, snapshot and add_files record each file’s full path. The metastore’s partition locations are followed and nothing moves.

The work comes afterwards, since the table no longer lives under one directory. Every engine needs read access to every location, orphan removal examines only the table location by default, expiry after migrate can delete replaced files anywhere, lifecycle rules on another bucket may delete needed files, disaster recovery must cover all locations and another system may still own a path.

Rehearse with snapshot, list path prefixes from the files table and compare partition counts. If the scatter is a problem, rewrite into the table’s own location over time and remove old data once no snapshot refers to it.

170. Can you convert a Delta Lake table to Iceberg without rewriting data?

Yes, within limits, a Delta Lake table can be converted to Iceberg without rewriting data. Iceberg’s Delta Lake module has a snapshot action that builds an Iceberg table over the existing Parquet files and replays the transaction history, leaving the source unchanged.

The module is separate from the engine runtimes, and its documentation covers older Delta protocol versions (reader 1, writer 2), so features such as deletion vectors are not included. The files are shared: a VACUUM on the source can break the new table, and expiry or orphan removal on the new table must never run.

The documentation prohibits that cleanup, yet the action does not set gc.enabled to false and uses the source location by default, so set both yourself. For a permanent move, stop Delta writers, take the snapshot, validate it and rewrite the data into the new table so that it owns its files. For read access only, use metadata translation.

DeltaLakeToIcebergMigrationActionsProvider.defaultActions()
    .snapshotDeltaLakeTable("s3://bucket/delta/orders")
    .as(TableIdentifier.of("db", "orders"))
    .icebergCatalog(catalog)
    .deltaLakeConfiguration(hadoopConf)
    .execute();
171. How do you prove that a migrated table matches its source at large scale?

Prove that a migrated table matches its source by freezing or pinning both sides and comparing in layers: counts, per-partition checksums, column aggregates and finally the rows of any partition that differs.

The query below sums a hash of every row for each day on both tables and returns only mismatches, so no rows means they agree. Summing hashes ignores row order and still notices duplicates, although matching checksums are strong evidence rather than proof.

Cast both sides to identical types, since a type or time zone difference changes hashes even when data is right, and watch nulls and padded strings. Compare a fixed Iceberg snapshot with a quiet source, examine differing partitions with EXCEPT ALL and finish by running the business queries people care about.

DROP TABLE IF EXISTS demo.shop.orders_copy PURGE;
CREATE TABLE demo.shop.orders_copy USING iceberg AS SELECT * FROM demo.shop.orders;

WITH source AS (
  SELECT CAST(order_ts AS DATE) AS day, count(*) AS n,
         sum(CAST(xxhash64(order_id, customer_id, amount, status, order_ts) AS DECIMAL(38,0))) AS h
  FROM demo.shop.orders GROUP BY CAST(order_ts AS DATE)
), target AS (
  SELECT CAST(order_ts AS DATE) AS day, count(*) AS n,
         sum(CAST(xxhash64(order_id, customer_id, amount, status, order_ts) AS DECIMAL(38,0))) AS h
  FROM demo.shop.orders_copy GROUP BY CAST(order_ts AS DATE)
)
SELECT * FROM source FULL OUTER JOIN target USING (day)
WHERE NOT (source.n <=> target.n AND source.h <=> target.h);

Operations, recovery and cost

172. A table was dropped with PURGE, but the bucket has versioning. How do you recover it?

With bucket versioning, a table dropped with PURGE can be recovered by restoring the deleted object versions and registering the latest metadata file.

Pause jobs and lifecycle rules first, then find the table location from catalog logs, backups or job configuration. A versioned delete normally leaves a delete marker, so remove markers or copy previous versions back for the newest metadata JSON, its manifest lists and manifests and every data and delete file they reference. Register it under a temporary name, as below, validate counts and rename.

Anything a lifecycle rule has already removed is gone, so the retention of old versions is the real recovery window. Files outside the table location need restoring too. Rehearse on a test table, because restoring millions of objects takes planning and time.

CALL demo.system.register_table(
  table => 'shop.orders_restored',
  metadata_file => 's3://bucket/warehouse/shop/orders/metadata/<latest>.metadata.json');
173. A pipeline bug corrupted hundreds of related tables. How do you restore them to one point in time?

To restore hundreds of related tables to one point, roll each back to the snapshot current at a chosen time, in dependency order with writers stopped, since Iceberg has no cross-table transaction.

Stop writers, expiry and orphan removal, pick the moment before the first bad write, find each table’s snapshot in history, record the plan and roll back as below. Then reset bookmarks, streaming checkpoints and source offsets and validate relationships between tables before restarting.

A timestamp only approximates consistency because tables commit at different moments; restore by batch ID, or tag a consistent set after each good run. Retention must exceed the time needed to detect such a bug. Generate the calls with a script, review them and keep the previous snapshot IDs so the restore can be undone.

CALL prod.system.rollback_to_timestamp('db.orders',    TIMESTAMP '2026-11-26 02:00:00');
CALL prod.system.rollback_to_timestamp('db.customers', TIMESTAMP '2026-11-26 02:00:00');
174. How would you attribute lakehouse storage, compute and request costs to business teams?

Attribute lakehouse costs by giving every table an owner, measuring storage from metadata, tagging compute with table and team and taking request costs from access logs by table prefix.

The query below sizes everything reachable from any snapshot, using distinct paths because all_files repeats them. Charge storage and maintenance compute to the table owner, query compute to the team that ran it from engine history, requests by prefix and identity and the shared catalog by an agreed rule.

Metadata cannot see orphans or old object versions, so reconcile with the storage inventory and report the gap as unowned. For shared tables, allocate storage by tenant partition and query cost by caller. Publish figures alongside the lever each owner controls, such as retention, so the report leads to action.

SELECT count(*) AS files, sum(file_size_in_bytes) AS reachable_bytes
FROM (SELECT DISTINCT file_path, file_size_in_bytes FROM demo.shop.orders.all_files) f;
175. Can you move old Iceberg data to colder storage classes?

Old Iceberg data can move to colder storage classes only if they still allow immediate reads, because every referenced file must be readable at once.

Standard and infrequent access classes work, some with retrieval fees, and Glacier Instant Retrieval gives millisecond access at higher retrieval cost and a minimum duration. Intelligent-Tiering’s automatic tiers are fine, but its optional archive tiers need a restore, as do Glacier Flexible Retrieval and Deep Archive, which would break queries, compaction and time travel.

Age-based lifecycle rules are risky since an old file may be current, and path rules fail with the object storage layout. Prefer tags set by a process that understands the metadata, never tier metadata files and remember that rewriting cold data pays retrieval. Rarely read data may belong in an archive table.

176. How do you audit who changed or read a table?

Auditing who changed or read a table means combining several sources, because table metadata is not an audit log.

snapshots and history show what changed and when, summary keys such as application IDs show which job did it, the catalog’s audit log shows which identity committed or loaded the table and engine and storage logs show who read the data. Summaries are written by clients, so they are informative rather than tamper proof, reads leave no trace and expiry removes history.

Require jobs to stamp identity and run ID using the snapshot-property. write option, ship catalog and storage logs somewhere writers cannot modify and export snapshot records before they expire. Direct file access bypasses catalog logging, so route access through the catalog.

177. Which rules would you enforce from the start on a company-wide Iceberg platform?

On a company-wide Iceberg platform, enforce from the start the rules that are cheap early and very expensive to add later.

Each table should have one catalog owning its commits, preventing forks and lost writes. Storage access should come through the catalog, with one location per table, preventing bypassed permissions and cross-table deletion. Every table needs an owner, retention and maintenance from creation, writes should be idempotent with a run ID, and versioned storage, catalog backups and rehearsed restores should make incidents reversible.

Build these into the platform through creation defaults, permissions that make the unsafe path impossible and automated audits, rather than documents. Allow exceptions with a named owner and expiry date, and upgrade format versions only when every engine using a table supports them, since the step cannot be reversed.

Features and ecosystem

178. What are the key features of Apache Iceberg?

Apache Iceberg’s key features are ACID transactions, schema evolution, partition evolution, hidden partitioning, time travel, support for many engines and metadata that makes planning efficient.

Writes are atomic: readers see all of a commit or none, concurrent writers are checked before they commit, and a bad change can be rolled back. Columns can be added, renamed or dropped without rewriting data because they are tracked by ID. The partition layout can change for new data while old data stays as it is, and queries filter on ordinary columns while Iceberg derives the partition values itself. Each commit leaves a snapshot that can be queried later for audits, debugging or recovery.

Spark, Flink, Trino, Presto, Hive and others can share the same tables through a catalog, and manifests with file statistics let them skip data without listing directories. Row-level UPDATE, DELETE and MERGE, branches and tags complete the picture. These features still need support from each engine, and compaction and snapshot expiry remain your jobs.

179. What is a table format, and how does it differ from a file format?

A file format defines how data is laid out inside one file, while a table format defines which files together make up a table and how that table may change.

Parquet, ORC and Avro are file formats. They decide how rows and columns are encoded, compressed and described within a file, and know nothing about other files. A table format such as Iceberg sits a level above: it records the files that belong to the table, the schema, the partitioning and the history of changes, and it defines how a writer publishes a new version safely.

The difference shows as soon as data changes. A directory of Parquet files cannot say what the current schema is, whether a write has finished or which file replaced which. A table format answers those questions, so several engines can read and write one table. It still stores the rows in ordinary data files, so the two work together.

180. Why does Apache Iceberg matter for a data platform?

Apache Iceberg matters because it lets one copy of data in open storage behave like a reliable database table for many engines.

Without a table format, a data lake gives cheap storage but weak guarantees, so teams copy data into warehouses to get transactions, schema control and fast queries. Iceberg brings atomic commits, evolution, history and metadata-based pruning to the files themselves. Because it is an open specification, ingestion, transformation and reporting can each use a suitable engine on the same tables.

The practical gain is fewer copies and pipelines to keep consistent, lower coupling to one vendor and layout changes that no longer force rewrites. It is not free: someone has to run a catalog, compact files, expire snapshots and check that every engine supports the features in use. For a small dataset with a single reader, that overhead may not pay off.

181. What is an open data lakehouse?

An open data lakehouse is a lakehouse built from open formats and interfaces, so that more than one engine or vendor can read and write the same data.

Data sits in object storage or HDFS in open file formats such as Parquet. An open table format such as Iceberg adds transactions, schemas and history, and a catalog with a published interface, for example the Iceberg REST specification, tells every engine where each table is. Compute is separate from storage, so engines can be added, scaled or replaced without converting the data.

The point is freedom to choose tools and to leave one without a migration project. Openness is only as good as its weakest part: a catalog that few engines support, or access rules that exist in one product only, can lock a platform in just as firmly as a proprietary format. Check write support, permissions and format version support for each engine you plan to use.

182. What does the table metadata file contain?

The table metadata file is a JSON document describing the whole table at one version: its structure, its settings and its snapshots.

It holds the format version, a table UUID and location, every schema and partition spec used so far with the current ones marked, sort orders, the last assigned column ID and sequence number, table properties, the list of snapshots with the path to each manifest list, named branches and tags, and logs of earlier snapshots and metadata files. Each change writes a new file, and the catalog points at the latest one.

Loading this one file tells an engine how to read the table without listing storage. Because it carries every retained snapshot, it grows on busy tables and slows commits. Expiring snapshots keeps the file small, while cleaning old metadata files only stops them piling up in storage. The metadata tables expose much of the same information through SQL, as below.

SELECT timestamp, file, latest_schema_id, latest_sequence_number
FROM demo.shop.orders.metadata_log_entries
ORDER BY timestamp DESC LIMIT 3;
183. How does Iceberg scale on object storage?

Iceberg scales on object storage by avoiding the operations that object stores do badly, mainly directory listing and rename, and by reading only the files a query needs.

Manifests name every data file, so planning does not list prefixes, and files are never modified in place. A commit is an atomic pointer change in the catalog instead of a rename of output directories. Partition values and column bounds in metadata skip files before any is opened, and large tables can have manifests planned across the cluster. Because paths come from metadata, files need not share a directory prefix: write.object-storage.enabled adds hashed prefixes that spread requests and reduce throttling.

Scale still depends on upkeep. Millions of small files, thousands of manifests, delete files that are never compacted and very frequent commits all slow planning and raise request costs. Cluster data to match queries, compact and expire regularly, and watch the metadata as the table grows.

184. How do you use Iceberg on AWS?

On AWS, Iceberg tables usually keep their files in S3 and are registered in the AWS Glue Data Catalog, with EMR, Glue jobs, Athena or other engines doing the work.

The iceberg-aws module provides the Glue catalog and S3FileIO, which the project recommends over the S3A file system for S3 access. Athena can read, write and optimise Iceberg tables, EMR runs Spark, Flink, Hive or Trino with them, Glue jobs read and write them, Redshift can query tables in the Glue catalog and Data Firehose can deliver streams into them. DynamoDB and JDBC catalogs are alternatives.

Glue is the easiest choice for a platform already using these services. Service features and supported format versions differ, so check each one you rely on, give identities access to only the table locations they need, and plan for S3 request throttling. The Spark runtime jar does not include the AWS SDK, so add iceberg-aws-bundle unless your platform provides it. A Spark catalog is configured like this.

spark.sql.catalog.prod                = org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.prod.type           = glue
spark.sql.catalog.prod.io-impl        = org.apache.iceberg.aws.s3.S3FileIO
spark.sql.catalog.prod.warehouse      = s3://my-bucket/warehouse
185. What programmatic APIs does Iceberg provide?

Iceberg provides a Java API, which is the core library that engines build on, and implementations in other languages such as the Python library PyIceberg.

Through the Java Table interface you can read the schema, partition spec, properties and snapshots, plan scans with filters, change schema or partitioning, add and remove files and group changes in a transaction. Maintenance is also available as actions. PyIceberg loads tables from a catalog, scans them into Arrow, appends, overwrites, deletes and upserts, and inspects metadata, without a Spark cluster.

Use SQL in an engine for ordinary data work and the APIs for platform tooling, custom ingestion or automation. Libraries differ in which format versions and delete types they support, so check your release. Low-level file operations are powerful enough to damage a table, for example by registering files that do not match the schema.

from pyiceberg.catalog import load_catalog
table = load_catalog("prod").load_table("shop.orders")
rows = table.scan(row_filter="status = 'PAID'",
                  selected_fields=("order_id", "amount")).to_arrow()
186. How do Presto and Trino work with Iceberg?

Presto and Trino each have an Iceberg connector that resolves tables through a catalog, plans queries from Iceberg metadata and can write as well as read.

Trino works with Hive Metastore, Glue, JDBC, REST, Nessie and Snowflake catalogs, the Snowflake one for reading only. Presto offers Hive, Nessie, REST and Hadoop catalog types, and reaches Glue through the Hive type with a Glue metastore. Both can create tables, insert data, run row-level changes and perform table maintenance, each with its own syntax and limits.

They are a common choice for interactive SQL on tables that Spark or Flink maintain. Their syntax differs from Spark’s procedures, and support for newer format versions arrives at a different pace; Trino describes version 3 support as experimental. Point every engine at the same catalog, and test deletes and types across them. Typical Trino maintenance looks like this.

ALTER TABLE orders EXECUTE optimize(file_size_threshold => '128MB');
ALTER TABLE orders EXECUTE expire_snapshots(retention_threshold => '7d');
SELECT * FROM "orders$snapshots";
187. How do you use Iceberg with Databricks?

Databricks works with Iceberg mainly through Unity Catalog, as managed Iceberg tables, as foreign tables read from another catalog, or as Delta tables that Iceberg clients can read.

A managed Iceberg table is created with USING iceberg; without that clause the table is Delta. Databricks maintains it, and external engines can read and write it through the Iceberg REST endpoint. Foreign tables registered from catalogs such as AWS Glue are generally read only and need a refresh to see new snapshots. Iceberg reads, built on UniForm, generates Iceberg metadata for a Delta table so that Iceberg clients can read it.

The choice decides who can write. Limits apply: for example, Iceberg reads for format version 2 cannot be combined with deletion vectors, while version 3 handles them differently, and some types and partition expressions are unsupported on managed tables. These change often, so check current Databricks documentation.

CREATE TABLE main.shop.orders (order_id BIGINT, amount DECIMAL(10,2))
USING iceberg;

Key takeaways

  • The tree explains the behaviour. Planning, time travel, concurrency and cleanup all follow from immutable metadata levels under one pointer.
  • A commit is optimistic. Losing the swap is retryable; failing validation is not; an unknown outcome must be checked.
  • Writes create maintenance. Compaction, delete cleanup, snapshot expiry and orphan removal each solve a different problem.
  • Support is per engine. A feature in the spec is usable only when every engine on the table implements it.
  • In scenarios, measure first. Name the metadata table or plan you would inspect before the fix.
