Apache Iceberg 1.12.0 came out on 30 September 2026 with 777 commits from 142 contributors. The new parts are geospatial types, a second clustering curve, a Flink task that turns equality deletes into deletion vectors, and a pile of format v4 groundwork. The part that will actually ruin a Monday is what it removes: Spark 3.4 and Flink 2.0 support, writing position deletes with row data, and the old S3 signer classes.

This guide covers what’s new, what breaks, and the order I’d upgrade from 1.11 in. The Spark behaviour below was checked on Spark 4.1.4 with iceberg-spark-runtime-4.1_2.13:1.12.0, and the versions come from the release’s build files and Maven Central.

Image 1: Iceberg 1.12.0 in numbers, and what lands in the release.

Key takeaways

  • Geospatial types (geometry and geography) are real column types, stored as WKB. They need a newer table format version, and Spark maps its own geospatial types onto them.
  • Hilbert-curve clustering joins Z-order as a rewrite_data_files sort strategy. In a test here the two came out about even, so measure before you switch.
  • Flink gains a maintenance task that converts equality deletes to deletion vectors, which cuts read cost for upsert pipelines.
  • Format version 4 plumbing is everywhere in the code, but v4 isn’t production-ready. The property is accepted without an error, so nothing stops you from setting it. Don’t.
  • Breaking: Spark 3.4 and Flink 2.0 support are removed, position deletes with row data can’t be written any more, and the old S3 signer classes are gone.
  • Apache Iceberg 1.12.0 for Java and Iceberg Rust 0.11.0 are separate releases. Validate Rust encryption, Variant, v3 scans and REST API changes on their own.
  • Upgrade by table behaviour, not by dependency file. The PDWR and Spark 3.4 changes need a plan before you bump.

Glossary

Term Meaning
PDWR Position deletes with row data: a position-delete file that also stores the deleted row
Deletion vector (DV) A compact bitmap of deleted row positions, stored in a Puffin file, from format v3
Equality delete A delete that names column values, not file positions. Cheap to write, costly to read
WKB Well-Known Binary, the encoding Iceberg uses for geometry and geography values
Space-filling curve A way to order multi-column values so that nearby rows land in the same files

1. What’s new in 1.12.0

1.1 Geospatial types arrive

Image 2: Geometry and geography are stored as WKB and need a v3 table.

Iceberg now has geometry and geography as proper types, stored as WKB (Well-Known Binary). Avro and Parquet both read and write them with self-describing logical types. The Spark 4.1 module maps Spark’s geospatial types onto them, and the release adds tests for geometry and geography DML.

Until now, spatial data in Iceberg meant a binary or string column and a convention your team had to remember. With a real type, engines and catalogs know what the column holds. If you store locations, that’s worth having.

Two things trip people up. The types need a format v3 table, and a v2 table rejects the schema with Invalid type for g: geometry(OGC:CRS84) is not supported until v3. Spark 4.1 also keeps geospatial behind its own setting, spark.sql.geospatial.enabled, and without it CREATE TABLE fails with UNSUPPORTED_FEATURE.GEOSPATIAL_DISABLED. With both in place, this works on Spark 4.1.4:

SET spark.sql.geospatial.enabled=true;
CREATE TABLE c.db.geo (id INT, g GEOMETRY(4326)) USING iceberg
TBLPROPERTIES ('format-version' = '3');
-- DESCRIBE shows g as geometry(4326)

Image 3: The two errors you can hit on the way to a working geometry column. Which one you see first depends on which setting you missed.

There are no ST_* functions in Spark 4.1, so you can’t write values from plain SQL. The data has to come in through a source that already produces the geospatial types.

One behaviour change to watch. GeometryType and GeographyType now put the resolved CRS (Coordinate Reference System) and edge algorithm in their toString() output. A plain geometry prints as geometry(OGC:CRS84) and a geography as geography(OGC:CRS84, spherical), so tests that compare type strings may need updating. The community kept the change on purpose: two equal types printing differently looked like a bug, and function IDs built from parameter type strings would have treated them as different overloads.

1.2 Hilbert clustering alongside Z-order

Image 4: Hilbert is a second curve for rewrite_data_files, with no options of its own.

rewrite_data_files gets a second space-filling curve. Z-order is still there, and you can now cluster on a Hilbert curve instead. The pitch for Hilbert is that it tends to keep nearby values closer together, which should give tighter file-level min/max statistics when you filter on several columns at once.

-- Existing: Z-order clustering
CALL my_catalog.system.rewrite_data_files(
  table => 'db.events',
  strategy => 'sort',
  sort_order => 'zorder(device_id, event_ts)'
);

-- New in 1.12: Hilbert curve clustering
CALL my_catalog.system.rewrite_data_files(
  table => 'db.events',
  strategy => 'sort',
  sort_order => 'hilbert(device_id, event_ts)'
);

The details that matter:

  • hilbert() has no options of its own. Each column contributes its full 8-byte primitive width to the index, so Z-order knobs like var-length-contribution and max-output-size do not apply.
  • You cannot combine hilbert() with zorder() in the same sort order.
  • Don’t assume Hilbert wins. Benchmark it on your real query patterns before switching.

Both limits show up as errors. On a table with four small files, hilbert(device_id, event_ts) compacted 8 data files into 1 with all 2,000 rows intact. The two things you can’t do fail like this:

Cannot mix Zorder and Hilbert sort expressions: zorder(device_id), hilbert(event_ts)
Cannot use options [max-output-size], they are not supported by the action or the rewriter HILBERT

To compare layouts, count the files whose min/max bounds can match a filter, using the files metadata table:

SELECT count(*) AS files,
  sum(CASE WHEN readable_metrics.device_id.upper_bound >= 100
            AND readable_metrics.device_id.lower_bound <= 119
            AND readable_metrics.event_ts.upper_bound >= timestamp_seconds(1700300000)
            AND readable_metrics.event_ts.lower_bound <= timestamp_seconds(1700400000)
           THEN 1 ELSE 0 END) AS files_that_can_match
FROM my_catalog.db.events.files;

The test table held 400,000 rows with a random device_id (0 to 999) and a random event_ts. Unsorted, all 15 files could match. After a zorder(device_id, event_ts) rewrite 3 of 20 files could, and after hilbert(device_id, event_ts) 2 or 3 of 20 could, depending on the run. The file count rose from 15 to 20 because the rewrite split the data at the target size, so read the figures as “files a reader must open”, not as a ratio. A one-file difference is noise. On this data the two orderings landed close together, so treat the Hilbert pitch above as a reason to test, not a promise.

Image 5: Both curves cut the files a reader opens from 15 to about 3, and they land within a file of each other.

A table that is already one well-sized file is skipped by both snippets above: a run on a single 5,000-row file reported 0 rewritten files. Pass options => map('rewrite-all', 'true') when the point of the run is the new layout.

1.3 Flink: equality deletes become deletion vectors

Image 6: Equality deletes are converted into deletion vectors off the read path.

For streaming teams this is probably the most useful change in the release. A Flink upsert pipeline writes equality deletes, which are cheap to write and expensive to read, because every reader has to match them against the data files. The new ConvertEqualityDeletes maintenance task rewrites those into row-position deletion vectors (DVs), and readers apply a DV with a cheap bitmap check.

Here’s the flow. The Flink IcebergSink writes data files and equality deletes to a staging branch. The converter resolves the deletes and commits the data files plus DVs to the target branch, usually main.

// Flink TableMaintenance, Iceberg 1.12
.add(ConvertEqualityDeletes.builder()
    .stagingBranch("staging")
    .equalityFieldColumns(ImmutableList.of("id"))
    .scheduleOnEqDeleteFileCount(10)
    .parallelism(4))

The catches:

  • The table must be format version 3 or higher.
  • Row lineage isn’t supported yet.
  • equalityFieldColumns must match the columns your writer uses.
  • The task keeps a primary-key index in Flink state, and RocksDB is the recommended backend. That index is the real cost: state grows with the number of live keys, so size it before you turn this on for a big table.
  • Keep other continuous writers off the target branch, or the conversion keeps losing the commit race.

1.4 Format v4 groundwork

Image 7: v4 is groundwork. v3 is where deletion vectors, variant and geospatial types live.

There’s a lot of code labelled v4 in 1.12, but format version 4 is not ready for production tables. Think of it as groundwork that shows where the format is heading.

What’s in the code:

  • Relative paths in the evolving specification, and utilities for converting absolute locations to relative ones. This can make table metadata less tied to one bucket or storage prefix.
  • Parquet or Avro manifests instead of Avro only, which can bring richer types and reader tooling to manifest data.
  • Content-statistics structures and filters, carrying structured index and average-size information alongside tracked files.
  • Tracked-file builders and adapters, plus a v4 manifest reader.
  • A draft Mumbling Bitmap specification and a read-only implementation.
  • EntryStatus.MODIFIED and TrackingBuilder status derivation, for changes that don’t fit the older added, existing and deleted model.

What not to do:

  • Don’t set format-version=4 on production tables. Nothing stops you: on Spark 4.1.4, CREATE TABLE ... TBLPROPERTIES ('format-version'='4') succeeds and SHOW TBLPROPERTIES reports 4.
  • Don’t write application code that parses v4 structures.
  • Don’t build a roadmap around draft field names.

What you can do today is keep assumptions about table location and metadata layout out of your application code, and follow the specification through later releases.

1.5 Variant, v3 interoperability, and encryption

1.12 fills in more engine paths for v3 features. Spark gets vectorized Parquet reads for Variant, and Flink, Kafka Connect and the generic record writers get Variant shredding paths. Java also tightens its v3 support for geometry and geography, row lineage, deletion vectors and encrypted metadata.

None of that helps unless every client touching the table can read it. A table that opens fine in one engine tells you nothing about whether another engine handles every feature inside it. Before you enable a v3 feature, test the real writer and reader pairs in your stack, including schema evolution, nulls, decimal edge cases and failure recovery. And don’t bundle the table format upgrade with the library upgrade, or a failure will have two suspects.

1.6 Scan planning, metrics, and maintenance

The quieter changes may save you more time than the headline ones.

  • Partition-statistics scans can now project columns and apply filters, so an optimizer reads less metadata.
  • Snapshot expiration now reads delete manifests correctly in cases where it used to get them wrong.
  • A scan-based action removes dangling delete files.
  • RESTMetricsReporter.report() no longer blocks the calling thread, so reporting metrics can’t stall the work being measured. Still watch queue size, delivery failures and dropped reports.
  • Adaptive split-sizing options are now documented, which makes it easier to trade planning overhead against parallelism.

Reader and file-format fixes cover Arrow integer-to-long promotion, dictionary-encoded INT96 timestamps with offsets, large decimals, decimal default values, end-of-file handling in object-store streams, Parquet row-group size tracking, and faster decimal handling that avoids unnecessary BigInteger conversions.

1.7 Kafka Connect stops hiding failures

The big change here is a simple one: commit failures are reported instead of silently swallowed.

  • There’s a new metric for partial commit failures.
  • Transient commit exceptions get a bounded number of retries.
  • Some rebalance scenarios used to commit files from a previous attempt, and that’s fixed.
  • Control-topic offsets are tracked as a high-water mark.

Schema and conversion fixes cover null-valued records after a schema change, UUID conversion from Avro, decimal inference, MongoDB timestamp and date arrays, and Variant shredding. Deprecated members were removed from TableReference and IcebergWriterResult, so custom transforms or extensions may stop compiling.

1.8 REST catalog: protocol and operational changes

Image 8: The REST contract grows, and both clients have to agree with the server.

The REST catalog contract grows in 1.12. The OpenAPI model adds table-unregister and function list and load endpoints, Variant types, catalog object identifiers, labels and remote-signing configuration. Path segments now use RFC 3986 percent-encoding, which fixes namespaces and object names with reserved characters. Spark can also hand DROP TABLE PURGE to the REST catalog, so the server decides how storage gets deleted.

That touches both compatibility and day-to-day operations:

  • Check capability negotiation. Confirm that your catalog server, and any proxy in front of it, implement the endpoints and request and response shapes your Java or Rust client needs. A product name or version string doesn’t prove it.
  • Test names end to end. Push reserved characters through client, proxy and server. If one of them decodes differently, you can hit the wrong object or lose access to the right one.
  • Review authorization. Test permissions for unregister, function metadata, remote signing and purge delegation.
  • Define deletion ownership. Unregister drops the catalog entry and leaves the files; purge asks for the files to be deleted. Write down the table’s metadata location and a recovery procedure before you run either.
  • Drill purge failures. See what happens when storage deletion is denied, half succeeds or times out. Does the table stay registered, can the cleanup be retried, and where is it audited?
  • Check authentication refresh. Exercise OAuth token refresh, SigV4 or assumed-role signing, and retries against your real catalog.

If you run both Java 1.12.0 and Rust 0.11.0 clients, test both against the same catalog. Separate release numbers don’t mean identical REST support.

1.9 Security and supply-chain work

  • The project published an Iceberg security model describing trust boundaries across catalogs, clients, storage, credentials, and metadata.
  • CI now blocks on vulnerability scanning for relevant pull requests.
  • Jackson versions were aligned and updated to address reported vulnerabilities.
  • OAuth token refresh keeps optional parameters during non-exchange refreshes.
  • AWS REST signing can use assumed-role credentials.
  • RemoteSigningConfig implements the formalized remote signing spec, and old S3 signer classes are removed.

Bumping a library doesn’t secure a deployment. Use the security model to ask who can change catalog metadata, who can request temporary storage credentials, who can delete files, where tokens get cached, and whether your audit trail ties a catalog action to the object-store action it caused.

2. Apache Iceberg 1.12.0 for Java and Iceberg Rust 0.11.0

Don’t read these two version numbers as one library. Iceberg Java 1.12.0 and Iceberg Rust 0.11.0 are companion releases with their own artifacts, APIs and feature coverage. Upgrade them separately, then test them against each other wherever they share a catalog or table. The Rust side adds end-to-end table encryption, better v3 reads, Variant support, row-lineage metadata and REST catalog changes. If you have Rust readers or writers, those close real cross-engine gaps, but read the final release artifacts and changelog before you rely on them.

The Rust changes to review:

  • Encryption: Rust reads and writes encrypted data, manifests, manifest lists, and Puffin files, with AES-256 support and a KMS factory integration. Test encrypted files written by Rust against Java readers and the other way round, including key rotation and missing-key failures.
  • V3 scans: Rust can now decode and apply deletion vectors, and adds Variant support, row-lineage metadata columns and more metadata columns. Test tables that use each feature with your real catalog, storage and other engines.
  • REST authentication: the AuthManager / AuthSession API changes authentication setup. Review OAuth2 and SigV4 configuration and confirm the client respects endpoints advertised by GET /v1/config.
  • API and behaviour changes: lazy table-property parsing, validated FileScanTask construction, write.metadata.path and the GCS host property change. Rebuild downstream Rust applications and integration crates.
  • DataFusion: check which DataFusion version line the Rust release needs. The integration has its own release cycle.

The rule that matters is cross-engine testing. Anything the Rust writer accepts has to be readable by every Java, Spark, Flink and query-engine client on that table, and the reverse. Test both directions before you turn new table features on in production.

3. Breaking changes

Send this section to whoever owns your Spark and Flink jobs. These removals break code, they don’t just deprecate it.

Image 9: What 1.12.0 removes.

3.1 Spark 3.4 and Flink 2.0 support removed

PR #14122 removes the Spark 3.4 runtime entirely. The 1.12.0 Java artifacts support Spark 3.5, 4.0 and 4.1, built against Spark 3.5.9, 4.0.4 and 4.1.3. Spark 4.2 isn’t in the source or binary artifacts, even though its module exists on the project’s main branch.

Flink 2.0 goes too. 1.12 adds Flink 2.2 and 2.3 and keeps 1.20 and 2.1. List your batch and streaming jobs, then test the exact Flink and Iceberg pair. For stateful jobs that means savepoint restore, checkpoint recovery, serializers and commit behaviour, and a clean compile isn’t enough.

3.2 Position deletes with row data (PDWR) cannot be written

PR #17706 removes the feature the community deprecated in 1.11. The rewrite_position_delete_files and rewrite_table_path actions now fail with an explicit exception on files that still carry row data.

That’s deliberate. At the August 26 sync the group agreed that table owners should decide what happens to existing PDWR, instead of a maintenance job quietly dropping the row column.

3.3 Deprecated methods removed

  • Deprecated SparkTableUtil methods in Spark 4.0 and 4.1 are removed.
  • SparkFilters is deprecated in favour of SparkV2Filters.

3.4 Old S3 signer classes removed

PR #17627 drops the deprecated AWS signer classes and properties. The new RemoteSigningConfig follows the formal remote signing spec.

4. Migrating from 1.11 to 1.12

Upgrade by table behaviour, not by dependency file. This sequence catches the failures a basic smoke test is most likely to miss.

4.1 Pre-upgrade inventory

Before you touch anything, build an inventory of engines and features:

Item What to record
Engine clients Every Spark, Flink, Kafka Connect, Python, Rust, query-engine, and maintenance client that touches each catalog
Runtime versions Spark, Flink, and other engine versions in use; flag Spark 3.4 and Flink 2.0
Iceberg library versions Current version on each client; track Java and Rust release tracks independently
Client feature support Which readers/writers support Variant, deletion vectors, row lineage, geo types, and encryption
Catalog client REST, Hive, Glue, JDBC, Nessie, or other
Authentication method OAuth2, SigV4, assumed-role, or other
REST catalog behaviour Supported endpoints, path encoding, unregister/purge semantics, and server/client versions
File I/O implementation S3, GCS, ADLS, HDFS, or other
Table format versions V1, V2, V3 for each table
Delete-file strategies Copy-on-write vs merge-on-read; position vs equality deletes

The inventory tells you which of the breaking changes actually apply to you.

4.2 Position deletes with row data (PDWR)

If you still have V2 tables whose position deletes carry row data, your maintenance jobs will start failing after the upgrade. There are two ways out.

Image 10: Two ways out for tables that still carry position deletes with row data.

Image 11: A v2 table writes a Parquet position-delete file, and a v3 table writes a Puffin deletion vector.

The figure comes from deleting 10 rows (id < 10) from a 1,000-row merge-on-read table in each format. delete_files listed one PARQUET file with record_count 10 on v2 and one PUFFIN file with record_count 10 on v3. On v3 the position_deletes table also shows content_offset 4 and content_size_in_bytes 39, the byte range of the bitmap inside the Puffin file. After a v2 table was upgraded to v3, its old Parquet delete file stayed where it was, and the next DELETE added a Puffin file next to it.

Option A: upgrade to V3 and rewrite as deletion vectors.

-- Upgrade table format version
ALTER TABLE prod.db.trips SET TBLPROPERTIES ('format-version' = '3');

-- Rewrite the position delete files into deletion vectors
CALL prod.system.rewrite_position_delete_files(
  table => 'db.trips',
  options => map('rewrite-all', 'true')
);

The option matters. On a v2 table with three deleted rows that was upgraded to v3, the plain call rewrote nothing, because it waits for a minimum number of input files. With rewrite-all it rewrote one delete file into one new one, and delete_files then listed a single PUFFIN file holding the 3 deleted rows.

This path is one-way. On 1.12.0, ALTER TABLE ... SET TBLPROPERTIES ('format-version'='2') on a v3 table fails with Unsupported table change: Cannot downgrade v3 table to v2, and a reader that only understands v2 can’t read a v3 table. Check every reader and writer first, not after.

Option B: stay on V2 and let data compaction fold those deletes into data files.

-- Run data compaction so the deletes are applied to the data files
CALL prod.system.rewrite_data_files(
  table => 'db.trips',
  options => map('delete-file-threshold', '1', 'remove-dangling-deletes', 'true')
);

Without delete-file-threshold, a table with only a few delete files isn’t picked up. With it, the compaction rewrote the data files and the table still returned the right 7 rows.

remove-dangling-deletes is a separate option. It drops delete files that no longer point at any live data file, which is what compaction leaves behind. Without it the old position-delete file stayed in delete_files after the rewrite, so an unchanged file count there isn’t a failure. Check the row count first. In a separate run on a 1,000-row v2 table with 10 rows deleted, the same call rewrote 2 data files into 1, and with remove-dangling-deletes it reported removed_delete_files_count 1, left delete_files empty and kept 990 rows.

Image 12: Without remove-dangling-deletes the old delete file stays in delete_files; with it the file is removed.

Pick one before you upgrade. Finding out after the first failed job is the expensive way.

How to find affected tables:

-- Query position deletes across tables to find PDWR
SELECT * FROM prod.db.trips.position_deletes LIMIT 10;
-- If the row column is populated, this table has PDWR.
-- On 1.12 a delete written by Spark leaves row as NULL.

4.3 Spark 3.4 and Flink 2.0 migration

If any job runs Spark 3.4 or Flink 2.0, move it to a supported runtime before you upgrade that integration to Iceberg 1.12.0. The supported Flink lines are 1.20, 2.1, 2.2 and 2.3.

The path:

  1. Move Spark 3.4 jobs to Spark 3.5.x first (3.5.9 is the 1.12.0 baseline), and Flink 2.0 jobs to a supported Flink line.
  2. Run engine and state-recovery tests on the new runtime.
  3. Only then upgrade the Iceberg integration to 1.12.0.

If you’re on Spark 4.2, stay on Iceberg 1.11.x until a later release ships official 4.2 artifacts. And don’t pretend Flink 2.0 is supported by swapping in a neighbouring runtime jar.

4.4 Deprecated API removals

Search your codebase for:

  • SparkTableUtil method calls in Spark 4.0 and 4.1 projects
  • SparkFilters usage (replace with SparkV2Filters)
  • Any code referencing removed S3 signer classes or properties

These fail at compile time, so a full build catches them.

4.5 Testing checklist

Once staging is upgraded, run these:

Test area Why it matters
Arrow integer-to-long promotion Fixed in 1.12; verify with affected types
Dictionary-encoded INT96 timestamps with offsets Fixed in 1.12
Large decimals Fixed in 1.12
Decimal default values Fixed in 1.12
End-of-file handling in object-store streams Fixed in 1.12
Parquet row-group size tracking Fixed in 1.12
Kafka Connect commit failures Force a catalog commit failure and confirm it is reported
Kafka Connect rebalance Trigger a task rebalance during a pending commit
Kafka Connect restart Restart from a known control-topic offset
Geospatial types (if used) Verify the toString() change doesn’t break tests

For Rust clients, compile against the target release and test REST authentication, metadata paths, GCS configuration, encrypted-file interoperability and v3 scans. For every shared table, check that each active client can read everything the others write.

The Kafka Connect rows are the drills the release notes recommend. Run all three, and confirm the connector reports the failure, doesn’t duplicate table data, and resumes from the right point.

4.6 Check every artifact before you bump

Iceberg runtimes are built per engine version, so the jar for your engine might not exist for 1.12.0. List the artifacts your jobs use and ask Maven Central, so you find the gap before the cluster does.

import urllib.request

ARTIFACTS = [
    "iceberg-spark-runtime-3.5_2.12", "iceberg-spark-runtime-4.0_2.13", "iceberg-spark-runtime-4.1_2.13",
    "iceberg-spark-runtime-4.2_2.13", "iceberg-flink-runtime-2.0", "iceberg-flink-runtime-2.3",
]
VERSION = "1.12.0"

for a in ARTIFACTS:
    url = f"https://repo1.maven.org/maven2/org/apache/iceberg/{a}/{VERSION}/{a}-{VERSION}.pom"
    try:
        urllib.request.urlopen(url, timeout=10)
        print(f"OK       {a}:{VERSION}")
    except Exception:
        print(f"MISSING  {a}  -> no {VERSION} build published")

The output:

OK       iceberg-spark-runtime-3.5_2.12:1.12.0
OK       iceberg-spark-runtime-4.0_2.13:1.12.0
OK       iceberg-spark-runtime-4.1_2.13:1.12.0
MISSING  iceberg-spark-runtime-4.2_2.13  -> no 1.12.0 build published
MISSING  iceberg-flink-runtime-2.0  -> no 1.12.0 build published
OK       iceberg-flink-runtime-2.3:1.12.0

That agrees with the breaking-changes section: there’s no Spark 4.2 or Flink 2.0 runtime for 1.12.0, and the last Spark 3.4 runtime is 1.11.0.

5. Upgrade sequence in one page

Image 13: The upgrade sequence on one page.

The order: record the engines, clients and table formats you have, settle the PDWR plan for every v2 table that carries them, move the Spark 3.4 and Flink 2.0 jobs to a supported runtime and test state recovery there, run the artifact check, bump Iceberg and run the staging tests, and finish with the Kafka Connect failure drills at the end of that checklist.

Frequently Asked Questions

What is new in Apache Iceberg 1.12.0?

Geospatial types, Hilbert clustering for rewrite_data_files, a Flink task that converts equality deletes to deletion vectors, REST catalog additions, Kafka Connect commit-failure reporting, and format v4 groundwork. It was released on 30 September 2026.

What breaks when I upgrade from 1.11?

Spark 3.4 and Flink 2.0 support is removed, position deletes with row data can no longer be written, the old S3 signer classes are gone, and some deprecated SparkTableUtil methods are removed. The API removals fail at compile time, and the PDWR change fails maintenance jobs.

Can I use geometry and geography types on Spark 4.1?

Yes, on a format v3 table with spark.sql.geospatial.enabled set. A v2 table rejects the column, and Spark 4.1 has no ST_* functions, so you can’t write values from SQL.

Can I use Iceberg 1.12.0 with Spark 4.2?

Not yet. No iceberg-spark-runtime-4.2_2.13 artifact exists for 1.12.0, so stay on 1.11.x for Spark 4.2.

Why did rewrite_position_delete_files do nothing?

It waits for a minimum number of input files before it does anything. Pass options => map('rewrite-all', 'true') to rewrite every delete file, for example to turn position deletes into a deletion vector after moving a table to v3.

Is format version 4 usable?

No. The code is there but the format isn’t ready, and Iceberg won’t stop you from setting format-version=4. Keep production tables on v2 or v3.

Can I mix zorder and hilbert in one sort order?

No. It fails with Cannot mix Zorder and Hilbert sort expressions, and hilbert() takes no options.

Do Java 1.12.0 and Rust 0.11.0 need to be upgraded together?

No, they are separate releases with their own APIs. Upgrade them one at a time, then test both against any table or catalog they share.

Summary

Plan around the removals first, because they’re what fails jobs: Spark 3.4, Flink 2.0, PDWR and the old S3 signers. Java 1.12.0 and Rust 0.11.0 are separate releases, so upgrade each client on its own and test shared tables and the REST catalog across both.

Geospatial types are worth a trial if you store locations. Hilbert clustering is worth measuring: in the one test here it came out about even with Z-order. Flink’s equality-delete conversion is worth a look for upsert pipelines, as long as you can pay for the state. The v4 code is worth reading and not using: relative paths, Parquet manifests and content statistics show where the format is going, and format-version=4 on a production table isn’t a supported path.
