TL;DR

  • Four minor releases in about seventeen months, each with its own centre of gravity: a break with the past and a far more expressive SQL (4.0), pipelines and procedural SQL (4.1), new data types and joins (4.2), stateful low-latency streaming and history tracking (4.3).
  • About eight features per release, each with what it is, why it exists, the syntax and the output of a real run on the release that introduced it.
  • Several headline features are off by default or need a connector. The text names the exact setting rather than implying they work out of the box.
  • Removals, default changes and upgrade risks are in the release history post.

A Spark release note lists hundreds of tickets, and most of them have nothing to do with the job you run on Monday. This post picks the features a data engineer meets in daily work across 4.0 to 4.3 and shows, for each, the syntax and what it printed when run.

Release Date Tickets resolved What the release note leads with
4.0.0 23 May 2025 over 5,100 Scala 2.13 and Java 17 as the baseline, ANSI mode on by default, VARIANT, SQL user-defined functions, session variables, pipe syntax, collations, a built-in XML source, a Python data source API, a lightweight Spark Connect client
4.1.0 16 Dec 2025 over 1,800 Spark Declarative Pipelines, Structured Streaming real-time mode, SQL scripting and VARIANT generally available, Arrow-native Python UDFs, recursive CTEs
4.2.0 14 Jul 2026 over 1,700 Geospatial types, change data capture, Arrow-optimized Python UDFs on by default, NEAREST BY joins, SQL path resolution, metric views
4.3.0 30 Oct 2026 over 1,100 Stateful real-time mode, SCD Type 2 in Auto CDC, JSON_TABLE, ASOF JOIN, VARIANT editing functions, faster queries on small data

The last gap is half the size of the first two, and 4.3.0 shipped with no preview builds.

That last point matters when you pick a release. 4.0, 4.1 and 4.2 went through two, four and five preview builds. 4.3.0 had none (no 4.3.0-preview exists on Maven Central or the Apache archive), so it has had the least outside testing, and the patch releases that follow it are where the first corrections will land.

Every example ran on the release that introduced the feature, on an official Docker image and, for the SQL and Scala examples, on the plain release tarball too. The setup is in Run every example yourself. Where a feature needed a flag, a connector or a second tool to run at all, that feature’s section says so.

Three shifts behind the features

Read the four release notes in order and they look like four unrelated lists. Read them as one line and three decisions run through all of them, which is also why some features arrive in pieces over two or three releases.

Each lane is one shift; each box is what that release added to it.

SQL becomes the main surface again

For a decade the work went into the DataFrame API. The fourth line turns back to SQL and adds constructs that other SQL engines have and Spark did not.

Capability 4.0 4.1 4.2 4.3
New query syntax Pipe syntax (SPARK-49555) Recursive CTEs (SPARK-24497), query parameter markers anywhere (SPARK-53573) QUALIFY (SPARK-31561), NEAREST BY join (SPARK-56395) ASOF JOIN (SPARK-58092), JSON_TABLE (SPARK-58366), UNNEST in FROM (SPARK-58419)
Procedural SQL Session variables (SPARK-42849), SQL user-defined functions (SPARK-46057) SQL scripting, enabled by default (SPARK-54499) Cursors in scripting (SPARK-54759) none in the headlines
Data types VARIANT (SPARK-45827), string collations (SPARK-46830) VARIANT generally available (SPARK-54454) GEOMETRY and GEOGRAPHY (SPARK-51658) VARIANT editing functions (SPARK-57804), nanosecond timestamps in preview (SPARK-56876)
Name resolution none none SET PATH and CURRENT_PATH() (SPARK-54806, behind a flag) none

Teams used to write logic in Python or Scala because SQL could not express it, and paid for it in code analysts could not read and the optimiser could not see through. Putting the constructs into the language fixes that. The cost is that each one is another thing the parser, analyzer and optimiser must keep correct, and several arrive behind a flag first.

Batch and streaming converge on one declarative layer

Streaming and batch meet in one declarative layer, and the streaming side gets a second, lower-latency mode.

Capability 4.0 4.1 4.2 4.3
Pipelines none Spark Declarative Pipelines (SPARK-51727) Auto CDC, SCD Type 1 (SPARK-56249) Auto CDC, SCD Type 2 (SPARK-58321 and others)
Change data none none CHANGES clause and DataFrame APIs for row-level changes (SPARK-55668) consumed by Auto CDC SCD Type 2
Streaming latency Arbitrary state API v2, state data source Real-time mode, stateless (SPARK-53736) none in the headlines Real-time mode with state: aggregation, dropDuplicates, transformWithState (SPARK-58635 and others)
Writes none stored procedures API for catalogs (SPARK-44167) Data Source V2 transaction management (SPARK-55855) dynamic table options for UPDATE, MERGE, DELETE

A pipeline used to need an orchestrator for ordering, a streaming job for freshness and hand-written merge logic for change data, written in different dialects by different teams. Declaring the datasets and letting Spark derive the graph removes that, and the cost is that you hand the execution graph to the framework: when a run behaves oddly, the schedule is not code you wrote. An external orchestrator with micro-batch triggers is still the better fit for pipelines that mix many engines.

Python and Connect move off the JVM path

The client and the language runtime change shape, not just the API.

Capability 4.0 4.1 4.2 4.3
Spark Connect A lightweight Python client, ML over Connect JDBC driver for Connect (SPARK-53484), ML on Connect generally available for Python (SPARK-51236) RDD API compatibility (SPARK-55227) REST endpoints for sessions and operations (SPARK-57941), more complete JDBC driver
Python UDFs Python UDTFs, unified UDF profiling Arrow-native UDF and UDTF decorators (SPARK-52214, SPARK-52979) Arrow-optimized UDFs and Arrow IPC on by default (SPARK-54555) Python performance work
Python data Python Data Source API (SPARK-44076), plotting API (SPARK-49530) filter pushdown for Python data sources grouped-aggregation UDFs in Arrow and pandas none in the headlines
Small data none none none opt-in single-task execution and Arrow-native caching (SPARK-57851, SPARK-57268)

Python was the most used language and the slowest path through Spark, because every row crossed the JVM boundary through pickling, and a client that only talks to a server still needed a full PySpark install. The fix is Arrow end to end, a thin client (4.0 added a 1.5 MB pyspark-client), and a server reachable by JDBC and REST. A default that changes how data crosses the boundary changes behaviour at the edges, in types, nulls and timestamps, which is why 4.2 is the release to test on your own UDFs.

The features, release by release

Every entry has the same shape: what it is and why it exists, the syntax, a run, and a maturity tag.

Tag Meaning
Default Works with no configuration on the release that introduced it
GA, on by default Was experimental earlier and is now enabled and supported
Behind a flag Present, but off until you set a configuration
Preview The release note says so; syntax or behaviour can still change
Needs a connector The engine defines the syntax; a data source has to implement it

The last tag is the one that surprises people. A feature that exists in Spark SQL does not exist for your table until the connector for that table supports it, which is true of change data capture, data source transactions and several INSERT extensions.

Spark 4.0: the break, and a far more expressive SQL

All 4.0 examples ran on apache/spark:4.0.5-python3, which reports Scala 2.13 and Java 17. Those two facts are themselves the baseline change: Scala 2.12 and JDK 8 and 11 are gone, which is covered in the release history post.

ANSI mode on by default (SPARK-44444)

Maturity: Default.

Example in the repo: 01_ansi_mode.sql.

Before 4.0, an invalid cast returned NULL and a divide by zero returned NULL, silently. With ANSI mode on, both fail loudly, and the error message names the function that tolerates the bad value instead. Data you used to lose without noticing now stops the job.

SET spark.sql.ansi.enabled;          -- true

SELECT CAST('abc' AS INT);           -- [CAST_INVALID_INPUT] ... Use `try_cast` to tolerate malformed input
SELECT try_cast('abc' AS INT);       -- NULL
SELECT 1/0;                          -- [DIVIDE_BY_ZERO] ... Use `try_divide` to tolerate divisor being 0
SELECT try_divide(1, 0);             -- NULL

Watch for: this is the change most likely to turn a green pipeline red. Run your own data through it before the upgrade, and use the try_* functions where a NULL was the intended answer.

VARIANT, a type for JSON you do not want to schema

Maturity: Default in 4.0, generally available in 4.1.

Example in the repo: 02_variant.sql.

A VARIANT holds a semi-structured value, such as JSON, in an encoded binary form, so a query reads a path out of it without re-parsing text and without a fixed schema up front. The alternative is a STRING column and get_json_object on every read.

SELECT parse_json('{"a":1,"b":[1,2,3],"c":{"d":"x"}}') AS v;
-- {"a":1,"b":[1,2,3],"c":{"d":"x"}}

SELECT variant_get(parse_json('{"a":1,"b":[1,2,3]}'), '$.b[1]', 'int');   -- 2

SELECT schema_of_variant(parse_json('{"a":1,"b":[1,2,3]}'));
-- OBJECT<a: BIGINT, b: ARRAY<BIGINT>>

The v:field colon shorthand is not in 4.0. The same statement fails on 4.0.5 with PARSE_SYNTAX_ERROR ... at or near ':', and works from 4.1.

SQL pipe syntax (SPARK-49555)

Maturity: Default.

Example in the repo: 03_pipe_syntax.sql.

Pipe syntax lets a query read top to bottom, one step per |>, instead of inside-out. It is the same logical plan, written in the order you think it.

FROM orders
|> WHERE amount > 5
|> AGGREGATE sum(amount) AS total GROUP BY region
|> ORDER BY total DESC;
-- eu  40.0
-- us  20.0

FROM orders |> EXTEND amount * 2 AS doubled |> SELECT id, doubled |> LIMIT 2;
-- 1  20.0
-- 2  40.0

SQL user-defined functions (SPARK-46057)

Maturity: Default.

Example in the repo: 04_sql_udf.sql.

A function written in SQL, scalar or table-valued. Because it is SQL, the optimiser can see through it, which a Python or Scala UDF does not allow.

CREATE TEMPORARY FUNCTION add_tax(x DOUBLE) RETURNS DOUBLE RETURN x * 1.18;
SELECT id, add_tax(amount) AS gross FROM orders;        -- 1  11.799999999999999 ...

CREATE TEMPORARY FUNCTION big_orders(min_amt DOUBLE)
  RETURNS TABLE (id INT, amount DOUBLE)
  RETURN SELECT id, amount FROM orders WHERE amount >= min_amt;
SELECT * FROM big_orders(20.0);                          -- (2, 20.0), (3, 30.0)

Session variables (SPARK-42849)

Maturity: Default.

Example in the repo: 05_session_variables.sql.

A typed variable that lives for the session, set with DECLARE and SET VAR and usable anywhere an expression is. It is the typed alternative to splicing a value into SQL text.

DECLARE OR REPLACE VARIABLE threshold DOUBLE DEFAULT 15.0;
SELECT id FROM orders WHERE amount > threshold;          -- 2, 3

SET VAR threshold = 25.0;
SELECT id FROM orders WHERE amount > threshold;          -- 3

String collation (SPARK-46830)

Maturity: Default.

Example in the repo: 06_string_collation.sql.

A collation controls how strings compare and sort: case-insensitive, accent aware, by locale. Before collations, case-insensitive matching meant wrapping both sides in lower().

SELECT 'Apple' = 'apple';                                -- false
SELECT 'Apple' COLLATE UTF8_LCASE = 'apple';             -- true
SELECT collation('x' COLLATE UNICODE_CI);                -- SYSTEM.BUILTIN.UNICODE_CI

-- values: 'Ana', 'ana', 'ANA', 'Bob'
SELECT count(DISTINCT n COLLATE UTF8_LCASE) FROM names;  -- 2

The built-in XML data source (SPARK-44265)

Maturity: Default.

Example in the repo: 07_xml_functions.sql.

XML reads and writes without the old external package, plus from_xml, to_xml and schema_of_xml for XML held in a string column.

SELECT from_xml('<p><name>Ana</name><age>30</age></p>', 'name STRING, age INT');
-- {name: Ana, age: 30}

SELECT schema_of_xml('<p><name>Ana</name><age>30</age></p>');
-- STRUCT<age: BIGINT, name: STRING>

df = spark.read.format("xml").option("rowTag", "person").load("/tmp/xmlin")
# age: long, name: string  ->  (30, 'Ana'), (41, 'Bob')

The Python Data Source API and Python UDTFs (SPARK-44076)

Maturity: Default, but needs the pyarrow package.

Example in the repo: 09_python_data_source.py.

You can write a data source in plain Python, register it, and read it by name, including from SQL. A Python user-defined table function returns several rows per input row. On the official image both fail until pyarrow is installed: the Python data source worker raises ModuleNotFoundError: No module named 'pyarrow'.

from pyspark.sql.datasource import DataSource, DataSourceReader
from pyspark.sql.functions import udtf

class CounterDataSource(DataSource):
    @classmethod
    def name(cls): return "counter"
    def schema(self): return "n INT, square INT"
    def reader(self, schema): return CounterReader(self.options)

class CounterReader(DataSourceReader):
    def __init__(self, options): self.limit = int(options.get("limit", 3))
    def read(self, partition):
        for i in range(1, self.limit + 1):
            yield (i, i * i)

spark.dataSource.register(CounterDataSource)
spark.read.format("counter").option("limit", 4).load().show()
# n=1..4, square=1,4,9,16

@udtf(returnType="word: string, length: int")
class SplitWords:
    def eval(self, text: str):
        for w in text.split():
            yield (w, len(w))

spark.udtf.register("split_words", SplitWords)
spark.sql("SELECT * FROM split_words('spark four point zero')").show()
# spark 5, four 4, point 5, zero 4

Also in 4.0, not run here:

  • transformWithState for custom stateful processing in Scala, Java and Python, the state data source reader, and state store improvements such as SST file reuse
  • Polymorphic Python UDTFs whose output schema is decided at call time
  • Named and unnamed parameter markers for parameterized queries
  • Structured JSON logging, seen in every error the 4.0 runs logged
  • A 1.5 MB lightweight Python client, spark.api.mode to switch Connect on, and community Spark Connect clients for Go, Swift and Rust
  • Native Plotly-based plotting on PySpark DataFrames (SPARK-49530)
  • Java 21 support, the Spark Kubernetes operator (SPARK-45923), Spark ML on Connect, and unified PySpark UDF profiling

Spark 4.1: pipelines, procedural SQL, and real-time mode

The 4.1 examples ran on apache/spark:4.1.3-python3, apart from real-time mode, which used the playground’s Spark 4.1.3 image because it needs Kafka.

SQL scripting (SPARK-54499)

Maturity: GA, on by default (spark.sql.scripting.enabled is true).

Example in the repo: 01_sql_scripting.sql.

A script is a BEGIN ... END block with variables, loops, conditions and error handlers, run as one statement. It moves logic that lived in a Python driver into SQL that an analyst can read.

BEGIN
  DECLARE total INT DEFAULT 0;
  DECLARE i INT DEFAULT 1;
  WHILE i <= 5 DO
    SET total = total + i;
    SET i = i + 1;
  END WHILE;
  SELECT total, i;
END;
-- 15, 6

BEGIN
  DECLARE result DOUBLE DEFAULT 0;
  DECLARE EXIT HANDLER FOR DIVIDE_BY_ZERO
  BEGIN
    SET result = -1;
    SELECT 'caught divide by zero' AS status, result;
  END;
  SET result = 1 / 0;
  SELECT 'not reached' AS status, result;
END;
-- caught divide by zero, -1.0

BEGIN
  DECLARE msg STRING DEFAULT '';
  FOR r AS SELECT region, sum(amount) AS total FROM orders GROUP BY region ORDER BY region DO
    SET msg = msg || r.region || '=' || CAST(r.total AS STRING) || ' ';
  END FOR;
  SELECT trim(msg) AS summary;
END;
-- eu=40.0 us=25.0

A script returns the result of its last query, which is what spark.sql handed back in each run above.

Recursive common table expressions (SPARK-24497)

Maturity: Default.

Example in the repo: 02_recursive_cte.sql.

A CTE that refers to itself, for hierarchies and graph walks that used to need a loop in application code.

WITH RECURSIVE t(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM t WHERE n < 5
) SELECT n FROM t;
-- 1, 2, 3, 4, 5

A four-level org chart walked from the root (boss IS NULL) returned ceo 0, vp 1, dir 2, mgr 3, one row per level, by joining each employee to the previous level’s output.

VARIANT generally available, with colon paths (SPARK-54454, SPARK-52494)

Maturity: GA, on by default.

Example in the repo: 03_variant_colon_paths.sql.

4.1 declares VARIANT generally available and adds the v:path shorthand, with ::type to cast the result. The release also adds shredding for faster Parquet reads of variants; that part was not run here.

SELECT v:user::string AS user,
       v:tags[0]::string AS first_tag,
       schema_of_variant(v:n) AS n_type
FROM ev ORDER BY 1;
-- a  x     BIGINT
-- b  NULL  STRING

The n field is a number in one row and a string in the other, which a typed column could not hold, and schema_of_variant reports each row’s own type.

Smaller additions: sketches, parameter markers and Arrow UDFs

Maturity: Default. The Arrow UDFs need pyarrow.

Example in the repo: 04_sketch_functions.sql, 05_parameter_markers.py, 06_arrow_udf.py.

Sketch functions (SPARK-52515, SPARK-54199, SPARK-52407) are approximate aggregates that can be stored and merged: top-k frequent items, KLL quantile sketches and Theta set-cardinality sketches. A sketch column can be rolled up later without rereading the raw rows.

SELECT approx_top_k(page, 2) FROM clicks;
-- [{item: a, count: 3}, {item: b, count: 2}]

SELECT kll_sketch_get_quantile_bigint(kll_sketch_agg_bigint(ms), 0.5D) AS p50,
       kll_sketch_get_quantile_bigint(kll_sketch_agg_bigint(ms), 0.99D) AS p99
FROM lat;                      -- ms = 1..1000
-- 499, 989 on 4.1.3 (500, 990 on 4.1.4)

SELECT theta_sketch_estimate(theta_union_agg(s)) FROM (
  SELECT theta_sketch_agg(x) s FROM VALUES (1),(2),(3) AS a(x)
  UNION ALL
  SELECT theta_sketch_agg(x)   FROM VALUES (3),(4)   AS b(x));
-- 4

The exact median of 1 to 1000 is about 500 and the exact 99th percentile about 990. The sketch returned 499 and 989 on 4.1.3 and 500 and 990 on 4.1.4 for the same input, so assert a tolerance on sketch results in tests, not an exact value.

Parameter markers (SPARK-53573): :name markers used to work in a few expression positions. In 4.1 a pre-parser substitutes them nearly anywhere, including identifiers and inside scripts, so a value from application code never has to be spliced into the SQL text.

spark.sql("SELECT * FROM IDENTIFIER(:t) ORDER BY id LIMIT :n", args={"t": "orders", "n": 2})
# (1, eu, 10.0), (2, us, 20.0)

spark.sql("""BEGIN
  DECLARE x INT DEFAULT :start;
  SET x = x + 1;
  SELECT x;
END""", args={"start": 41})
# 42

Arrow-native UDFs (SPARK-52214, SPARK-52979): @arrow_udf and @arrow_udtf pass a function whole PyArrow arrays instead of converting to pandas first, so a vectorised function stays vectorised.

import pyarrow as pa, pyarrow.compute as pc
from pyspark.sql.functions import arrow_udf, col

@arrow_udf("double")
def with_tax(amount: pa.Array) -> pa.Array:
    return pc.multiply(amount, 1.18)

df.select("id", with_tax(col("amount")).alias("gross")).show()
# 1  11.799999999999999
# 2  23.599999999999998

Spark Declarative Pipelines (SPARK-51727)

Maturity: Default, driven by the spark-pipelines CLI. The official image needs extra Python packages.

Example in the repo: 07_declarative_pipelines.

You declare datasets, and Spark works out the order. A pipeline project is a spark-pipeline.yml and a folder of Python or SQL files. This one has a materialized view in Python and another in SQL that reads it:

name: orders_pipeline
libraries:
  - glob:
      include: transformations/**
storage: file:///work/sdp/storage

# transformations/orders.py
from pyspark import pipelines as dp
from pyspark.sql import DataFrame, SparkSession
spark = SparkSession.active()

@dp.materialized_view
def orders() -> DataFrame:
    return spark.sql("SELECT * FROM VALUES (1,'eu',10.0D),(2,'us',20.0D),"
                     "(3,'eu',30.0D),(4,'us',5.0D) AS t(id, region, amount)")

-- transformations/revenue.sql
CREATE MATERIALIZED VIEW revenue_by_region AS
SELECT region, sum(amount) AS total, count(*) AS orders
FROM orders
GROUP BY region;

spark-pipelines dry-run      # catches syntax, analysis and cycle errors without writing
spark-pipelines run

The run log shows both flows queued together and orders running first, because revenue_by_region reads it. Nothing in the files states that order. The output tables were:

orders:                          revenue_by_region:
 id region amount                 region total orders
  1 eu     10.0                   eu      40.0  2
  2 us     20.0                   us      25.0  2
  3 eu     30.0
  4 us      5.0

Nothing in the files states the order; Spark reads it from the dependency.

The official image does not contain the Python packages the CLI needs. The first run fails with ModuleNotFoundError: No module named 'yaml', and the CLI works through Spark Connect, so grpcio and its companions are needed too. Install pyyaml grpcio grpcio-status protobuf googleapis-common-protos zstandard, or use pip install pyspark[pipelines], which the 4.3 documentation recommends.

Structured Streaming real-time mode (SPARK-53736)

Maturity: Default for stateless queries, Scala only, Kafka source.

Example in the repo: 08_real_time_mode.scala.

Real-time mode runs a streaming query as long-lived tasks that process records as they arrive, instead of cutting the stream into micro-batches. You choose it with a trigger. In 4.1 it supports stateless queries and a short allowlist of sources, sinks and operators; the Kafka source is the supported source, and console, memory, foreach and Kafka are the supported sinks.

import org.apache.spark.sql.streaming.Trigger
import org.apache.spark.sql.functions._

val out = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "kafka:29092")
  .option("subscribe", "rtm_demo_in2").option("startingOffsets", "latest").load()
  .select(upper(col("value").cast("string")).alias("v"))

val q = out.writeStream.format("console").outputMode("update")
  .trigger(Trigger.RealTime("5 seconds")).start()

Messages hello, real and time produced to the topic came out as HELLO, REAL and TIME in a single batch. Python does not accept the trigger on 4.1.3: trigger(realTime="5 seconds") raised TypeError: DataStreamWriter.trigger() got an unexpected keyword argument 'realTime', matching the release note’s “Scala stateless support”. Stateful queries wait for 4.3.

Also in 4.1, not run here:

  • CONTINUE HANDLER and multi-variable DECLARE in SQL scripting, and shredding for faster VARIANT reads
  • Spark ML on Connect generally available for Python, zstd compression for protobuf plans, chunked Arrow result streaming, and no 2 GB limit on local relations
  • python_worker_logs() to query Python worker logs, and filter pushdown for Python data sources through pushFilters
  • A JDBC driver for Spark Connect (SPARK-53484)

Spark 4.2: new types, new joins, and a clearer SQL surface

The 4.2 examples ran on apache/spark:4.2.1-python3. Three of the release’s headline items, change data capture, INSERT ... WITH SCHEMA EVOLUTION and Data Source V2 transactions, are defined by the engine but implemented by a connector, so the built-in sources cannot show them. They are listed at the end of this section.

Geospatial types: GEOMETRY and GEOGRAPHY (SPARK-51658)

Maturity: Default in 4.2. The same call on 4.1.3 fails with GEOSPATIAL_DISABLED.

Example in the repo: 01_geospatial_types.sql.

Two first-class types for spatial values, each carrying an SRID (spatial reference id), so a geometry knows its coordinate system instead of being an anonymous BINARY. The release notes mention ST_* functions, WKB and WKT, and Parquet I/O. On 4.2.1 the function surface is small: SHOW FUNCTIONS lists five, and 4.3.0 lists the same five.

-- the five: st_asbinary, st_geogfromwkb, st_geomfromwkb, st_setsrid, st_srid
SELECT typeof(ST_GeomFromWKB(X'0101000000000000000000F03F0000000000000040'));   -- geometry(0)
SELECT typeof(ST_GeogFromWKB(X'0101000000000000000000F03F0000000000000040'));   -- geography(4326)

SELECT ST_SRID(ST_SetSRID(ST_GeomFromWKB(X'0101000000000000000000F03F0000000000000040'), 4326));
-- 4326

CREATE TEMP VIEW places AS
SELECT 'a' AS name,
       ST_SetSRID(ST_GeomFromWKB(X'0101000000000000000000F03F0000000000000040'), 4326) AS g;
DESCRIBE places;        -- name string, g geometry(4326)

Watch for: a GEOMETRY defaults to SRID 0 (unknown), a GEOGRAPHY to 4326, and there are no distance or containment functions in this release, so the types are a storage and interchange foundation rather than a spatial query engine yet.

The QUALIFY clause (SPARK-31561)

Maturity: Default.

Example in the repo: 02_qualify.sql.

QUALIFY filters on a window function directly, so “the top row per group” no longer needs a subquery around the window.

SELECT id, region, amount FROM orders_t
QUALIFY row_number() OVER (PARTITION BY region ORDER BY amount DESC, id) = 1
ORDER BY region;
-- 3  eu  30.0
-- 2  us  20.0

SELECT id, region, rank() OVER (PARTITION BY region ORDER BY amount DESC) AS r
FROM orders_t QUALIFY r = 1 ORDER BY id;     -- aliases work; ties all qualify
-- 2 us 1,  3 eu 1,  5 eu 1

The condition must contain a window function, and aggregates are not allowed in it.

NEAREST BY top-K ranking join (SPARK-56395)

Maturity: Default. Evaluation is brute force today.

Example in the repo: 03_nearest_by_join.sql.

For each row on the left, return the K best rows on the right under a ranking expression. It is the join shape behind “closest store”, “most similar item” and fuzzy matching, written as one clause instead of a cross join and a window.

-- pts:  (q1, 1.0), (q2, 9.0)       base: (a, 0.0), (b, 2.0), (c, 8.0), (d, 20.0)
SELECT q, x, name, y
FROM pts JOIN base EXACT NEAREST 2 BY DISTANCE abs(x - y)
ORDER BY q, abs(x - y);
-- q1 1.0 a 0.0
-- q1 1.0 b 2.0
-- q2 9.0 c 8.0
-- q2 9.0 b 2.0

SELECT q, name FROM pts JOIN base EXACT NEAREST BY DISTANCE abs(x - y);   -- K defaults to 1
-- q1 a,  q2 c

Syntax: { APPROX | EXACT } NEAREST [ k ] BY { DISTANCE | SIMILARITY } expr. INNER and LEFT OUTER are the supported join types, and k is between 1 and 100000. APPROX lets the optimiser use a faster strategy when one exists. The 4.2.1 documentation states the cost plainly: the current implementation evaluates the full cross product of the two sides, so pre-filter a large right side.

SET PATH: where unqualified names are looked up (SPARK-54806)

Maturity: Behind a flag (spark.sql.path.enabled, default false).

Example in the repo: 04_set_path.sql.

The SQL path is an ordered list of schemas Spark searches to resolve an unqualified table, view, function or variable. SET PATH changes it for the session, and current_path() reads it. Persistent views and SQL functions capture the path when they are created.

SELECT current_path();    -- system.builtin,system.session,spark_catalog.default

SET PATH = DEFAULT_PATH;
-- [UNSUPPORTED_FEATURE.SET_PATH_WHEN_DISABLED] SET PATH is disabled.
-- Set spark.sql.path.enabled to true to enable it.

SET spark.sql.path.enabled = true;
-- two schemas each holding a table named facts: ref.facts (2,'ref'), sales.facts (1,'sales')

SET PATH = spark_catalog.ref, DEFAULT_PATH;
SELECT current_path();    -- spark_catalog.ref,system.builtin,system.session,spark_catalog.default
SELECT * FROM facts;      -- (2, 'ref')

SET PATH = spark_catalog.sales, DEFAULT_PATH;
SELECT * FROM facts;      -- (1, 'sales')

DDL does not use the path: CREATE TABLE t always creates t in the current schema.

Metric views (SPARK-54119)

Maturity: Default, on the built-in catalog.

Example in the repo: 05_metric_views.sql.

A metric view defines dimensions and measures once, in YAML, so every consumer computes the same number. You query a measure with MEASURE(...) and group by a dimension.

CREATE OR REPLACE VIEW sales.revenue_mv WITH METRICS LANGUAGE YAML AS $$
version: "0.1"
source: spark_catalog.sales.orders
dimensions:
  - name: region
    expr: region
measures:
  - name: total_amount
    expr: sum(amount)
  - name: order_count
    expr: count(1)
$$;

SELECT region, MEASURE(total_amount) AS total, MEASURE(order_count) AS n
FROM sales.revenue_mv GROUP BY region ORDER BY region;
-- eu  70.0  3
-- us  25.0  2

The 4.2.1 documentation has no page for this syntax. The statement form comes from the project’s own test suite, and the YAML layout above is the one that ran.

Smaller addition: time_bucket and IGNORE NULLS (SPARK-56594, SPARK-55256)

Maturity: Default.

Example in the repo: 06_time_bucket_ignore_nulls.sql.

time_bucket(size, ts[, origin]) returns the start of the bucket a timestamp falls into, replacing the date_trunc or epoch-division arithmetic everyone writes for fixed-width windows. collect_list and array_agg now take IGNORE NULLS and RESPECT NULLS.

SELECT time_bucket(INTERVAL '15' MINUTE, TIMESTAMP_NTZ '2026-11-01 11:27:00');

SELECT time_bucket(INTERVAL '1' HOUR, ts) AS hour, count(*) AS n, sum(v) AS total

-- 11:00  1  5

Spark 4.3: stateful real-time mode, semi-structured SQL, and history tracking

All 4.3 examples ran on apache/spark:4.3.0-python3, which reports Scala 2.13 and Java 21. The release shipped without preview builds, and several features below are behind a flag or labelled preview.

JSON_TABLE (SPARK-58366)

Maturity: Default. Flat form only.

Example in the repo: 01_json_table.sql.

The SQL-standard way to turn a JSON document into rows and typed columns. It is the construct that migrated Oracle, DB2 and MySQL queries expect.

SELECT t.* FROM JSON_TABLE(
  '{"items":[{"id":1,"n":"a"},{"id":2,"n":"b"}]}',
  '$.items[*]'
  COLUMNS (
    seq  FOR ORDINALITY,
    id   INT    PATH '$.id',
    name STRING PATH '$.n'
  )
) AS t;
-- 1  1  a
-- 2  2  b

SELECT * FROM JSON_TABLE(
  '{"rows":[{"id":10,"opt":1},{"id":20}]}',
  '$.rows[*]'
  COLUMNS (id INT, hasOpt BOOLEAN EXISTS PATH '$.opt')
) AS t;
-- 10  true
-- 20  false

-- against a column, with LATERAL
SELECT d.id, t.k, t.v FROM docs d,
LATERAL JSON_TABLE(d.doc, '$.tags[*]' COLUMNS (k STRING PATH '$.k', v INT PATH '$.v')) AS t;
-- 1 x 1,  1 y 2,  2 z 3

NESTED PATH columns are not supported yet, so a document nested more than one array deep still needs two steps.

ASOF JOIN (SPARK-58092)

Maturity: Behind a flag (spark.sql.join.asofJoin.enabled, default false).

Example in the repo: 02_asof_join.sql.

For each left row, take the closest preceding row on the right: the quote in force when a trade happened, the price list valid on an order date. Without it you write a window function plus a join.

SELECT t.id, t.sym, t.ts, q.ts AS quote_ts, q.bid
FROM trades t ASOF JOIN quotes q
  MATCH_CONDITION (t.ts >= q.ts)
  ON t.sym = q.sym
ORDER BY t.id;

With the flag off the statement fails at parse time with [UNSUPPORTED_FEATURE.ASOF_JOIN] ... Set "spark.sql.join.asofJoin.enabled" to true. With it on, using trades at 10:00:05 and 10:00:20 for AAPL and 10:00:07 for MSFT, against quotes at 10:00:00 and 10:00:10 for AAPL and 10:00:06 for MSFT:

id  sym   ts        quote_ts  bid
1   AAPL  10:00:05  10:00:00  100.0
2   AAPL  10:00:20  10:00:10  101.0
3   MSFT  10:00:07  10:00:06  200.0

Three trades matched to their quotes: 100.0, 101.0 and 200.0.

Only INNER and LEFT OUTER are supported. In streaming, micro-batch supports a streaming left side joined to a static right side, and real-time mode does not support it.

UNNEST in the FROM clause (SPARK-58419)

Maturity: Default.

Example in the repo: 03_unnest.sql.

The ANSI way to expand arrays into rows, in place of explode and LATERAL VIEW. Several arrays expand in parallel and the shorter ones pad with NULL.

SELECT * FROM UNNEST(array('a','b')) WITH ORDINALITY AS t(value, pos);
-- a 1,  b 2

SELECT * FROM UNNEST(array(1,2), array(10,20,30)) AS t(a, b);
-- 1 10,  2 20,  NULL 30

SELECT id, elem
FROM VALUES (1, array(10,20)), (2, array(30)) AS data(id, arr),
     LATERAL UNNEST(arr) AS t(elem);
-- 1 10,  1 20,  2 30

VARIANT editing functions (SPARK-57804 and others)

Maturity: Default.

Example in the repo: 04_variant_editing.sql.

Until now a variant could be read but not changed without rebuilding it. These return a new variant with a path set, inserted, deleted or appended to.

SELECT variant_set(parse_json('{"a":1,"tags":["x"]}'), '$.b', 3);
-- {"a":1,"b":3,"tags":["x"]}

SELECT variant_insert(parse_json('["a","b","c"]'), '$[1]', 'z');
-- ["a","z","b","c"]

SELECT variant_delete(parse_json('{"a":1,"b":2,"items":[1,2,3]}'), '$.a', '$.items[0]');
-- {"b":2,"items":[2,3]}

SELECT variant_array_append(parse_json('{"a":[1,2]}'), '$.a', 3);
-- {"a":[1,2,3]}

SELECT variant_strip_nulls(parse_json('{"a":1,"b":null,"c":[1,null]}'));
-- {"a":1,"c":[1]}

variant_set and variant_insert differ on an existing key: set replaces it, insert is an error. try_ forms exist too (try_variant_set and others).

TIME(p) and nanosecond timestamps (SPARK-57551, SPARK-56876)

Maturity: Behind flags, and preview for the nanosecond timestamps.

Example in the repo: 05_time_and_nanosecond_types.sql.

TIME(p) goes up to nanosecond precision, and TIMESTAMP_NTZ(9) and TIMESTAMP_LTZ(9) add nanosecond timestamps. Two flags guard them: spark.sql.timeType.enabled for TIME, and spark.sql.timestampNanosTypes.enabled for the timestamps, which the release notes call a preview.

SET spark.sql.timeType.enabled = true;
SET spark.sql.timestampNanosTypes.enabled = true;

SELECT typeof(CAST('10:15:30.123456789' AS TIME(9)));        -- time(9)

SELECT CAST(CAST('2026-11-01 10:00:00.123456789' AS TIMESTAMP_NTZ(9)) AS STRING),
       typeof(CAST('2026-11-01 10:00:00.123456789' AS TIMESTAMP_NTZ(9)));
-- 2026-11-01 10:00:00.123456789   timestamp_ntz(9)

SELECT CAST('2026-11-01 10:00:00.123456789' AS TIMESTAMP_NTZ);   -- default keeps microseconds
-- 2026-11-01 10:00:00.123456

Without spark.sql.timeType.enabled, CAST(... AS TIME(9)) fails with UNSUPPORTED_TIME_TYPE, so TIME itself is still behind a flag in 4.3.0. The Python client in this release cannot materialise a TIMESTAMP_NTZ(9) result: selecting the column raised CANNOT_PARSE_DATATYPE ... timestamp_ntz(9), which is why the example casts to a string.

Stateful real-time mode (SPARK-58635, SPARK-57228, SPARK-58508)

Maturity: Default for the supported operators; needs one task slot per shuffle partition.

Example in the repo: 07_stateful_real_time_mode.scala.

4.1 gave real-time mode to stateless queries. 4.3 adds streaming aggregation, dropDuplicates and transformWithState. The trigger is the same.

val counts = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "kafka:29092").option("subscribe", "rtm43_demo3")
  .option("startingOffsets", "latest").load()
  .select(col("value").cast("string").alias("word"))
  .groupBy("word").count()

counts.writeStream.format("console").outputMode("update")
  .option("checkpointLocation", "/tmp/rtm43_ckpt3")
  .trigger(Trigger.RealTime("5 seconds")).start()

Producing a, b, a, a printed the running counts as the records arrived:

Batch 2
|word|count|
|   a|    1|
|   a|    2|
|   a|    3|
|   b|    1|

The word a appears three times in one batch because real-time mode emits each update as it happens, not one row per key at the end of the batch.

Watch for: the first attempt, with Spark’s default 200 shuffle partitions on a local[2] session, failed:

[CONCURRENT_SCHEDULER_INSUFFICIENT_SLOT] Cannot run the pipelined stage group:
it needs 201 concurrent task slots to run all its stages together, but only 2
are currently free.

The stages of a real-time query run at the same time, so the cluster needs a free slot for every task in all of them. Set spark.sql.shuffle.partitions to a number the cluster can run concurrently (2, on a local[6] session, worked) before you size the job.

Auto CDC with SCD Type 2 (SPARK-58321, SPARK-58247, SPARK-58261)

Maturity: Needs a connector. Spark’s built-in file formats are refused.

Example in the repo: 08_auto_cdc_scd2.sql.

Auto CDC applies a stream of change events to a target table inside a Declarative Pipeline. Type 1 keeps only the latest row per key. Type 2, new in 4.3, keeps the history of every change. The SQL form is a streaming table with an Auto CDC flow:

CREATE STREAMING TABLE customers_history
FLOW AUTO CDC
FROM STREAM(cdc_events)
KEYS (id)
APPLY AS DELETE WHEN op = 'DELETE'
SEQUENCE BY version
COLUMNS * EXCEPT (op)
STORED AS SCD TYPE 2;

On a pipeline whose target is a default Parquet table, the syntax parses and the flow fails to start:

[AUTOCDC_TARGET_DOES_NOT_SUPPORT_MERGE] Cannot start AutoCDC flow: the target table
`spark_catalog`.`default`.`customers_history` (format: parquet) does not support
row-level operations.

Each micro-batch is applied with a MERGE, so the target must be a table whose connector implements Data Source V2 row-level operations. The 4.3 documentation names lakehouse connectors such as Apache Iceberg as the usual choice, and it notes that its own page for SCD Type 2 is still to be written. This is the clearest case in the line of an engine feature that does nothing until a connector supports it. A pipeline run against an Iceberg catalog was not done here.

Faster queries on small data (SPARK-57851, SPARK-57268)

Maturity: Behind flags. Not demonstrated here.

A runner that executes a SQL file

The runner reads a file of statements separated by a line containing only ;;. A line starting with -- ### is printed as a heading, and the SQL after it runs. It uses only spark.sql, so any statement from the previous section works in it.

import scala.io.Source

val specPath = sys.env("SPEC")
val statements = Source.fromFile(specPath).mkString.split("\n;;\n").map(_.trim).filter(_.nonEmpty)
println("SPARK " + spark.version + " | Scala " + scala.util.Properties.versionNumberString + " | Java " + System.getProperty("java.version"))

statements.foreach { block =>
  val lines = block.linesIterator.toList
  // A leading "-- ### title" line is printed as a heading; whatever follows it is the SQL.
  val (heading, sql) =
    if (lines.head.startsWith("-- ###")) (Some(lines.head.drop(7)), lines.tail.mkString("\n").trim)
    else (None, block)
  heading.foreach(h => println("\n### " + h))
  if (sql.nonEmpty) {
    println(sql.linesIterator.next().take(110))
    try spark.sql(sql).collect().take(12).foreach(r => println("   " + r.mkString(" | ")))
    catch { case e: Throwable => println("   ERROR: " + e.getMessage.linesIterator.next().take(200)) }
  }
}
sys.exit(0)

class CounterDataSource(DataSource):
    @classmethod
    def name(cls):
        return "counter"

    def schema(self):
        return "n INT, square INT"

    def reader(self, schema):
        return CounterReader(self.options)


class CounterReader(DataSourceReader):
    def __init__(self, options):
        self.limit = int(options.get("limit", 3))

    def read(self, partition):
        for i in range(1, self.limit + 1):
            yield (i, i * i)

What to budget for

Feature Cost to plan for
NEAREST BY The current implementation evaluates the full cross product of the two sides, so its work grows with left rows times right rows times the log of k. Pre-filter the right side.
Real-time mode One free task slot per task across all stages, held for the life of the query.
Sketch functions Approximate answers, and answers that can differ between runs.
Declarative Pipelines The execution graph is derived, not written. Run spark-pipelines dry-run first to catch syntax, analysis and cycle errors without writing data.
Auto CDC Each micro-batch is a MERGE, so the target must support row-level operations.
Arrow-optimized UDFs Types, nulls and timestamps are where the new exchange path differs from the old. Test your own UDFs.
Metric views The 4.2.1 documentation has no page for the syntax, so you depend on the project’s tests and release notes.

Upgrade by upgrade

This part is my judgement, drawn from what ran, not a measurement.

  • To 4.0. Not optional once you leave 3.x, because Scala 2.13 and Java 17 are the baseline. The work is dependency and ANSI-mode testing, and the language gains (pipe syntax, SQL functions, session variables, collations) come with it.
  • 4.0 to 4.1. Worth it for SQL scripting, recursive CTEs and VARIANT colon paths if you have logic living in driver code. Declarative Pipelines is worth a trial on one pipeline, with dry-run, before you commit a team to it.
  • 4.1 to 4.2. QUALIFY and metric views pay back quickly for analysts. The geospatial types are a foundation: five functions today, no distance or containment.
  • 4.2 to 4.3. JSON_TABLE, UNNEST and the VARIANT editing functions help any pipeline that handles nested documents. Stateful real-time mode is for the few queries that need sub-second latency and a Kafka source. 4.3.0 shipped without preview builds, so a cautious team waits for the first patch release.

Before you upgrade

  1. Test in this order: ANSI errors on your real data first, then the settings above for anything a job relies on, then the Python environment.
  2. Pin the interpreter and the packages with the release. The Python floor moved from 3.9 to 3.11 across the four releases.
  3. Switch on one flag at a time, in the session that uses it rather than cluster-wide, so a failure points at the feature.
  4. Check the connector before the engine. For Auto CDC, CHANGES, schema evolution and transactions, the connector decides whether the feature exists for your table.
  5. Print spark.version at the top of every run. It is the cheapest check against running the wrong install.

The line is moving faster than at any point in the 4.x series. Treat the tables here as a snapshot, re-check the maturity of each feature against the release note of the version you deploy, and keep the SQL files from the demo section as a smoke test you can rerun on the next release.
