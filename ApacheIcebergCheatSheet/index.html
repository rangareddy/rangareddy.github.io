TL;DR

  • Iceberg describes a table as an immutable tree: a catalog pointer to metadata.json, which names a snapshot, which points at a manifest list, which points at manifests, which list data files. The catalog’s compare-and-swap on that pointer is what makes a commit atomic.
  • Every example on this page is PySpark, run end to end against a Hive Metastore catalog named iceberg_db, with tables in the iceberg_schema database. Where PySpark has no API (DDL, CALL procedures), the Python calls spark.sql().
  • The default that surprises everyone: write.delete.mode, write.update.mode and write.merge.mode all default to copy-on-write. And a merge-on-read DELETE that removes every row of a file writes no delete file at all; it drops the file from the snapshot.
  • Four failures you will meet on a Hive catalog, all reproduced below: a column reorder rejected by the Metastore as CommitStateUnknownException, CALL arguments that must be literals, changelog scans that refuse delete files, and snapshot tables that refuse PURGE.
  • New tables are format version 2 by default; version 3 brings deletion vectors and row lineage. Format version 4 code exists but is not for production tables.

Most Iceberg questions are not conceptual. You know you want a merge-on-read DELETE, you know roughly what expire_snapshots does, and what you need is the exact option name, whether its default will surprise you, and what the Hive Metastore will do to your ALTER TABLE. That is what this page is for.

It is organised for lookup. Each section leads with a table of keys, options or procedures, then the PySpark that uses them, then the output that PySpark produced. Every Python block on the page is part of one script that ran end to end on Spark 3.5.9 with Iceberg 1.12.0 against the datalake-playground stack: Hive Metastore as the catalog, MinIO as S3. Run the blocks in order in one session and they reproduce the outputs shown.

2. Introduction, key features and architecture

Apache Iceberg is an open table format for large analytic tables. It sits above the file formats (Parquet, ORC, Avro) and below the engines, and replaces the Hive model of “a table is a directory, and the Metastore tracks its partitions” with a tree of immutable metadata files that lists every data file explicitly. Planning reads that metadata instead of listing storage, which is why it scales to tables of millions of files on object stores.

Feature What you get
ACID commits Serialisable commits through an atomic swap of one catalog pointer; readers always see a complete snapshot
Hidden partitioning Partition by a transform of a column (days(started_at)); queries filter on the column and prune automatically
Partition evolution Change the partition spec without rewriting data; old files keep their old spec
Schema evolution Add, drop, rename, reorder and widen columns, tracked by column ID, with no data rewrite
Row-level operations UPDATE, DELETE, MERGE as copy-on-write or merge-on-read, per operation
Time travel and refs Read any retained snapshot; branches and tags name snapshots; write-audit-publish stages commits
Metadata tables Snapshots, files, manifests, partitions and more, queryable as ordinary tables
Multi-engine Spark, Flink, Trino, Presto, Hive, Snowflake, BigQuery, DuckDB and others read and write the same table

When Iceberg fits, and when it does not

Good fit Poor fit
Large analytic tables on object storage, queried by more than one engine OLTP and single-row point lookups at low latency
Tables that need row-level changes: GDPR deletes, CDC, corrections Sub-second freshness on small, hot data
Replacing Hive-managed Parquet or ORC tables and their partition listings Tiny datasets, where a plain file is simpler
Streaming and batch writers on the same table Workloads needing record-key upserts with an index, where Hudi’s design is closer

What ACID means here

Property How Iceberg provides it
Atomicity A commit is one compare-and-swap of the catalog’s pointer to metadata.json; it either moves or it does not
Consistency Every snapshot is a complete, self-describing list of files; there is no partially written state to read
Isolation Readers pin a snapshot for the life of a query; writers use optimistic concurrency and retry on conflict
Durability Data and metadata files are written before the pointer moves, and are never mutated afterwards

Read it top down. The Metastore stores only metadata_location for the table. That file names the current snapshot, whose manifest list names the manifests, which name the files. A commit writes new files bottom up and finally swaps the pointer, so nothing a reader is using is ever changed.

Adapted from the Apache Iceberg documentation.

Sharing is the part worth noticing. A commit that adds one file writes a new manifest and a new manifest list, but reuses every manifest that did not change, which is why snapshot history costs metadata rather than data.

FileContent enumerates what a manifest entry can describe: DATA, POSITION_DELETES, EQUALITY_DELETES, DATA_MANIFEST and DELETE_MANIFEST.

Planning is a sequence of prunes, and each step reads metadata, not data:

 query with a filter
   │
   ▼  manifest list: skip whole manifests by partition range
   ▼  manifests:     skip files by partition value
   ▼  column bounds: skip files by per-column min and max
   ▼  the files actually scanned

The session. iceberg_db is a SparkCatalog backed by the Hive Metastore, and spark_catalog is wrapped in SparkSessionCatalog so the same session can read plain Hive tables and convert them in place with migrate (section 22). Every later block runs in this session.

4. Catalogs

The catalog is not optional. Nothing inside the table says which metadata.json is current, so commit atomicity is a property of the catalog, not of the format.

Catalog Session config Notes
Hive type=hive, uri=thrift://... Stores metadata_location as a table parameter; takes a Metastore lock per commit (engine.hive.lock-enabled, default true). Used on this page
REST type=rest, uri=https://... The catalog spec other engines implement, and the portable choice. Polaris, Unity, Gravitino and Nessie serve it
Glue type=glue, io-impl=org.apache.iceberg.aws.s3.S3FileIO AWS Glue Data Catalog. Optimistic locking on the Glue table version
JDBC type=jdbc, uri=jdbc:postgresql://... Any relational database holds the pointer
Nessie type=nessie, uri=..., ref=main Git-like, catalog-level branches across tables
Hadoop type=hadoop, warehouse=... Filesystem only. Relies on atomic rename, so not safe for concurrent writers on S3
Session catalog spark_catalog set to SparkSessionCatalog Wraps the built-in catalog so Iceberg and non-Iceberg tables share one namespace. Needed for migrate

The table holds 9 data files, 7 metadata.json files, 12 manifests and 7 manifest lists. There is one metadata.json per commit, numbered 00000 upward, because every commit rewrites the table metadata in full. There is one snap-<snapshot-id>-...avro manifest list per snapshot, named after the snapshot. And the data directory still holds files that the current snapshot no longer references: the copy-on-write UPDATE wrote replacements, but the old files stay until expire_snapshots removes them (section 16).

The partition directory names (started_at_day=...) are cosmetic. Readers take partition values from the manifests and never parse paths.

Hidden partitioning is the point. The writer declares days(started_at) and the reader filters on started_at. There is no dt column to add to the schema, no query that forgets to filter on it, and no correlation for the user to remember.

Partition evolution changes the spec for new writes only. Existing files keep the spec they were written with, and planning prunes each spec separately:

spark.sql(f"ALTER TABLE {TRIPS} ADD PARTITION FIELD bucket(16, rider_id)")
spark.sql(f"ALTER TABLE {TRIPS} DROP PARTITION FIELD days(started_at)")
spark.sql(f"ALTER TABLE {TRIPS} ADD PARTITION FIELD hours(started_at)")

7. Row-level operations: copy-on-write and merge-on-read

Concept Property or form Description
Copy-on-write write.delete.mode, write.update.mode, write.merge.mode = copy-on-write Rewrites every data file containing a changed row. Reads stay plain Parquet. The default for all three
Merge-on-read the same three = merge-on-read Writes delete files instead of rewriting data. Cheap writes; reads reconcile; something must compact
Position delete file path plus row position, format version 2 Precise and cheap to apply
Equality delete column values, for example trip_id = 'trip-1001' No positions needed, so streaming writers (Flink) use them; readers apply the predicate more widely

Metadata-only delete any mode A DELETE whose filter covers whole files drops them from the snapshot and writes nothing

   │ write a new file without it        │ (v3: a deletion vector)
   ▼                                    ▼ data file untouched
 read = plain Parquet                 read = data merged with deletes
                                        │
                                        ▼ compact later
                                      rewrite_data_files,
                                      rewrite_position_delete_files

Switch the table to merge-on-read and delete twice:

spark.sql(f"""
    ALTER TABLE {TRIPS} SET TBLPROPERTIES (
      'write.delete.mode' = 'merge-on-read',
      'write.update.mode' = 'merge-on-read',
      'write.merge.mode'  = 'merge-on-read'
    )
""")
# trip-1005 is alone in its data file, so Iceberg drops the whole file: no delete file
spark.sql(f"DELETE FROM {TRIPS} WHERE trip_id = 'trip-1005'")

# Two rows written into one file; deleting one of them needs a position delete
pair = spark.createDataFrame([
    ("trip-2001", "rider-77aa10", Decimal("8.00"), datetime(2026, 9, 17, 18, 10, 0), "nyc"),
    ("trip-2002", "rider-77aa10", Decimal("9.50"), datetime(2026, 9, 17, 18, 20, 0), "nyc"),
], trip_schema)
pair.coalesce(1).writeTo(TRIPS).append()

One delete file, not two. trip-1005 was the only row in its data file, so Iceberg removed the file from the snapshot and wrote no delete file at all, even in merge-on-read mode. trip-2001 shared a file with trip-2002, so that delete became one position delete file (content 1) in Parquet. When you size delete file growth, count rows deleted from files that survive, not rows deleted.

Note: TableProperties sets DELETE_MODE_DEFAULT, UPDATE_MODE_DEFAULT and MERGE_MODE_DEFAULT all to RowLevelOperationMode.COPY_ON_WRITE.modeName(). Set the three together: a table that merges on read for MERGE but copies on write for DELETE behaves differently depending on which statement a job happened to use.

1.12 breaking change: position deletes with row data can no longer be written, and rewrite_position_delete_files and rewrite_table_path fail on files that still carry it. Either upgrade the table to version 3 and rewrite the deletes as deletion vectors, or stay on version 2 and let data compaction fold them into data files.

Iceberg itself allows the reorder. The Hive catalog is what rejected it: on every commit it mirrors the schema into the Metastore’s column list, and a Metastore running with its default hive.metastore.disallow.incompatible.col.type.changes=true compares the old and new lists position by position. Moving city_id (string) after passenger_id shifts fare_amount and started_at into positions held by other types, so the Metastore refuses, and Iceberg reports CommitStateUnknownException because it cannot tell from the response whether its pointer moved. Here it had not: the schema printed afterwards still has city_id after started_at.

Reorders and drops that only shift compatible types pass. A separate run dropped a middle INT column between two STRING columns and moved a STRING column first, and the Metastore accepted both.

Note: the fix is server-side: set hive.metastore.disallow.incompatible.col.type.changes to false in the Metastore’s hive-site.xml. Setting it on the Spark side does not help, because the check runs inside the Metastore. Until then, treat CommitStateUnknownException from a DDL as “re-read the table and check”, never as “retry blindly”.

The last statement added tip on write. merge-schema only takes effect when the table allows it through write.spark.accept-any-schema. With the property unset, Spark rejects the DataFrame before Iceberg sees it, with AnalysisException: [INSERT_COLUMN_ARITY_MISMATCH.TOO_MANY_DATA_COLUMNS].

19. Concurrency

Concept Where Description
Optimistic concurrency every commit A writer prepares a snapshot, then swaps the catalog pointer. If another writer moved it first, the commit fails and is retried against the new base
Catalog atomicity Hive, REST, Glue, JDBC, Nessie The compare-and-swap lives in the catalog
Hive lock engine.hive.lock-enabled, default true The Hive catalog wraps each commit in a Metastore lock
Retries commit.retry.num-retries, default 4 With backoff from 100 ms to 60 s
Isolation isolation-level write option serializable validates that no conflicting data was added; snapshot validates less and conflicts less
Filesystem caveat type=hadoop on S3 No atomic swap. The table looks identical on disk but has weaker guarantees

Two exceptions to tell apart. CommitFailedException means the commit definitely did not happen and is safe to retry. CommitStateUnknownException (section 13) means the catalog call failed in a way that leaves the outcome unknown; re-read the table before doing anything else.

20. Change data: the changelog view

create_changelog_view turns the snapshots between two points into rows tagged INSERT, DELETE, UPDATE_BEFORE and UPDATE_AFTER. With identifier_columns, a delete and insert of the same key in one snapshot is reported as an update pair.

      identifier_columns => array('trip_id')

Three procedures, and the difference is what happens to the source table. All three reuse the existing data files.

Four things worth knowing before running migrate on anything that matters.

The data is not rewritten, so the layout you had is the layout you get. A Hive table of many small files becomes an Iceberg table of many small files. Plan a rewrite_data_files pass afterwards.

Partitioning carries across as identity transforms, because that is what a Hive directory layout means. To move to days(started_at), add the partition field afterwards; older files keep their original spec.

A snapshot table does not own its files. It is created with gc.enabled=false, and DROP TABLE ... PURGE on it fails with Cannot purge table: GC is disabled (deleting files may corrupt other tables). Drop it without PURGE.

Stop the writers first. These procedures capture the current file list, so a job still writing to the Hive table during migrate can leave files no Iceberg snapshot references.

Summary and key takeaways

The catalog is part of the table. Commit atomicity, where the namespace lives, and which schema changes are allowed all come from the catalog. On a Hive catalog, the Metastore’s own column checks apply to Iceberg DDL.

Defaults to remember. Copy-on-write for all three row-level operations, format version 2, 512 MB target files, zstd on new tables, 4 commit retries, 5-day snapshot age. Set merge-on-read for all three operations together or not at all.

Count what the metadata tables show, not what the procedures return. The compaction result row hid a skipped commit group; the delete_files count did not. Three queries (files, snapshots, delete_files) answer most “why is this table slow” questions.

Plan for 1.12.0 specifically. Spark 3.4 support and position deletes with row data are gone. Hilbert clustering is Spark 4.1 only. The V4 code is to watch, not to use.
