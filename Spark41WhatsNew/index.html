Spark 4.1 changes how you describe work to Spark. A pipeline becomes a set of declared datasets whose order Spark derives. SQL gains scripts, loops and recursion, so logic that lived in a Python driver can move into a query. And Structured Streaming gets a real-time trigger for low-latency, stateless queries. This post is for data engineers who build pipelines and for streaming teams who want to know what the real-time trigger covers. You will learn what eight features do, the syntax, what a real run printed, and where each one stops. All four releases side by side are in the Spark 4.x features-by-release post.

Everything in Spark 4.1.

Verified execution. Every sample in this post ran on Spark 4.1.3, on the apache/spark:4.1.3-python3 image, in November 2026. Real-time mode and the parameter markers also ran on the 4.1.4 tarball. Each feature carries a Status line: Ran means the printed output is real, behind a flag names the setting, and needs a connector means the engine defines the syntax and a table format has to implement it. Where I could not run something, it is labelled listed and its limits are in Known limitations. The runnable files are in ranga-spark4-examples under spark-4.1/.

Try this first

A three-step path if you are new to these features. None of it needs Kafka, pyarrow or extra packages.

  2. Run one query. Count to five with the recursive CTE.
  3. Run one script. Try the WHILE loop in SQL scripting.

1. Spark Declarative Pipelines [Intermediate]

Since: 4.1.0 · Status: Ran; the official image needs extra Python packages · Source: SPARK-51727

Lineage: Auto CDC flows arrive in pipelines in 4.2 (SCD Type 1, SPARK-56249) and 4.3 (SCD Type 2, SPARK-58321).

What it is

A pipeline is a set of datasets, each defined by a query, where some read others. Declarative Pipelines lets you state those datasets and leave the run order, parallelism and retries to Spark (SPARK-51727). A project is a spark-pipeline.yml file plus a folder of Python or SQL files, and you run it with the spark-pipelines command. A materialized view is a dataset whose result Spark computes and stores.

Why it matters

This means you can write each table as a query and stop hand-ordering the steps. Under the hood, Spark builds a graph from the references between datasets, which is why orders ran before revenue_by_region in the run log: the SQL view reads it, and nothing in the files says so. spark-pipelines dry-run checks syntax, analysis and cycles without writing anything. The CLI works through Spark Connect, and the official image lacks the Python packages it needs: the first run fails with ModuleNotFoundError: No module named 'yaml'. Install pyyaml grpcio grpcio-status protobuf googleapis-common-protos zstandard, or use pip install pyspark[pipelines].

Sample code

Runnable files: 07_declarative_pipelines.

# transformations/orders.py: a materialized view defined in Python
from pyspark import pipelines as dp
from pyspark.sql import DataFrame, SparkSession
spark = SparkSession.active()

@dp.materialized_view
def orders() -> DataFrame:
    return spark.sql("SELECT * FROM VALUES (1,'eu',10.0D),(2,'us',20.0D),"
                     "(3,'eu',30.0D),(4,'us',5.0D) AS t(id, region, amount)")

-- transformations/revenue.sql: reads orders, so it runs after it
CREATE MATERIALIZED VIEW revenue_by_region AS
SELECT region, sum(amount) AS total, count(*) AS orders
FROM orders GROUP BY region;

spark-pipelines dry-run   # syntax, analysis and cycle errors, nothing written
spark-pipelines run       # eu 40.0 over 2 orders, us 25.0 over 2

When to use it

Use it when you have related datasets whose run order you would rather derive than write. Skip it when the pipeline mixes many engines, where an external orchestrator is the better fit, or you need a custom schedule. Common beginner mistake: running spark-pipelines on the official image without installing its Python packages; the first run fails with ModuleNotFoundError: No module named 'yaml'.

Where it helps. A chain of related tables, such as bronze, silver and gold, where hand-written code today encodes the run order. You declare each dataset and Spark derives the order, and a dry run validates the graph before anything is written.

Visual

Nothing in the files states the order; Spark reads it from the dependency.

2. Real-time mode for stateless queries [Advanced]

Since: 4.1.0 · Status: Ran (needs a Kafka broker) · Source: SPARK-53736

Lineage: stateless queries in 4.1.0, a PySpark trigger in 4.2 (SPARK-54660), stateful queries in 4.3.0.

What it is

Structured Streaming normally cuts a stream into micro-batches and runs a job per batch. Real-time mode runs the query as long-lived tasks that process records as they arrive (SPARK-53736). You choose it with a trigger. In 4.1 it supports stateless queries only, such as a filter or a projection, in Scala, with Kafka as the source. The supported sinks are console, memory, foreach and Kafka.

Why it matters

This means you can cut the wait between a record landing and a result appearing for queries that keep no state.

Under the hood, the supported sources, sinks and operators are a short allowlist, and anything outside it is rejected. Python does not accept the trigger on 4.1.3: trigger(realTime="5 seconds") raised TypeError: DataStreamWriter.trigger() got an unexpected keyword argument 'realTime', which matches the release note’s “Scala stateless support”. Stateful queries, such as counts, wait for 4.3. I make no latency claim here: the run showed messages hello, real and time coming out as HELLO, REAL and TIME in a single batch, and I did not benchmark it.

Sample code

Runnable file: 08_real_time_mode.scala.

import org.apache.spark.sql.streaming.Trigger
import org.apache.spark.sql.functions._

// needs a Kafka broker
val out = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "kafka:29092")
  .option("subscribe", "rtm_demo_in2").option("startingOffsets", "latest").load()
  .select(upper(col("value").cast("string")).alias("v"))

// the real-time trigger replaces the micro-batch trigger
val q = out.writeStream.format("console").outputMode("update")
  .trigger(Trigger.RealTime("5 seconds")).start()

When to use it

Use it when a stateless Scala query on Kafka needs results as records arrive. Skip it when the query keeps state, which waits for 4.3, uses Python, or reads from a source other than Kafka. Common beginner mistake: calling trigger(realTime=...) from Python, which raises a TypeError in 4.1.

Where it helps. Fraud checks, alerts and other stateless filters on a Kafka stream where waiting for a micro-batch is too slow. Managed platforms may lag the open-source release, so check which Spark line your platform runs before planning around it; Microsoft Fabric Runtime 2.0, for example, is documented as Spark 4.1.

Constraints and reported latency

The first four items come from the 4.3 real-time mode guide, for the stateless queries that arrived in 4.1.0, and the last from the vendor’s 4.1 announcement. I did not run them.

  • Output and checkpoint. The output mode must be update, and a checkpointLocation is required.
  • Sources and sinks. Kafka is the only source. Sinks are Kafka, foreach, console and memory, and foreachBatch is not supported.
  • Stateless operators. Projections, filters, a union of distinct sources, and stream-static joins whose static side is broadcast.
  • Sizing. Each input partition gets a long-running task, so a 10-partition topic needs at least 10 cores. The trigger duration is a checkpoint interval, with a 5,000 ms minimum by default, not a latency target.
  • Reported latency. The announcement reports p99 latencies “in the single-digit milliseconds range” for stateless workloads. It gives no hardware, workload or method, and I did not measure latency, so treat it as a vendor claim.

Micro-batches wait for a boundary; long-lived tasks pass records through as they arrive.

3. SQL scripting [Beginner]

Since: 4.1.0 · Status: Ran · Source: SPARK-54499, SPARK-53621, SPARK-52998

Lineage: cursors arrive in 4.2, behind flags (SPARK-54759).

What it is

A SQL script is a BEGIN ... END block that can declare variables, loop, branch and handle errors, and runs as a single statement (SPARK-54499). It moves logic that used to live in a Python driver into SQL that an analyst can read. Spark 4.1 enables it by default, so spark.sql.scripting.enabled is true.

Why it matters

This means a multi-step job, such as a loop that builds a total or a block that recovers from an error, can be one SQL statement instead of a program.

Under the hood, a script returns the result of its last query, which is what spark.sql hands back. An error handler is declared with DECLARE EXIT HANDLER FOR <condition>, and a FOR loop can iterate over a query result. The release also adds CONTINUE HANDLER support (SPARK-53621) and several variables in one DECLARE (SPARK-52998), though CONTINUE HANDLER sits behind an internal flag, spark.sql.scripting.continueHandlerEnabled, that read false on 4.1.3 and is still off in 4.3.0, which the 4.2 post shows with cursors.

Sample code

Runnable file: 01_sql_scripting.sql.

BEGIN
  DECLARE total INT DEFAULT 0;
  DECLARE i INT DEFAULT 1;
  WHILE i <= 5 DO
    SET total = total + i;
    SET i = i + 1;
  END WHILE;
  SELECT total, i;
END;
-- 15, 6

BEGIN
  DECLARE result DOUBLE DEFAULT 0;
  DECLARE EXIT HANDLER FOR DIVIDE_BY_ZERO
  BEGIN
    SET result = -1;
    SELECT 'caught divide by zero' AS status, result;
  END;
  SET result = 1 / 0;
END;
-- caught divide by zero, -1.0

When to use it

Use it when a multi-step job, such as a loop or an error handler, can live in one SQL statement. Skip it when a set-based query does the job. Common beginner mistake: expecting a CONTINUE handler to work. Its flag, spark.sql.scripting.continueHandlerEnabled, read false on 4.1.3.

Visual

A loop that returns 15 and 6, and a handler that catches the divide by zero.

4. Recursive common table expressions [Intermediate]

Since: 4.1.0 · Status: Ran · Source: SPARK-24497

What it is

A common table expression (CTE) is a named subquery introduced with WITH. A recursive one refers to itself: it starts from a base query and repeatedly applies a step to the previous result until the step returns nothing (SPARK-24497). That is how SQL walks a hierarchy, such as an org chart, or a graph, and before 4.1 it needed a loop in application code.

Why it matters

This means you can answer “who reports to whom, at every level” in one query, inside the engine.

Under the hood, the base query runs first, then the recursive part runs against the rows the previous pass produced, joined to the source table, so the number of passes equals the depth of the hierarchy. The WHERE condition in the recursive part is the stop rule. Without one, Spark stops the query at 100 levels with RECURSION_LEVEL_LIMIT_EXCEEDED, and the error shows a MAX RECURSION LEVEL clause to raise the limit. I checked this on 4.1.3. A four-level org chart walked from the root, where boss IS NULL, returned ceo 0, vp 1, dir 2 and mgr 3: one row per level. The sample below counts to five.

Sample code

Runnable file: 02_recursive_cte.sql.

WITH RECURSIVE t(n) AS (
  SELECT 1                          -- the base case
  UNION ALL
  SELECT n + 1 FROM t WHERE n < 5   -- the step, and the stop rule
) SELECT n FROM t;
-- 1, 2, 3, 4, 5

When to use it

Use it when you walk a hierarchy or a graph, such as an org chart. Skip it when the data is flat, or a join does the job. Common beginner mistake: leaving out the stop rule; the query ends at 100 levels with RECURSION_LEVEL_LIMIT_EXCEEDED.

Visual

The base row seeds the recursion, and each pass adds one until n reaches 5.

5. VARIANT generally available, with colon paths [Beginner]

Since: 4.1.0 · Status: Ran · Source: SPARK-54454, SPARK-52494, SPARK-53659, SPARK-54410

Lineage: VARIANT in 4.0 (SPARK-45827), generally available with colon paths in 4.1, editing functions in 4.3 (SPARK-57804).

What it is

VARIANT is the Spark type for semi-structured data such as JSON, stored in a binary encoding that is parsed once instead of on every read. 4.1 declares it generally available and on by default (SPARK-54454), and adds a shorthand to read a field: v:path, with ::type to cast the result (SPARK-52494). Version note: VARIANT arrived in 4.0 and gained editing functions in 4.3.

Why it matters

This means you can read a JSON field without a schema and without get_json_object. Under the hood, a path that does not exist returns NULL, and a field can hold a different type in each row, which a typed column could not. schema_of_variant reports each row’s own type. In the sample, n is a number in one row and a string in the other. The release also adds shredding, which stores frequently read fields as separate Parquet columns for faster reads, and Parquet support for the Variant logical type (SPARK-53659, SPARK-54410). I did not run shredding.

Sample code

Runnable file: 03_variant_colon_paths.sql.

-- ev(v VARIANT) holds two rows:
--   {"user":"a","n":3,"tags":["x","y"]}
--   {"user":"b","n":"x"}
SELECT v:user::string AS user,
       v:tags[0]::string AS first_tag,
       schema_of_variant(v:n) AS n_type
FROM ev ORDER BY 1;
-- a  x     BIGINT
-- b  NULL  STRING

Before 4.1, a field needed variant_get with a path and a type:

SELECT variant_get(v, '$.user', 'string') AS user,
       variant_get(v, '$.tags[0]', 'string') AS first_tag
FROM ev ORDER BY 1;
-- a  x
-- b  NULL

It returns the same rows as the colon form. Both are in 09_before_after.sql.

When to use it

Use it when JSON arrives with a changing shape and you read fields by path. Skip it when the shape is fixed and typed columns would be simpler. Common beginner mistake: using colon paths on a 4.0 cluster, which fails with PARSE_SYNTAX_ERROR; there, use variant_get.

Visual

One path expression, applied to two rows whose n field has different types.

6. Parameter markers anywhere [Beginner]

Since: 4.1.0 · Status: Ran · Source: SPARK-53573

Lineage: parameterized SQL through sql() in PySpark in 4.0 (SPARK-41666), markers nearly anywhere in 4.1.

What it is

A parameter marker is a :name placeholder in a SQL string whose value you pass separately, so application code never has to splice a value into the text. Markers worked in a few expression positions before. In 4.1 a pre-parser substitutes them nearly anywhere (SPARK-53573): a LIMIT, an identifier through IDENTIFIER(:t), and a default inside a script.

Why it matters

This means you can build a query from user input without string concatenation, which is the source of SQL injection.

Under the hood, the substitution happens before parsing, so a marker can stand where only a literal would normally fit, including a table name. The values go in as the args argument of spark.sql. The sample returned the first two rows of orders, and the script printed 42 after adding 1 to the start value of 41. The 4.0 release notes already list parameterized SQL through sql() in PySpark (SPARK-41666), so 4.1 widens where a marker is allowed, not whether markers exist.

Sample code

Runnable file: 05_parameter_markers.py.

# the table name and the limit are parameters, not spliced text
spark.sql("SELECT * FROM IDENTIFIER(:t) ORDER BY id LIMIT :n",
          args={"t": "orders", "n": 2})
# (1, eu, 10.0), (2, us, 20.0)

# a marker inside a script
spark.sql("""BEGIN
  DECLARE x INT DEFAULT :start;
  SET x = x + 1;
  SELECT x;
END""", args={"start": 41})      # 42

When to use it

Use it when a value comes from user input or application code and must not be spliced into SQL text. Skip it when the value is a constant of the query itself. Common beginner mistake: building the SQL string with an f-string anyway; markers keep the value out of the text.

Visual

A row count, a table name and a script default, all passed as arguments.

7. Sketch functions [Intermediate]

Since: 4.1.0 · Status: Ran · Source: SPARK-52515, SPARK-54199, SPARK-52407, SPARK-52588

Lineage: native Tuple sketches and Tuple/Theta set operations in 4.2 (SPARK-54179, SPARK-55558).

What it is

A sketch is a small summary of a large set that answers an approximate question. 4.1 adds approx_top_k for the most frequent items (SPARK-52515), KLL sketches for quantiles (SPARK-54199) and Theta sketches for distinct counts and set operations (SPARK-52407). They are aggregates that can be stored in a column and merged later.

Why it matters

This means you can roll daily summaries up into a weekly one without reading the raw data again.

Under the hood, a sketch trades exactness for size: the median of 1 to 1000 is about 500 and the 99th percentile about 990, and the sketch returned slightly different values from run to run. On 4.1.3 alone the same query gave 497, 499, 500 and 501 for the median and 989 or 990 for the 99th percentile, depending on how many cores the run used and between identical runs. 4.3.0 gave 499 or 500 and 989 or 990. The variation comes from the run, not the release, so assert a tolerance on sketch results in tests, not an exact value.

approx_top_k also comes in accumulate, estimate and combine forms (SPARK-52588, SPARK-52515), which is what lets its state be stored and merged.

Sample code

Runnable file: 04_sketch_functions.sql.

-- the two most frequent pages
SELECT approx_top_k(page, 2) FROM clicks;
-- [{item: a, count: 3}, {item: b, count: 2}]

-- merge two theta sketches, then estimate the distinct count
SELECT theta_sketch_estimate(theta_union_agg(s)) FROM (
  SELECT theta_sketch_agg(x) s FROM VALUES (1),(2),(3) AS a(x)
  UNION ALL
  SELECT theta_sketch_agg(x)   FROM VALUES (3),(4)   AS b(x));
-- 4

When to use it

Use it when you want approximate rollups that can be stored and merged later. Skip it when you need an exact answer. Common beginner mistake: asserting an exact sketch value in a test. The median varied from 497 to 501 across runs of the same query.

Visual

Merge two sketches, then estimate: the shared value 3 is counted once.

8. Arrow-native Python UDFs and UDTFs [Intermediate]

Since: 4.1.0 · Status: Ran; needs pyarrow · Source: SPARK-52214, SPARK-52979

Lineage: Arrow-optimized Python UDFs become the default in 4.2 (SPARK-54555).

What it is

A user-defined function (UDF) is Python code that Spark calls per batch of rows. A user-defined table function (UDTF) returns several rows per call. 4.1 adds @arrow_udf and @arrow_udtf (SPARK-52214, SPARK-52979), which hand the function whole PyArrow arrays instead of converting to pandas first. Arrow is the columnar in-memory format Spark already uses to move data between the JVM and Python.

Why it matters

This means a vectorised function stays vectorised: it computes over an array with PyArrow kernels, with no per-value Python loop and no pandas copy.

Under the hood, the data crosses from the JVM as Arrow batches either way, and the saving is the conversion to a pandas Series. The sample multiplies an amount column by 1.18. The function needs the pyarrow package. The release also adds Iterator[pandas.DataFrame] support in applyInPandas (SPARK-53614), UDT input and output in Arrow-optimized UDFs (SPARK-51619), yielding scalar values from an Arrow UDTF (SPARK-52934), and Arrow compression for pandas UDFs (SPARK-54226).

Sample code

Runnable file: 06_arrow_udf.py.

import pyarrow as pa, pyarrow.compute as pc
from pyspark.sql.functions import arrow_udf, col

# the function receives and returns a whole PyArrow array
@arrow_udf("double")
def with_tax(amount: pa.Array) -> pa.Array:
    return pc.multiply(amount, 1.18)

df.select("id", with_tax(col("amount")).alias("gross")).show()
# 1  11.799999999999999
# 2  23.599999999999998

When to use it

Use it when a numeric or columnar function can run on whole PyArrow arrays. Skip it when the logic is row by row. Common beginner mistake: forgetting to install pyarrow, which the official image does not include.

Visual

The Arrow-native path drops the pandas Series step.

When these features bite

Each item is a failure hit during the runs, with the text it produced, so you can grep for it. Every item is also an anchor, so you can link to one error.

ModuleNotFoundError: No module named 'yaml' from spark-pipelines. The CLI needs pyyaml and runs over Spark Connect, so it also needs grpcio and its companions. Fix: Install them, or pip install pyspark[pipelines].

TypeError: DataStreamWriter.trigger() got an unexpected keyword argument 'realTime'. Real-time mode has no Python trigger in 4.1. Fix: Use the Scala or Java API.

STREAMING_REAL_TIME_MODE.OPERATOR_OR_SINK_NOT_IN_ALLOWLIST. RealTimeModeAllowlist, with spark.sql.streaming.realTimeMode.allowlistCheck defaulting to true, accepts the Kafka source and the console, memory, foreach and Kafka sinks. Fix: Stay inside the allowlist. This row is from the source and the documentation, not from a run.

[RECURSION_LEVEL_LIMIT_EXCEEDED]. A recursive CTE with no stop rule hits the default limit of 100 levels (checked on 4.1.3). Fix: Add a stop condition, or raise it with MAX RECURSION LEVEL.

TypeError: unsupported operand type(s) ... 'type' and 'type' from a Python worker. The 4.1 tarball declares Python 3.10 or newer, and Python 3.9 cannot run it. Fix: Use a newer interpreter.

Parameter markers need bound arguments, so they go through the Scala API rather than a SQL file. This ran on the 4.1.4 tarball and printed P1 (the two eu rows), P2 (the first two rows of orders) and P3 (42):

spark.sql("CREATE OR REPLACE TEMP VIEW orders AS SELECT * FROM VALUES " +
  "(1,'eu',10.0D),(2,'us',20.0D),(3,'eu',30.0D),(4,'us',5.0D) AS t(id,region,amount)")

println("P1 " + spark.sql("SELECT * FROM orders WHERE region = :r ORDER BY id",
  Map("r" -> "eu")).collect().mkString(" "))
println("P2 " + spark.sql("SELECT * FROM IDENTIFIER(:t) ORDER BY id LIMIT :n",
  Map("t" -> "orders", "n" -> 2)).collect().mkString(" "))
println("P3 " + spark.sql("BEGIN DECLARE x INT DEFAULT :start; SET x = x + 1; SELECT x; END",
  Map("start" -> 41)).collect().mkString(" "))
sys.exit(0)

Adopt now or wait?

4.1.0 shipped on 16 December 2025 and has had four patch releases since, 4.1.1 to 4.1.4, the latest on 27 October

  1. The versioning policy gives a feature release a 6-month maintenance window, but 4.1.4 arrived ten months after 4.1.0, so read the window as a minimum. As of 18 November 2026, 4.1 is also the newest line for which Apache Iceberg (1.12.0), Apache Hudi (1.2.1) and Delta Lake (4.1.0) all publish Spark artifacts on Maven Central, which makes it the practical target for a lakehouse stack. My recommendation, a judgement and not a measurement: adopt the latest patch, 4.1.4, and try Declarative Pipelines on one pipeline with dry-run before you commit a team to it.

Known limitations in this release

  • Real-time mode. It covers stateless Scala queries on Kafka only, and Python has no trigger. I ran one query with three messages and made no latency measurement; the constraints and the vendor’s latency claim under feature 2 come from documentation, not from a run.
  • Declarative Pipelines. I ran a materialized view in Python and one in SQL. Streaming tables, flows and Auto CDC were not run, and the official image needs extra Python packages first.
  • Sketches. Results vary from run to run and with the core count, so no exact value is safe to assert.
  • Listed only. Spark ML on Connect, the JDBC driver, the transport changes, stored procedures, table constraints, join pushdown and Python transformWithState are from the release notes, not run.

Key takeaways

  • Pipelines: Declarative Pipelines derives the run order from references between datasets. Install the CLI’s Python packages before the first run.
  • Streaming: real-time mode covers stateless Scala queries on Kafka. It is the first release of a feature that grows in 4.3, so treat it as narrow.
  • SQL as a language: scripts and recursive CTEs move loops and hierarchies out of driver code and into queries.
  • Semi-structured data: VARIANT is generally available, and colon paths make reading a field a one-liner.
  • Test tolerance, not equality: sketch results shift from run to run, so assert a range.
